# HTTP Mode Invariants

**What holds HTTP mode together and is easy to break by touching the wrong layer**: OAuth admission, per-action write gating, the instance allow-list, routing, and how a call is bound to its credential and its POST.

> **Diátaxis type**: Explanation · **Audience**: 🛠️ Contributors & maintainers

The path a request takes through these layers is described in [Internal Architecture](architecture.md), and the decisions behind them in [ADR-0018](adr/adr-0018-authorization-admits-per-action-gating.md) and [ADR-0020](adr/adr-0020-one-server-per-configuration-shape.md).

---

Eight invariants of HTTP mode that are easy to break by touching the wrong layer:

- **One `mcp.Server` per configuration shape, not per credential** (ADR-0020). `serverShapeKey` in `cmd/server/shape.go` names what a server is built for: tool surface, capability surface, meta parameter-schema mode, tier and whether it was pinned, GitLab.com or self-managed, read-only, the narrowing a token carrying `read_api` and not `api` causes, safe mode, excluded tools, token scopes, statelessness, and the language the texts a person reads are rendered in (`GITLAB_MCP_LANGUAGE`, set per process, so it splits no deployment; the effective one, so a snapshot built by hand with no language shares the shape of `en`). The instance URL is deliberately **not** in it, because the client is per credential regardless and two instances of one tier share a catalog. What is per credential is `serverpool.Entry`: its client, its configuration, its rate-limit bucket, its resource watchers, its listen-stream ceiling and an opaque `Owner()` token minted from `crypto/rand.Text`. A shape server registers with `gitlabclient.NewUnboundClient`, which refuses every request, and each request's own client is installed on the context by `credentialStates.bindCredential` and read back by `(*gitlab.Client).For(ctx)` in `toolutil.WrapAction` and its three siblings, the 38 resource closures, the 37 prompt closures, the completion handler and the elicitation flows. **The binding middleware is added after the telemetry, rate-limit, listen-ceiling and subscription middlewares so that it runs before them**, and it reads the entry out of the per-POST carrier, which is why `carriedMCPHandler` wraps the SDK handler **inside** the gate: with the carrier outside it, the registry recorded the request context as it arrived, before the gate had resolved anything, and every call failed with `ErrUnboundClient` while every stateful session was refused as somebody else's. Watchers stay per credential because ADR-0015 makes the first read the authorization check; delivery is filtered by `sessionOwners.sendingMiddleware`, which drops anything untagged or addressed to a session with no recorded owner and forwards the rest with the private owner key removed from `_meta`. Two things about that middleware are not obvious and both were bugs first: it must read the **params**, never the request, because the SDK's legacy and 2026-07-28 delivery paths instantiate `ServerRequest[P]` differently and a type assertion on the request matches one and silently drops the other; and it must **never write** to the params it is handed, because the legacy path hands one params value to every subscriber, and go-sdk's main after v1.8.0 sends to each on a goroutine of its own (row 23 of `docs/development/upstream-bugs.md`), so it forwards a new request of the same shape carrying a copy of the params with the key removed, and drops a request of any other shape. Putting the key back after the send, which it used to do, lost notifications and handed the key to clients once delivery ran concurrently. The `_meta` map is never mutated either: the stripped one is a new map, and on v1.8.0 the shared one is where the SDK stamps its subscription id. Session ownership is recorded rather than derived, because `ServerOptions.GetSessionID` takes no request and a per-server tag stops meaning anything once a server serves many credentials. Eviction is the other end of that: an entry whose credential still holds watchers or open `subscriptions/listen` streams is **not** idle-evicted (`serverpool.WithInUse`, consulted on the idle sweep alone, because `lastUsed` is refreshed by pool hits and a subscription produces none), and an entry evicted anyway has its own streams closed by owner, since `Manager.Close` fires no `OnStop` and the client would otherwise be left holding a stream that never speaks again.

- **Admission asks for the minimum, not the deployment's scope.** `oauth.MinimumScope` (`read_api`) is what the door checks; `oauth.RequiredScope` is only what the challenge _recommends_ and the first entry of `oauth.SupportedScopes`. Since issue 952 the legacy door asks the same minimum through the one predicate `gitlabclient.MeetsMinimum`: a token GitLab accepted that carries neither `read_api` nor `api` (the probe answering `403 insufficient_scope`, or the token's description naming `read_user` or other scopes below it) is answered `403`, uncharged and remembered in ADM-006's structure, before the tier is asked and under `--ignore-scopes` too, and an entry later found below it ends with `CauseBelowMinimum` and its verdict is recorded through `ServerPool.RememberBelowMinimum`. Scopes nothing answered for (`nil`) are not below it. On stdio the same predicate reads the process's token at start, under `--ignore-scopes` too, and a token below it leaves the process answering the handshake while the readiness gate refuses every catalog method with `-40300` (`readinessGate.markRefused`); a version GitLab refuses for want of a scope (`gitlabclient.VersionRefusedForScope`, what a `self_rotate` or `read_repository` token gets) counts as an instance that answered, so the start asks the token's scopes rather than waiting a round for a recovery that never comes, and is a refusal on its own, since that endpoint takes `read_user`, `ai_features`, `ai_workflows`, `api` and `read_api`: the process refuses even when the token's description went unanswered. A `read_api` token is admitted by a deployment that writes and is served the actions whose requests GitLab accepts from `read_api` ([ADR-0026](adr/adr-0026-read-api-token-served-what-gitlab-accepts.md)): `gitlabclient.NarrowToTokenScope` sets `ServerConfig.ReadAPIOnly` when `WriteCapable` says the token cannot write, per pool entry in HTTP mode and once at startup on stdio, and `actioncatalog.Catalog.FilterReachableWith` keeps the actions whose classic scope, derived from the requests each sends and carried in the generated table (`finegrained.Requirement.Classic`), `read_api` reaches. That is not the read-only surface: two reads GitLab answers only from `api` (`template.lint`, `project.dependency_firewall_evaluate`) are withheld and five actions the catalog calls writes are served (`package.download`, `access.token_personal_revoke_self`, and three GitLab authenticates by another credential the caller passes). `ServerConfig.ReadOnly` is the operator's switch alone, and `FilterActionCatalog` runs it before the `read_api` step so an action both remove is reported as the operator's; a meta group keeps its read-only hint only when every action it keeps reads. The standalone guided flows post, and `toolvisibility.Apply` removes them by the same rule (`tools.StandaloneToolsBeyond`). Do not reintroduce a deployment-wide scope demand at the door: that is what refused a read-only OAuth application at `initialize`. Unknown scopes (`nil`) mean write-capable: a wrong "no" silently removes tools, a wrong "yes" surfaces as GitLab's own 403. **A narrowed surface must say it is narrowed.** `tools.FilterActionCatalog` returns what each filter removed, split into `ByTokenScope` (each with the scopes the credential lacks for it, `api`, `admin_mode` or both, from `gitlabclient.MissingClassicScopes`) and `ByOperator`, and the dynamic registry answers a request for one of those with the cause, naming those scopes (`dynamic.WithWithheldActions`), instead of `unknown action … Did you mean …`. The dynamic catalog is built by `dynamiccatalog.Build`, in `cmd/server` and in the e2e suite alike: the suite used to assemble its own copy without that bookkeeping and was green on the copy. The suggestions in that older message were all real read-only actions, so a model reading it concluded the server lacked the capability rather than that the credential was narrow. Tools removed by name through `--exclude-tools` stay out of both lists: the operator asked for them not to exist.

  **The scope filter is applied to the catalog, never to registered tool names.** `MetaToolScopes` in `internal/tools/scope_filter.go` maps a catalog **group** name to the PAT scopes every action in it needs, and `FilterScopeFilteredCatalog` removes the group before anything is registered: on meta and dynamic that removes the group a caller would name, and on individual it removes every tool that group projects. Both catalog assemblers apply it, `SharedMetaCatalog` through `FilterActionCatalog` and `SharedIndividualCatalog` directly, and both key their shared catalog on `catalogRelevantScopes` so a caller cannot pin one catalog per scope subset in a cache that never evicts. There is deliberately **no** second pass over registered names in `toolvisibility.Apply` (the post-registration pass, shared by `cmd/server` and the surface evaluator since 3.1.0 so a read-only or safe-mode meta evaluation withdraws or previews the `gitlab_interactive_*` flows the way the binary does): that is what the individual surface used to be filtered by until 3.0.0, and nothing there is ever called `gitlab_admin`, so it matched nothing and all 92 admin tools stayed listed for a token with no `admin_mode`. The calls were refused by GitLab, so it was a listing defect rather than an authorization one, which is the worse half to leave: a model reads `tools/list` to decide what is possible. Removal is all-or-nothing per group, so a group belongs in the map only when every action in it needs the scopes; `gitlab_admin` is the one entry that strains that rule, since four of its reads (topics and broadcast messages) are served to any token and go with the rest.

  **A fine-grained personal access token is unknown authority, and its grant decides per action** ([ADR-0024](adr/adr-0024-fine-grained-token-authority-per-action.md), [guide](https://docs.jmrp.io/gitlab-mcp-server/operations/fine-grained-tokens/)). Its scope list is the single value `granular`: `gitlabclient.FineGrained` recognizes exactly that shape, `WriteCapable` answers true for it and `CatalogScopes` maps it to nil, so it is never narrowed to read-only, keeps the `admin_mode` groups, and shares the catalog key of a classic token whose scopes are unknown and never that of a token with none (`AUT-001`, `AUT-002`). `oauth.SatisfiesMinimum` counts it as meeting `read_api`. A door probe GitLab answers `403 insufficient_granular_scope` (the token lacks User: Read) is a fourth verdict, `CredentialAcceptedPermissionMissing`: both doors answer it `403` `-40300`, uncharged (`INV-007`), quoting GitLab's sentence in the body only, filtered and cut at 512 bytes, with a constant `error_description` in the bearer challenge, and remember it in the rejected-token cache for five minutes (`ADM-001`, `ADM-002`, `ADM-006`), since nothing edits a grant after creation. What a session is shown is an immutable `*finegrained.Authority` on the credential's client (`Client.SetAuthority`, `gitlabclient.AuthorityFrom(ctx)`), built per pool entry (per process on stdio, attached after registration and before the readiness gate opens so the first `tools/list` is already narrowed) from `DetectToken`, `ReadGrant` (1 MiB and 1000 scopes through `WithResponseLimit`, `RQB-011`) and the validated `/version`, taken under a `POL-006` probe slot after `DetectTier`, and replaced whole on every accepted revalidation only by reads that answered (`INV-009`). A `DetectToken` that got no answer (anything but GitLab's 403 refusing Personal Access Token: Read) leaves the kind unknown (`TokenFacts.KindUnknown`, set too when the OAuth verifier admitted the token on its own `api` assumption, `oauth.ScopesAssumedKey`): the client carries no authority and the whole catalog is served until the kind is asked again (`RedetectToken`), on each accepted revalidation, on the stdio timer, and as soon as a degraded stdio start's client recovers (`Client.SetOnRecovered`); the round that learns a fine-grained token attaches its authority, and the scope narrowing the build decided stays. Phase B (the grant read, the instance on the recorded 19.5 release, every assignable name known) lists what the grant reaches and lets a call through where GitLab would serve it on a public project or group; anything else is phase A, which withholds only the 55 actions no fine-grained token reaches at 19.5.0, and the prerelease of the next minor (GitLab.com's `19.6.0-pre`) is phase B for the listing only. The orbitlive suite holds the version GitLab.com reports to that rule (`TestOrbitLiveGitLabCom_Version_IsOneTheActionTableJudgesAGrantAt`), so GitLab.com moving past the table fails a run rather than putting its fine-grained sessions in phase A unnoticed. A classic token's client carries no authority, so its path and cost are what they were. The grant and the version **never** reach `serverShapeKey`, `CatalogFilterKey` or `manifestShareKey` (`INV-010`, `TestServerKeys_AGrantReachesNoKey`): one shape server serves classic and fine-grained credentials and narrows per request, at `toolvisibility.CallMiddleware` (added after the argument limit and before the rate limiter, so it answers before validation and spends the call's rate token), the dispatcher check `toolutil.FineGrainedRefusal` (before confirmation and safe mode on every surface), `toolvisibility.ListingMiddleware` (right after the rate-limit block, outside the limiter, so `RTC-007` keeps charging the shape's full count), find, and `gitlab://tools` per read; each returns the whole surface under `toolutil.IsInternalInspection` (`AUT-007`, `AUT-008`).
- **Routing happens before authentication, and the gate resolves only what can act on a session: every POST, and GET and DELETE on `--stateless=false`.** `mountMCPEndpoint` mounts the MCP handler on `/{$}`, `/mcp`, and the `--public-url` path prefix (for a proxy that forwards its prefix instead of stripping it); everything else is an unauthenticated 404. On `--stateless=false` a GET opens a session's standalone SSE stream and a DELETE terminates the session, so both are resolved and ownership-checked like a POST (`mcpServerGate.addressesSession`). Every other request passes `mcpServerGate.middleware` with no credential resolved and no session checked, and the SDK answers it 405: on `--stateless` that is every non-POST method, whatever it carries, and in both modes it is OPTIONS, HEAD and any other method. OPTIONS is the one that has to pass, since a CORS preflight is sent without credentials by definition (one from a trusted origin is answered by `corsMiddleware` before it gets that far), and `TestMCPServerGate_NonPOSTMethods_ReachTheHandler` pins both modes. Nothing behind the gate may assume it ran for such a request; this is the gate's rule alone, and in OAuth mode the SDK's bearer middleware in front of it checks a token on every request first, a preflight included, which `bearerGuard` before it lets past. The SDK's own server-initiated keepalive ping is off for every HTTP pool entry (`withKeepAlive(0)`), stateful included, because it closes a session on the first unanswered ping, which idle clients fail. Liveness is the SSE keep-alive comment in `sseAwareWriter` instead, which puts bytes on the wire without asking the client for anything. A catch-all auth gate told every scanner that `/.well-known/oauth-authorization-server` was a protected document that is not there. `securityHeadersMiddleware` is the outermost wrapper so even a middleware that answers instead of forwarding (host validation's 403) carries `nosniff`, CSP, `X-Frame-Options` and `Referrer-Policy`.
- **The card routes serve two different documents, and merging them back would undo the point.** `/server-card` and `/mcp/server-card` answer the SEP-2127 card (`cmd/server/discovery_card.go`): identity, and a `remotes` block when `--public-url` names an address. The extension reserves `<streamable-http-url>/server-card`, and the endpoint answers at the root and at `/mcp`, so the card is mounted after both, each again under `--public-url`'s prefix (`publicPaths(cfg, serverCardPath, mcpEndpointPath+serverCardPath)`); until #533 it was at `/server-card` alone, so an endpoint published as `https://host/mcp` answered 404 at the one card URL a client derives from it. `publicURLPath` returning "" for a path of exactly `/mcp` is what keeps that mount from being registered twice, which ServeMux refuses with a panic; a path that only ends in `/mcp` (`/gitlab/mcp`) is a prefix like any other. It carries no tools, resources, prompts or capabilities, because that extension omits primitives on purpose, so nothing should ever add a tool list there to satisfy a scanner. `/.well-known/mcp/server-card.json` keeps the enumerating SEP-1649 document `buildServerCard` produces, which is the unauthenticated answer to what the server can do and the one a scanner wants. Only the legacy route runs the build-once-in-the-background machinery, because only that document registers a catalog; the SEP-2127 card is rendered from constants and flags at mount time. Until 3.1.0 both paths answered the enumerating document and differed only in `Content-Type`, which left the older shape at the location SEP-2127 reserves and forced the public deployment to shadow `/server-card` with a static file in nginx. `TestDiscoveryCard_AgreesWithServerJSON` is what stops the card's identity constants drifting from `server.json`; `isRequired` is deliberately excluded from that comparison, since the card schema defines it as whether the input is needed for the connection to succeed while the registry schema surrounds it with fields about configuration a user is prompted for. `/.well-known/ai-catalog.json` is deliberately not served (the catch-all's unauthenticated 404): an AI Catalog lists everything a host publishes, which only the deployment knows, so the HTTP server mode guide carries the entry (`url` = `<--public-url>/server-card`, no `displayName` or `description`) and an nginx location serving it with `types { }` plus `default_type application/ai-catalog+json`.

  **Both cards and the RFC 9728 document carry an `ETag`** (`cmd/server/etag.go`), so a client holding a copy revalidates instead of downloading 137 KB again; `http.ServeContent` does the conditional handling rather than a comparison of our own, because If-None-Match is a list, `*` is a value of its own, the function a GET uses is the weak one, and a compressing proxy forwards the tag weakened. The tag is a hash of the document's own bytes and of nothing about the process, which is the property the whole thing rests on for a fleet: replicas serving one configuration publish one tag, so a client revalidating against a different replica than answered it is still told 304, and `TestServerCard_TwoReplicasPublishTheSameValidator` holds that by starting two binaries. A per-process tag (a start instant, a random string, the build digest) would miss on nearly every conditional request and would do it silently, since the 200 it produces is still correct. `/health` deliberately has none: `uptime_seconds` makes its body differ on every probe. The metadata document is the one this package publishes without rendering, so `capturedResponse` buffers what the SDK handler wrote and hashes exactly those bytes rather than re-marshaling the struct to hash a copy.
- **There is one Host guard, and it is ours.** `cmd/server/host_guard.go` decides which `Host` a deployment answers: the loopback names, the host `--http-addr` binds when it names one, and the host `--public-url` advertises, plus anything forwarded by a peer listed in `--trusted-proxies`, asked through `trustedProxies.trustsPeer`, the one question the authentication budgets' address asks too, so a `unix` entry means the socket's peer to both. A wildcard bind declares no host and falls back to the rule the SDK used to apply for the MCP endpoint alone: refuse a non-loopback `Host` on a connection accepted over loopback. `StreamableHTTPOptions.DisableLocalhostProtection` is therefore set, and must stay set: the SDK's copy cannot see either flag, so with it on, every reverse proxy in the deployment guide is answered 403 (they all preserve the client `Host` and connect to 127.0.0.1) and `--public-url` cannot help. A request carrying **no** `Host` at all is served, because a balancer health check sends none and no browser omits it.
- **The instance is chosen from an allow-list, and verification follows it.** `--gitlab-url` is repeatable; `serverpool.ResolveRequestOptionsFor` refuses a `GITLAB-URL` header naming an unpublished instance instead of ignoring it, `oauth.NewGitLabVerifierFor` verifies against the instance the request selected, and `oauth.TokenCache` keys on instance **and** token. Keying that cache on the token alone would let a credential verified against one published instance pass as identity on another. `oauth.TokenCache` is bounded at `tenancy.OAuthCacheCapacity` (10000, held equal to `PoolSizeMax` by the values test) and makes room by dropping an expired identity or else the least recently used one, a take across keys issue 950 decided (`ADM-005`); the verifier's round trips run under `tenancy.OAuthVerifications` (16) slots of its own, not the pool's probe slots (`ADM-014`), and a request refused for want of a slot is answered from the same return and in the same words as a verification with no verdict (`bearerGuard.classify`), so the wording adds nothing to the one bit `INV-019` accepts.
- **Held calls are counted where the SDK dispatches them, and the gate counts only what its headers prove.** `heldRequestsMiddleware` (`HLD-011`) takes one of `processHeldRequests`' slots for every call that reaches GitLab (`MeterFor`'s tool-call and completion buckets, a `subscriptions/listen` aside) arriving on an HTTP POST, so each call of a JSON-RPC batch counts and a client's response to an elicitation never does; it runs before the rate limit, and refuses the way the rate limit refuses the same method. On protocol 2026-07-28 or later, where the SDK holds `Mcp-Method` to the body and refuses batches, `mcpServerGate.middleware` takes the slot itself after admission and hands it to the call through the carrier (`gateHeldSlot`), refusing with a 503 that closes its connection. The ceiling is `heldRequestsFor(descriptors)`, read once at startup from `RLIMIT_NOFILE`, which the Go runtime has already raised to the hard limit. A held call makes no pool entry busy (`POL-003`), and an entry evicted while it holds one leaves the call running. On `--stateless=false` the gate also takes one of `processStatefulSessions`' slots (`HLD-010`, half the held-call ceiling) and one held-call slot for the session's standalone stream (`mcpServerGate.takeSessionSlot`) for every POST carrying no `Mcp-Session-Id` on a revision before 2026-07-28, after admission and before the SDK creates a session, and refuses it past either ceiling with the held-call ceiling's 503 word for word; the first request dispatched on the new session keeps both slots through the carrier (`claimSessionSlot`, `statefulSessionsMiddleware`) and a goroutine waiting on `ServerSession.Wait` gives them back, while a POST whose session did not survive it gives them back as the gate returns. The standalone `GET` takes no slot of its own, so a session the process keeps is never refused its stream: the go-sdk client never asks again for a stream it was refused, and would lose every message the server sends outside a response. `processSlots` is the one count type both ceilings use. Issue 951 decided what stands beside them, which is nothing: no per-credential ceiling beside either and no metering of `initialize` (`RTC-004`), because the credential is a key a caller can mint and a number or a price on it multiplies with every token a caller mints, so one credential can fill either ceiling; and no memory cap, fixed or derived, since the memory limit the process runs under (a container's, or a systemd unit's `MemoryMax`) bounds memory where the descriptor limit is large. Windows, which has no descriptor limit to read, is sized as 1024 rather than left unbounded.
- **The POST is the lifetime of the calls it carries, and the handler learns that through a header.** `requestCarriers` in `cmd/server/carrier.go` stamps every POST to the MCP endpoint with a minted token, registers that request's context under it, and an `mcp.Middleware` binds each incoming call to it, so abandoning the POST cancels the handler and with it client-go's retries. The handler context does not descend from the HTTP request (the SDK ignores `req.Context().Done()` on purpose, for resumability), and `StreamableHTTPOptions.PropagateRequestCancellation` only covers protocol 2026-07-28, which is exactly the revision that can already send `notifications/cancelled`. The header is the mechanism because it is the only per-request channel the SDK exposes (`mcp.RequestExtra.Header`): a context value would work in stateless mode, where the session is connected with the POST's own context, and be wrong in stateful mode, where it is connected with the **initialize** POST's. Notifications are deliberately exempt, since no POST waits for one and their handlers can outlive the carrier. This is exact rather than a bound because no `EventStore` is configured, so a response whose POST is gone can never be delivered; adding one would make it a heuristic and this decision would have to be revisited.

Nothing here should need a reverse proxy to be correct: the binary answers its own CORS preflights, its own 404s, its own security headers, and can terminate TLS or listen on a unix socket itself.
