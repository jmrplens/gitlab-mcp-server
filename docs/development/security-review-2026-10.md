## Why this record exists

The OpenSSF Best Practices gold criterion `security_review` asks that the
project has performed a security review within the last five years, and that
the review considered the security requirements and the security boundary. The
project's own members may make it, supported by static and dynamic analysis,
and a person has to review it as well, to find what tools cannot, in the design
above all.

The requirements and the boundaries this server holds itself to are the threat
model and the security considerations of [SECURITY.md](../../SECURITY.md). This
page takes each of them in turn, says where the code enforces it and what would
fail if it stopped holding, and lists what the review found and where each
finding is tracked.

## The assumptions

SECURITY.md assumes that the operator is trusted and chooses the token and its
scope, that GitLab enforces its own authorization, and that the host running
the server is not already compromised. The rows above rest on those three and
on nothing further that this preparation found. The one place the server acts
on a caller's choice of destination, `--allow-any-gitlab-url`, is refused
unless the listener is loopback or a unix socket, where the caller is the
operator (`TestGate_TheEscapeHatchIsRefusedOnAReachableListener`). Confirming
that no row rests on more is the maintainer's.

## The project's websites

The OpenSSF Best Practices criterion `hardened_site` asks the project's
website, its repository and its download site for `Content-Security-Policy`,
`Strict-Transport-Security`, `X-Content-Type-Options` as `nosniff` and
`X-Frame-Options`, each with a value that is not permissive. The repository,
the release pages and the source archives (`codeload.github.com`) are served
by GitHub with all four; a release asset itself is redirected to
`release-assets.githubusercontent.com`, a blob store that serves no HTML and
sends none of them. The packages are served by their registries. The
documentation site,
[docs.jmrp.io/gitlab-mcp-server](https://docs.jmrp.io/gitlab-mcp-server/), is a
GitHub Pages build behind Cloudflare, and on 26 October 2026 it sent
`Strict-Transport-Security` and `X-Content-Type-Options` and neither of the
other two.

`cmd/audit_site_headers` now judges the four after every deploy, in the
`headers` job of `.github/workflows/pages.yml`, and fails when one the site
serves is lost or turns permissive. The two it lacks are declared pending: they
are reported with the value to set and do not fail the job, because only a
Cloudflare rule, which the maintainer sets, can add them. The value it
recommends for `Content-Security-Policy` was written from what the site's 216
pages load, and with it and `X-Frame-Options: DENY` injected into every
response each page loaded in Chromium with no violation, the theme switch and
the search worked, and the external badge images loaded.
[Repository Settings](repository-settings.md#documentation-site-response-headers)
says what the rule sets and why.

## What the maintainer's review covers

What tools cannot find is the part of the review that rests on a person, the
design above all. The maintainer's reading takes each row above against the
code at the commit, and in particular:

- whether the four boundaries are still the ones that matter, and whether
  anything has crossed one of them since the September audit without a test
  that would fail;
- whether any row rests on more than [the assumptions](#the-assumptions);
- the decisions recorded as ADRs that a boundary rests on (0018, 0020, 0022,
  0023, 0024 and 0026), and whether what each decided still holds;
- the statements recorded as not traced, and whether each is enforced
  somewhere this preparation did not find, should be, or should leave
  SECURITY.md;
- finding 8, the statement whose row waits with it, and whether it changes the
  result of any row above;
- whether each severity in [Findings](#findings) is the right one.
