# Test Infrastructure

**What the shared test transport does for every unit test, and the rules a test is held to**: the mock GitLab, the schema and cost checks on every GraphQL request, the request recording, and the conventions the gates enforce.

> **Diátaxis type**: Reference · **Audience**: 🛠️ Contributors & maintainers

How to run the suites and the patterns a domain test follows are in the [Development Guide](development.md#testing); the generated per-package reference is [Testing](testing/README.md).

---

All tests use `httptest` to mock GitLab API responses. Shared helpers in `internal/testutil/`:

- `testutil.NewTestClient()`: creates a mock GitLab client pointing to an httptest server
- `testutil.RespondJSON()`: responds with a JSON body
- `testutil.RespondJSONWithPagination()`: responds with pagination headers
- `testutil.ProgressMessages(t, elicit, call)`: runs a handler with a request that asks for progress, on an initialized session, and returns every progress message the server sent while it ran, in order (`testutil.RecordProgress(server)` is the recorder underneath); a handler called with a nil request has no tracker, so a test of what it tells a person while it works goes through this
- `testutil.CancelOnArrival(t, respond)`: a context cancelled when the first request reaches the mock, and a client whose mock holds each request until the client abandons it; a handler returns `context.Canceled` promptly only if its first request carried the context, and a request that sits out the hold, sent without it, fails the test at cleanup, which is what holds a handler's later requests to the same rule. A context cancelled up front cannot show this in a handler that checks `ctx.Err()` before it builds anything, as the handlers it was written for do
- **The mock refuses what GitLab refuses.** `NewTestClient` wraps the handler it is given, and every POST to `/api/graphql` has its document and its variables validated against the pinned GitLab schema in `internal/graphqlschema` before the mock answers. Until this existed no GraphQL test could fail for the reason that matters: the handler returned whatever the test wrote, so a green test proved our code agreed with our own fixture and nothing about GitLab, and four registered tools shipped documents no current instance accepts. The document half catches an unknown field, an argument the field does not take and a variable typed as something the argument is not; the variables half catches a variable sent that the operation never declared, which is what let eight domains advertise a backward pagination no operation asked for. A query carrying a file is read out of the `operations` part of its multipart body and judged the same way: it used to be waved through for not being the JSON envelope, which exempted the one mutation this server sends with a file attached (an achievement's avatar) and so the one whose variables the SDK rewrites on the way out. A refusal is reported with `t.Errorf` and the request still proceeds, so the test's own assertions report too, and never with `t.Fatal`, which would abort the httptest server's goroutine. `testutil.AllowInvalidGraphQL(t)` exempts a test that deliberately sends a malformed document and belongs nowhere else. A document no test drives is covered by `make check-graphql-documents` instead. See [GraphQL Integration](graphql.md)
- **The mock records what the request was.** The same wrapper writes down every request a test issues: the method, the path with its identifiers replaced by placeholders named after the collection in front of them (`/projects/:project_id/issues/:issue_id/notes`), the query parameter names, the top-level field names of a JSON body or the part names of a multipart form (an upload's file and every option client-go writes beside it, read up to 8 MiB and put back for the mock), and for GraphQL the operation and the variables the document declares, an upload's `operations` part included. It also counts, per row and per placeholder, how many **distinct** raw values it templated away, which is the one thing the fold discards that a reader needs back: with a single fixture value a handler that reads the caller's project and one with that id written into it produce the same row. The count is running rather than final, since the recorder has no shutdown hook to write a total from, so a new value costs one more line and the merge takes the highest; the values themselves never leave the test process. Recording is off unless `GITLAB_MCP_TEST_INVENTORY_DIR` names an absolute directory, `make gen-request-inventory` runs the suite with it set, and `cmd/gen_request_inventory` merges the shards into `docs/development/request-inventory.json`. It exists because all five dimensions of the 1:1 audit describe the surface and none of them looks at the request a handler builds, which is how nine registered tools shipped unable to work. A row's names are a union over the calls that package made, never one call's set, so the file says which parameters an endpoint was sent and not which of them were sent together. The attribution is the package that built the client and the test that built it, never the action: nothing on the wire names an action, and the httptest server answers on its own goroutine where the calling test is not on the stack. CI records during the coverage job and gates the artifact with `go run ./cmd/gen_request_inventory/ -check`; the race job records too, since the recorder is the one concurrent thing the test transport has
- **A document's cost is held to what GitLab measured.** GitLab refuses a query whose complexity exceeds 250 for an authenticated user (300 for an administrator) before it runs anything, and the schema says nothing about cost, so the transport cannot see it. `testutil.GitLabQueryComplexity` runs GitLab's computation over the pinned schema, with the per-field costs GitLab's Ruby sets (Gitaly surcharges, per-item multipliers, free fields) in a table that holds only what a measurement needed, so a test holds the estimate equal to a figure GitLab reported for the same document and under the limit: a change to the selection changes the estimate and sends whoever made it to measure again, which needs no credential (the refusal names the figure, and below 200 a `queryComplexity { score }` selection does). The epic notes and discussions list documents are held at 220; see [GraphQL Integration](graphql.md)
- **Never `t.Fatal`/`FailNow` off the test goroutine** (httptest handlers, `go` statements, MCP handlers): follow the six-rule contract in `.github/instructions/test-goroutines.instructions.md`: `t.Errorf` + deterministic response + `return`, or record with atomics and assert afterwards. `make check-test-goroutines` detects violations; `make audit-test-goroutines` writes the work list
- **Every case table runs under `t.Run`**: a range over a slice or map literal that asserts must open one subtest per case, named by a `name` field, the string element, or the map key. `go run ./cmd/audit_test_subtests/ -fix` rewrites the unambiguous shapes; `// sequential: <reason>` on the line above a loop declares dependent steps rather than cases; `make check-test-subtests` gates it in CI
- **An address nothing answers comes from `internal/testutil/netfixture`, never from a closed `httptest` server.** Closing a server gives its port back at once, and the next listener given it, a parallel test of the same package or a test binary of another package in the same coverage run, can answer the request the test exists to see fail: `cmd/bench_resources` failed that way in CI (fixed in pull request 1131), and issue 1132 moved sixteen more sites. `netfixture.DeadEndpoint(t)` holds a loopback port for the whole test and closes every connection it accepts before reading a byte. `netfixture.NewStoppableServer(t, handler)` answers through its handler until `Stop`, then hangs up on every request, a connection kept from before included, and keeps its port, which is what a test needs whose client or cache is bound to an instance that answers first and then goes away. A request to either ends with an EOF or a reset, not `connection refused`, so a test holds that no answer came rather than how the connection ended. A client constructor sends nothing, so a case about an unreachable instance builds its client on the dead address from the start. The package sits beside `internal/testutil` rather than in it because `internal/gitlab`'s own tests use it and `testutil` imports `internal/gitlab`. `make check-closed-servers` ([`audit_test_closed_servers`](cmd-utilities.md#audit_test_closed_servers)) refuses a server closed while its address, or a value built from it, is still used later in the function
- **A test that compares a committed generated artifact calls `freshness.SkipIfDeferred(t)` first**, before it reads or measures anything. That is the one reader of `GITLAB_MCP_TEST_SNAPSHOT_PARITY` (`internal/freshness`), which CI answers from `FRESHNESS`, and it is what lets a stacked layer leave the artifacts stale on purpose and refresh them once at the top. Guard the comparison and nothing else: a test that also asserts something about the surface keeps that half running (`cmd/gen_llms` guards one subtest per committed file, not the whole test), and a test driving a replica in a `t.TempDir` is not a freshness comparison and is never deferred, which is what keeps a stale artifact failing the checker itself on every run
- **The e2e support packages are held to the whole-package rule against their offline tests and the complete runs together.** `test/e2e/internal/fixture` and `test/e2e/modeleval` are mostly code only a GitLab reaches, the fixture builders, the model evaluation's worlds and the sessions that start the real binary, so their own tests leave out most of what the suite reaches and the offline figure is not the measurement of them (issue 1461). For these two packages the 100% a touched package is held to is taken on the merge: a statement is reached when their offline tests or a complete run (`make test-e2e-ce`, `make test-e2e-ee`) reaches it, and a statement neither reaches needs a test or a reason. Two parts of that code no complete run measures today: no package the complete runs test imports `test/e2e/modeleval`, whose online code runs under `make modeleval-ce` and `make modeleval-ee`, which write no profile, so its runs' half is absent; and a test binary writes its profile when its last test ends, so what only the `harness.AtExit` hooks reach after it (the World's teardown, the run's exit sweep, the model evaluation's record flush) is in no run's profile. CI runs no GitLab, so the runs' half is committed: after the complete runs the instance allows on the tree being committed (`make test-e2e-ce`, and `make test-e2e-ee` with an EE license), `make e2e-support-coverage-record` writes `docs/development/e2e-support-coverage.json`, which keeps every declaration the runs reached into by its key and the hash of its text, and every package with the number of statements neither half reached. It takes a run profile only beside the stamp a complete run of the tree leaves, the SHA-256 of every source file of the two packages that `run-docker-e2e.sh` writes before each pass builds and keeps only once the run ended complete, so a run that failed or skipped scenarios, or a run of an older version of the code, is never recorded as this tree's. A record of the CE run alone leaves what only the licensed run reaches to neither half, inside the ceiling, until a licensed run is recorded. The coverage job of CI runs `make check-e2e-support-coverage`, which runs the offline half on the pull request's tree, credits the record's reach to each declaration whose text is still what the runs ran, and fails a package with more statements reached by neither half than the record allows ([`merge_coverage`](cmd-utilities.md#merge_coverage)). A change that rewrites a declaration only the runs reach, or adds code only they can reach, therefore cannot pass on the offline figure while the package stands at its ceiling: it reaches the code with a test, or records a complete run of its own tree. The ceiling is a count, not a list of statements, so statements a test has reached, or a change has deleted, since the record was taken leave that many to spare, which the gate reports as a ceiling the next record lowers, and a change can spend them until a record is taken again. Below a stack's top, where `FRESHNESS` is deferred, an excess a record older than the tree explains is a note, and the top records the run; an offline test lost from a package the record still describes fails on every layer, while in a package the record no longer describes (a recorded declaration dropped, or its statement count moved) it is part of that note until the top. The record's counts are taken from the offline half of the machine that writes it, so it is written where those tests run as they do in CI. Until the first record is committed the gate reports the offline half and holds nothing, and the count the first record leaves to neither half is the ceiling until the statements behind it are covered or given their reason, the step of issue 1461 that follows the first measured runs
- Test naming: `TestToolName_Scenario_ExpectedResult`
- Test-file naming: a `_test.go` exists only under the name of a module it tests (`register.go` → `register_test.go`); `export_test.go`, build-constrained qualifiers (`file_utils_unix_test.go`), external-package qualifiers (`kind_integration_test.go`), and `test/e2e/` are the codified exemptions. `make check-test-file-names` gates it in CI
