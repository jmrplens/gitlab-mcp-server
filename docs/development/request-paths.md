# Request Paths and Fine-Grained Grants

**The dimensions of the 1:1 audit that read the requests a handler sends rather than the surface it publishes**: R-PATH, which holds each request and each answer to GitLab's own records, R-GRANT, which derives what a fine-grained token needs for each action, R-PARAM, which holds every param a route this server reaches declares to whether anything here can send it, and R-ROUTE, which holds every route the live record mounts to an action that sends it or a reason none does.

> **Diátaxis type**: Reference & Explanation · **Audience**: 🛠️ Contributors & maintainers

The other five dimensions (R-INPUT, R-OUTPUT, R-ACTION, R-META and R-ENUM) and the flags of the command that runs all nine are in [Command-Line Utilities](cmd-utilities.md#audit_1to1).

---

## Request paths (R-PATH)

The sixth dimension of the 1:1 audit, `go run ./cmd/audit_1to1/ -scope=paths`, and the only one that reads the request a handler builds. The other five compare what we **publish** against what the SDK and the API documentation **offer**, which is why all five were green while nine registered tools could not work: a perfect input struct, a perfect output struct, a registered action, complete enums, and a request GitLab refuses. Its input is `docs/development/request-inventory.json`, recorded by the test transport and committed by `cmd/gen_request_inventory`.

Seven checks, three of which gate. Six need no network and no suite run (`make audit-1to1-paths`, run by `make analyze` and by CI's generated-artifacts job); the endpoint one needs 250 documentation pages, so it runs only when asked for (`make audit-1to1-paths-endpoints`) and nothing schedules it. Four of them read the inventory as a list of endpoints and parameter names, which is what the recording keeps of a request, and the document check reads the source; the last two read **values**, because names alone leave two whole classes invisible:

- **Has the path ever been observed.** An action whose owning package issued no request has never had its request seen by anything. Held at package grain, because nothing on the wire names an action, and the report says so beside the number (`actions_observed_grain`): 1090 of 1090 on 2026-10-20 means 1090 actions whose _owner_ issued something, which is a regression guard and not per-action assurance. A silent package means either that nothing drives it or that the inventory is stale, and the finding cannot tell those apart. A package silent for a reason is held to a declaration with a category and a reason in `cmd/audit_1to1/internal/paths/declarations.go`, and a declaration that no longer describes the tree is itself a finding. No package is declared today: `internal/tools/adminspecs` was the one entry, for declaring 92 specs whose handlers live in other packages, until each of those actions was given the domain package its route names as its owner. Naming the owner where the handler lives is the better answer of the two, because a declaration excuses a join that cannot be made while a true owner makes it, and the sharper join is what put `admin.system_hook_list` on R-PAGE's list below. An action whose owner names no package fails too: nothing in the catalog validates that field, and such an action used to be classified unmapped, which the gate ignored and `-gaps-only` dropped, so it could be neither counted nor seen. The owner `tools` is the catalog's own exception, for the orchestration package rather than a domain under it, and resolves to `internal/tools`. An owner that names a real package and the wrong one is a lie no version of this can catch, since the recording joins on that name and nothing else.

  **The grain sharpens to the action where an end-to-end run speaks** (`e2e_observation`, `make audit-1to1-paths-e2e`). The unit recording cannot name an action because the httptest server answers on its own goroutine; a Docker run can, because the harness stamps a trace id into each MCP call, the server's span carries it back with the route the dispatcher actually chose, and every GitLab request the handler made is a child of that span. The receiver counts those children per trace and the harness writes the count on the `dispatch` line it already emits (`e2ecalls.Dispatch.Requests`), so `-e2e-calls <dir>` answers, per action, which were seen issuing a request and which ran and issued none. It **reports and never gates**, and both halves of that are about what a missing record means: the shards are a byproduct of a run CI does not schedule and never commits, so failing on their absence would fail every push, and the counts are floors, since the batching span processor drops silently when its queue overflows. A positive claim is therefore solid and a negative one is a lead. A dispatch carrying a refusal reason is kept off the lead list, because the server declining to run something is not a handler that could not build a request.
- **Does the document validate.** Every raw GraphQL document in the source against the pinned schema, through `cmd/internal/graphqldocs`, shared with `make check-graphql-documents`. It judges the document and never the values: four of the nine broken tools sent a document the schema refuses and the other five sent an accepted document carrying a value GitLab does not have, and the second half is caught by `internal/testutil`'s validating transport, which checks the variables with the document on every request a test drives. Neither substitutes for the other.

  **The other half of the GraphQL surface is judged here too** (`sdk_graphql`). client-go builds 42 documents inside its own module, for the achievement, work item, saved view, security attribute, security category, scan profile, target branch rule and Terraform state services, and every one of them reaches GitLab through this server while being judged by nothing but whichever of them a unit test happens to drive. `graphqldocs.SDKDocuments` reads them out of the module directory `structs.CollectOutputPairings` already resolves, which needs no GitLab and no network, only `GOWORK=off` and `-mod=readonly` (client-go ships a `go.work` naming a directory its module zip does not carry, and a module cache is read-only). Six of the 42 are written with holes in them: the work item get, create, update and list documents are `text/template` shells and the Terraform state queries are printf format strings, so what the type checker folds carries a placeholder where a value belongs. The collector renders a shell wherever the call that fills it settles the text (`graphqldocs.Assembly`): a format string through `fmt.Sprintf` with each constant argument's own value and a stand-in of its type for the rest, a template by executing it inside the set cloned from its package variables, provided nothing it reaches reads data. `TestSDKDocuments_TheShellsItRenders_AreWhatClientGoSends` holds each rendering byte for byte to what client-go posts. Five are rendered and judged as that rendering (`rendered_documents`); the work item list stays a shell, since its fragment is parsed inside a function from the fields a caller asks for and its variables are the filters a caller sets, and it is counted apart rather than refused, under the reason the walk records (its template set is built when a function runs), because a refusal list with permanent entries in it is a list a reader learns to skip. The pinned schema accepts all 41 judged. It **reports and never gates**, for a reason unlike the usual one: the pin is what GitLab serves, so a refusal there is real, but the answer is an upstream merge request and a version bump rather than an edit here, and that is not a state to fail a build on.
- **Does the endpoint exist.** `-check-endpoints` compares every recorded REST endpoint with GitLab's own API documentation and **fails on one no declaration accounts for**. What makes that safe is `declaredUndocumentedEndpoints` in `cmd/audit_1to1/internal/paths/endpoint_declarations.go`, where each shape the oracle cannot express carries a category and a reason: a deprecated-but-working alias (`/services/` for the integrations endpoints, `/-/search` for the scoped search, `bridges` for `trigger_jobs`), an endpoint documented under `doc/user` rather than `doc/api` (the generic package registry, Terraform state), one whose only mention is a sentence (`/usage_data/track_events`), a method the documentation never spells (`HEAD` on a raw file), and a path client-go builds wrongly (`//sidekiq/*`). A declaration that stops matching anything is a finding too. The page listing comes from the repository tree rather than `api_resources.md`, because many pages under `doc/api` are not linked from that index or from `rest/_index.md` (101 of 253 when the listing moved to the tree), and against the index alone the comparison would report roughly five times as many as against all 246 readable pages (81 undocumented of 1399 recorded today, every one of them declared); the report counts the pages it could not read, since a hole in the corpus produces findings that are only about the hole.
- **Does GitLab say it sends what we publish.** The one check here whose oracle is GitLab itself: `docs/development/gitlab-api-live.json` (`cmd/gen_api_live`, taken from a booted GitLab). It **reports and never gates**, and it asks the question at two grains, both published so a reader can see which findings the sharper one keeps. One record answers both halves of it, what an endpoint sends and what gates each field, which is why a finding can always say when GitLab sends the field it names.

  **Package grain** (`shapes.unpublished`) joins the inventory: a package's recorded endpoints are unioned and every top-level `*Output` type of that package is held against the union. Three deliberate concessions each lose findings so that none is invented: the inventory names a package and never an action, so the union is exact for a package with one endpoint and weaker as the package grows; a route the record names no response entity for, 709 of the 2192 at 19.5.0, silences its package rather than condemning it; and a nested output type is skipped here, being comparable only against the object it sits under, which the type grain does and this grain cannot. It finds 713 fields across 133 packages (`unpublished_fields`), and most of them are not phantoms: our own wrappers around a JSON array (`ListOutput.users`, `SSHKeyListOutput.keys`), our own answers to a 204 and to a not-found (`DeleteOutput.deleted`, `userNotFoundOutput.identifier`), and an endpoint the document gives no schema for sitting in a package where another endpoint has one (`files.Output`, whose 12 fields are reported because `files` calls 32 endpoints and one of them declares a response). The join itself is published beside the findings (`shapes.join`: 1031 of 1600 REST rows exact, 489 after accepting one untemplated fixture segment, 80 unmatched) because a package whose rows all miss would otherwise have its whole output condemned by a lookup failure, and the untemplated segments go with it, which measures this repository's own recording rather than the server.

  **Type grain** (`shapes.typed`) asks only about the endpoints a type actually models, along a chain that consults the inventory nowhere: a converter pairs an output type with a client-go struct (`structs.CollectOutputPairings`, the pairing the R-OUTPUT field diff runs over in the tool packages; the diff also reads the converters of `internal/toolutil`), client-go's service methods say which endpoints answer with that struct (`readSDKRoutes`, cut from `cmd/internal/sdkroutes`, which parses the `route()` templates and `withMethod` options out of the SDK source the handlers compile against and follows a method into the helpers it delegates to with the constants it hands them, so the award emoji routes keep the collection their caller names and the custom attribute routes are reached at all), and the document says what those endpoints send. **What decides whether a type is judged here is the envelope it sits in, not whether some struct names it as a field.** This grain used to pass over every type named as a tagged field, and that rule selected exactly the types that model the responses: the convention here is a one-key envelope, so `badges.GetProjectOutput` is `{badge: BadgeItem}`, the envelope carries no pairing and was counted a skip, and `BadgeItem` (which a converter pairs with `gl.ProjectBadge`, whose service methods name the endpoints) was passed over for being named as its field. No finding about that endpoint's response could be made here at all. The rule now distinguishes the two shapes that used to look alike, in `envelopePayload`: a struct carrying one object and nothing else beside it (a list's pagination aside, which is this server's framing rather than GitLab's) is packaging, and its payload is judged against the endpoint; a struct carrying other content of its own names a **reference**, and that reference stays out. Both halves matter, and the second is the one whose absence bites harder: `jobs.ProjectObject` is a project reference inside a job, and judging it against the endpoints that answer with a whole project reported all 85 fields of one as missing from it. Together with the compact projections below, the rules take the comparison from 26 types to **252** (`summary.typed_types_compared`, of which `shapes.typed.compared_inner` are reached through an envelope) and the sent list from 63 fields to 2080 (`typed_unsurfaced_fields`), 1611 of them unconditional (`typed_unsurfaced_sent_always`), across 59 types. One level down the same list is `shapes.typed.nested_unsurfaced`: a key the object under a property sends that the nested type there does not publish, read on the entity rendering that object and marked with whether client-go's struct under the same key carries it. It reports 1085 on the pinned record, 642 of them not modeled by client-go either, and none is declared yet; a declaration answers one only when it names the property in `Under`. That list is also the honest one: the package grain reports 45 user fields against `health`, whose only claim on the user entity is the `/user` call that checks a token, and declares every one of them, 44 as a read for the package's own use and `custom_attributes` as an entity option no endpoint passes, while this grain reports none. The three skip counters now name the types behind them (`shapes.typed.skipped`), because a figure alone says how much was declined and nothing about whether declining was right, which is the only question a reader has: the 401 that no converter paired were described as wrappers on the strength of the counter alone, and 256 of them were plain `*Output` types. With every envelope now judged through its payload the counter (`typed_types_without_pairing`) reads 125, and each of them is a plain `*Output` type or an envelope around another tools package's row, which that package judges; `orbit.DSLOutput` left it for the Orbit record (below). A type's published fields are what encoding/json would write, an untagged embed's promoted into it, and a type is nested when any struct of its package names it as a tagged field's type, output type or not; an embed names nothing nested, since its fields are promoted rather than placed under a key, and the embedded type stays a response of its own. The shapes `internal/toolutil` shares are read once and resolved wherever a package names, embeds or aliases one, the hints type aside; an alias is nested when the shape is named under either name or by another shared shape, unless an exported function of the package returns it. An alias of another tools package's type (`type Output = labeldata.Output`, which is how the project and group labels and iterations publish their responses) resolves the same way, and at package grain a package is credited with the fields of the types its responses name one level down, so a shared row such as `diffs: []toolutil.DiffOutput` counts as the package's the way a row it declares does; without either, those five packages read as publishing no field of the entity every route of theirs answers with. A row another tools package declares, named by a field of one of the package's types (`commits: []commits.Output`), is credited in that direction as well, as a borrowed type the type grain and the unpublished direction pass over, since its own package judges it; without it a merge request's commits and pipelines, a runner's jobs, a repository's commits and a package's release link reported 55 fields they publish as missing. A type a handler returns whole, with no field naming it, is not borrowed, because the guided creation flows return four domains' outputs as they are and would be held to every answer those domains give. The first reading of this walk held a details type to be missing every field of the row type it embeds, held the user under the row of a list of uploads to the endpoints answering with a whole user, and saw nothing of a package whose only user object is the shared one. Each of those silences is counted rather than judged, and an empty response list means the document does not say rather than that GitLab sends nothing. Since schema version 2 of the record it asks the same question one level down, holding a nested output type against the properties the document gives the response property it sits under, and only where the document describes an object there: 294 nested types compared (`typed_nested_types_compared`). It compared 44 until the walk recorded what a payload nests: the payload of an envelope is named by the envelope, so it is inner, and the walk left the nested types of every inner type out, which kept 184 of the 252 compared types, the merge request a list wraps among them, from ever being held one level down. That is how `head_pipeline.name` stayed published on every merge request although `API::Entities::Ci::Pipeline` sends no name. The package grain still reads one level down from a top-level type and no further, since it joins on names alone and a name two levels down answered nine of its findings about objects the package never publishes. The 25 fields the level first found in `issuelinks` and `pipelinetriggers` left those outputs, and the 111 it reports on the pinned record (`typed_nested_unpublished_fields`) are open: no declaration answers them, so `summary.typed_undeclared_fields` reads 111, all of them at this level. At the top level it reads 0: the 88 the wider comparison first opened were removed from the outputs that published them without GitLab sending them (issue 964) or answered in the declaration table below where the record is incomplete (issue 965), and each of the 65 `typed_unpublished_fields` left carries a declaration. Four more were keys the context commit list sends and its annotation did not name, until the record was taken from 19.5.0, which annotates `GET .../context_commits` with the `CommitWithLink` it presents (upstream-bugs row 77, issue 1025); the six keys of that entity the row does not publish are answered in the sent table instead. Twenty are the approval state every Enterprise build answers the approvals GET with through an override of the presenting helper the route's annotation does not name, which `mrapprovals.ConfigOutput` publishes with its presence (upstream-bugs row 24). The two discussion packages and the shared note shape were on this list until the notes review read the note and discussion entities: the four fields the shape published that GitLab's note does not carry are gone, and the four it lacked are read from the captured response (ADR-0021). A finding at this grain can be answered rather than fixed, because the oracle is generated and is not always complete, so `cmd/audit_1to1/internal/paths/shape_declarations.go` records such an answer with a category and its evidence, and a declaration that matches nothing is itself reported stale. The confirmed phantom of [issue 580](https://github.com/jmrplens/gitlab-mcp-server/issues/580) is the case it was built against, and is the fixture that proves it: `mrapprovals.ConfigOutput` as it stood before the fix produces exactly the twenty findings the fix removed. It also shows where the record stops: the same twenty keys are what every Enterprise build answers the route with, through an override of the presenting helper the route's annotation does not reflect, so its current shape publishes them with their presence and answers each finding with a declaration naming that override (upstream-bugs row 24).

  **A compact projection is paired too, and judged per endpoint.** A converter is not the only way an output type is filled: a milestone's issue rows, a resource group's job queue and the group's project list are built in a composite literal inside the handler, or in a helper it calls, each field read off the client-go struct the handler ranged over, and nothing paired them, so their gaps reached only the package grain. `structs.CollectProjections` reads those literals from the same typed load: the struct most of the literal's fields are read off (the receiver of the outermost field selection, so `mr.Author.Username` is read off the author) and the service methods answering with it that the function holding the literal references, or the package's functions calling it, up to three calls up. The type is then judged against the endpoints of those methods alone, cut per method from the same reader by `readSDKMethodRoutes`, because a compact row comes from one endpoint and a finding about it has to name that one; a type a converter pairs keeps its converter's endpoints, and the field diff does not read these pairings at all. They are listed in `shapes.typed.projections` (`typed_types_compared_through_projection`). The wrapper around a paired payload, a one-key envelope or a struct that publishes nothing of its own and embeds its payload (`GetOutput{HintableOutput; PlanLimitItem}`), is judged under the payload's name and, once every payload was compared, listed in `shapes.typed.envelopes` (`typed_envelopes_judged_through_payload`) instead of being counted among the types without a pairing, which read as a response nobody judged while its payload was judged a line below. A payload that is paired and still skipped, for want of a route or of a response schema, takes its envelope into the same skip, since the response was judged no more than the payload was.

  **A search answer is held to the entity its scope selects.** GitLab annotates `GET /search` and the group and project search routes with no response entity, since `SCOPE_ENTITY[params[:scope]]` in `lib/api/search.rb` picks one per request, so every type built from a search answer was skipped for a record that gives no schema, which is how the code search row came to drop the blob id GitLab sends and the wiki search to publish a page nothing sends (issue 1393). A client-go search method sends one scope, so `cmd/audit_1to1/internal/paths/scope_entities.go` names the entity for each of the 25 (`scopedEntities`), the route reader carries it on every route the method reaches, and the type grain answers such a route with that entity where the record names none and with the record's own where it names one. A key both kinds of route carry is credited to the entity the record names, since the declaration is ours and search routes sort ahead of most others. The record mounts the scoped routes under an optional group (`/projects/:id/(-/)search`), which the operation index now indexes under each spelling; that also lets the recorded `POST /projects/:id/trigger/pipeline` meet the route the record mounts as `/projects/:id/(ref/:ref/)trigger/pipeline`, which took 19 fields of the trigger's pipeline off the package grain's unpublished list and gave the always-sent check its two required trigger params. A method whose answer client-go decodes into a struct GitLab does not send (the wiki scope, decoded into a wiki page, upstream-bugs row 130) is marked so its routes are not credited to that struct, and the type read off the captured response instead is paired with its methods in `capturedPairings` and listed in `shapes.typed.captured`. Both tables are held to the tree like every declaration table: a method client-go has no route for, an entity the record lacks, a route the record does not mount, now annotates or that takes no scope, and a captured type the package no longer publishes are reported in `shapes.typed.unused_scope_declarations` and through the stale list. The five search row types the record gave no schema for are compared now (the code, note, snippet and user rows through their projections and the wiki row through its capture), their five envelopes are judged through them, and every key they leave out is declared: the blob's `group_id`, which only the wiki scope's class carries, the user presenter options no search route passes, and the rest as compact rows naming the action that returns the whole object. The note row publishes `internal` and marks it in its table, since the row quotes the note.

  **Each sent finding says which of two backlogs it belongs to.** Every rule here compares this server with something: the field diff holds our type against client-go's struct, and the join above holds our type against what GitLab sends. Between them nothing ever holds **client-go** against GitLab, which is the question that decides where a fix goes. It is asked now, from the same pairing, by carrying the SDK struct's own json names (`structs.OutputPairing.SDKFields`, flattened exactly as the field diff flattens them) and marking each finding `sdk_models`. False means client-go does not model the field either, so surfacing it is an upstream contribution or a captured response (ADR-0021) and the finding is evidence for the merge request; true means the SDK already carries it and only this server does not, which is a local edit. Measured on the pinned record (19.5.0): of 2079 sent fields, **1404** are absent from client-go too, and 995 of those are two Geo structs (`GeoSite` 603, `GeoSiteStatus` 392) whose fields GitLab generates per replicable resource and which therefore appear in no source a scanner or a hand-written struct could have read; all 995 are declared. The 675 client-go does model came mostly with the compact projections, whose rows leave most of an entity to the detail action on purpose: 404 are declared that way, 141 as published by another type and 49 as the part of a write's answer its confirmation leaves to the detail action. Another 49 are the group routes held against the group an approval rule names, since `approver_groups` wraps it in a one-key object, and are declared as routes no handler of that package calls. None of the 2079 is answered by no declaration: issue 971 took the last 153, in 19 types, to 0, surfacing what a caller needs (a share's `shared_with_groups`, the job token allowlist's whole basic project, a package file's pipelines, a failed import's relations) and declaring the rest one key at a time, and the re-pin on 19.5.0 (issue 1023) answered the 41 that release opened the same way: the keys 19.5 added that client-go does not model are read from the captured response (a group's two SHA settings and its Duo review decisions flag, a project's, a service account's `external`, an SSH certificate's `fingerprint`, a runner's `token_expires_at`), and the rest are declared. The package grain reaches 0 undeclared as well (`unsurfaced_fields` equals `unsurfaced_declared`): the reads a package makes only to probe or resolve an object are declared as such, and the application settings, which `settings` publishes whole as a map, by one entry. The run on 19.5.0 found 349 there first, all of them such reads no declaration named yet (the project `terraformstates` and `repositorysubmodules` read for its path, the to-do items a transfer reads for a failure, the failed jobs a pipeline wait lists in its error) and a release link a `dynamic` test creates through the release link package, and each is declared now. `summary.typed_unsurfaced_not_in_sdk` is the counter; a route whose `desc` annotation names the wrong entity inflates it, which is what the declaration table is for.

  **The Orbit output types are held to a recording instead** (`shapes.orbit`). No self-managed GitLab serves Orbit, so the live record carries its routes with no response entity, and GitLab's generated reference gives them no response schema; the type grain skipped all six outputs. `docs/development/orbit-responses.json` (`cmd/gen_orbit_record`, described under [Recording the answers](orbit-fixtures.md#recording-the-answers-make-gen-orbit-record) in the Orbit fixtures page) names for each recorded call the output type its handler returned, so the join infers nothing: the calls of one type are unioned and the type is walked field by field to every depth, both directions asked, and a third question the other records cannot answer, since this one keeps the JSON kind of every value, asked in two halves: whether the client-go struct a converter fills the output type from decodes each recorded kind at the key it declares, which is what fails a handler at run time, and whether the output type carries each kind to the caller as it came, a `null` only as a null or as the key left out (behind a pointer, as a nil slice or map, in an interface, or in a scalar tagged `omitempty`). The converter between the two is read by neither, and the question is of kinds, never of values. A field published as `any` passes through whatever is below it and is not judged there, a subtree the record kept verbatim shields what a type models inside it while a body kept whole shields nothing of its carrier, a finding is reported at the top of what is missing, and a bare array answer is compared with the one field of the type that wraps it. Against the recording of 2026-10-29 (Orbit 0.163.0, `jmrp-oss/orbit-fixtures`, schema version 4, ten calls with `orbit.graph_status` listed unrecorded) it compares 5 output types and 8 nested ones and finds 9 fields GitLab does not send at the place they are published, 3 keys it sends unpublished and 1 kind the published type does not carry, all 13 declared, with only `QueryOutput` keeping a client-go decoder (`OrbitQueryResult`) since the status, schema, tools and query language are read from GraphQL and the Orbit MCP endpoint after GitLab.com removed their REST routes; the declarations live in `cmd/audit_1to1/internal/paths/orbit_declarations.go`, a table keyed by the path under the output, under three categories: a value this server derives from what GitLab sends (the schema's grouped `domains`, its edge `variants` read from `source { name }` and `target { name }`, a node's `domain` read from an object, a tool's `inputSchema` published as `parameters`, `orbit.dsl`'s echoed `response_format`), a key sent only under a condition the recording did not meet (`raw_query_strings`), and a body carried whole (the llm text of the schema and the query language, and the query's `text/plain` llm and gql answers). The five flat status keys client-go's `OrbitStatus.UnmarshalJSON` copied up from `system`, and `system.error`, retired with `GET /orbit/status`, and the JSON query DSL carried as `content` with issue 1414. It reports in its own section with `orbit_*` summary counters (`orbit_kinds_compared`, `orbit_decoder_kinds_compared`, `orbit_mismatched_kinds`, `orbit_decoder_mismatched_kinds`, `orbit_kinds_unjudged` and `orbit_decoder_kinds_unjudged` among them), a kind finding named by its path with one element marker per depth and answered in the same table under a `kind` or `decoder-kind` direction, and gates only through the stale list, a declaration that answers nothing and a recorded type the tree no longer declares; the seven types the type grain skipped are listed in `typed.compared_against_orbit_record` instead of its skip lists.

  **The same question of GraphQL is asked in `cmd/audit_graphql_shapes`, not here** (`make audit-graphql-sent`, written to `plan/graphql-sent.json`). It belongs there because that command already holds the three things the question needs and this one holds none of them: the pinned schema, the document as GitLab receives it, and the Go struct the answer is decoded into, all at the same position of one walk. Folding it in here would mean loading the whole program with `go/packages`, which `audit_1to1` deliberately does not do. What it buys is measured: the eleven GraphQL-only domains (vulnerabilities, securityfindings, securityattributes, securitycategories, the four epic domains, branchrules, cicatalog, customemoji) contribute **zero** findings to everything above, because their output types pair with no client-go struct and GitLab's REST record says nothing about them, so the sent question was never asked of them at all. Asked now, across the 45 document-and-decoder pairings, it reports **1437 fields the schema offers that no document of their package selects** on the 19.6.0-pre pin, every one of them answered by one of 149 declarations (225 of the rows are the tier probe's membership document in `internal/gitlab`, issue 1224, a lookup whose groups reach no caller), and the list was not noise: it named a branch rule that never said who may push, a DAST location's `hostname`, `param` and `requestMethod` (the decoder read the SAST and container-scanning members of that union and not the rest), an epic note's `internal` flag and a note mutation payload's `quickActionsStatus`. All of those are published now (issues 969, 967 and 968), and every row left is declared.

  **The claim is package-wide and is computed that way.** A package sends several documents at one object and they differ on purpose, so a per-document answer is false of the package a reader would act on: `branchrules` expresses a licensing tier as a CE document that omits `codeOwnerApprovalRequired` and an EE document that selects it, and `epicissues` sends a query that reads a work item beside a mutation whose payload can echo little more than an id. Judging each document alone reported the sibling's selections as gaps: 3 of 19 findings in `branchrules` and 8 of 44 in `epicissues` were false that way. The walk therefore records what each document _did_ select **and decode** alongside what it did not, and reports a field only where no document of the package does both; the document a finding names is the witness, not the extent of the claim. Decoding is part of the evidence because the claim being cancelled is that the package surfaces the value: a document that asks GitLab for a field and drops it on the floor surfaces exactly as little as one that never asked, and counting it would repeat this same error one level down, where it is harder to see. A finding is filed against **the package whose struct decodes the object**, which is not the package the call is in wherever a shared wrapper sends the document: every epic note and discussion mutation goes through `toolutil.ExecGraphQLNoteMutation` and is decoded into the domain's own struct, and filing it against the wrapper named a package that publishes nothing and made all 29 of its same-name annotations wrong. That annotation is `same_name_in_package` and is deliberately named as the lead it is rather than as an answer: nothing here pairs a GraphQL type with an output type, so the match is over a package's output types flattened together, and a hit may be the same value under another spelling or a different object's field sharing a name. Spelled `published_as`, it invited a triager to skip the row, and one of the rows it was covering was `vulnerabilities`, which declared `web_url` and filled it nowhere because no document selected `webUrl`. That one is fixed (the documents select `webUrl` and the list card links it), which is what the annotation was renamed for: the row it hid was real.

  **What the question was put to, and what it was not.** The report publishes a coverage breakdown rather than one number: 406 object positions reached, **243 asked about**, 85 skipped for being traversed rather than read, 78 skipped because the pairing had already been asked about that schema type (a later position selecting strictly less is skipped too), and three silences counted so they are visible: an object selection no Go field decodes stops the walk before anything under it (1 today), an object decoded into a map has no fields to judge and no package to file against (and is the one place the mutation-errors gate is not applied), and a type that unmarshals itself is walked no further (0 each today). Beyond the walk entirely: like `check-graphql-documents`, it reads `./internal/...` and so sees only documents this repository's source writes. The report names what that leaves out, read from the request inventory: **37 GraphQL operations in 6 packages** whose documents client-go builds (`achievements` 12, `workitems` 7, `epics` 6, `workitemsavedviews` 6, `projects` 3, `securityscanprofiles` 3), where the document text and the decoder are both inside the SDK's module. R-PATH can see the documents, since `graphqldocs.SDKDocuments` folds them out of the module source and puts them to the pinned schema (`sdk_graphql`), and the decoder half is the `-sdk` run of the same command (`make check-graphql-sdk-shapes`, issue 1022), which loads client-go's program, pairs each send this server reaches with the struct client-go decodes it into and asks the same questions there. Unlike this report it gates: every disagreement and every reached send whose document a caller builds is answered in `cmd/audit_graphql_shapes/sdk_declarations.go`, and every field no document of a client-go service selects in `cmd/audit_graphql_shapes/sdk_declarations_sent.go` (415 sent fields, 30 disagreements and 1 send on client-go 3.30.0 and the 19.6.0-pre pin, the gaps client-go owes each naming upstream-bugs row 27 or 104 to 108), so a bump or a re-pin that moves one fails until the tables say why, except on a type declared whole rather than field by field, whose new fields that declaration already answers.

  **It reports and does not gate**, for a different reason than the REST joins: the pin is exactly what GitLab serves, so the oracle is not incomplete, but a field GitLab offers is a candidate for the surface rather than a defect in it, GitLab adds fields weekly, and this dimension has **no tier oracle and no deprecation oracle**: the schema declares no tier (GitLab gates a GraphQL field at resolve time) and the pin carries no `@deprecated`, because `cmd/internal/graphqlintrospect` drops the directives and descriptions on decode. Both blind spots are stated on the report rather than silently absorbed, and both are closed by one sidecar record written from the introspection fetch that already carries the data. Nine of the eleven domains are Premium or Ultimate surfaces, so most of these findings sit on licensed ground: a `tier` is omitted from a finding rather than emitted empty, since an empty field would read as a condition that was checked and found absent. The one sub-class that **does** gate, and on every run, is a mutation payload whose `errors` **no field of the decoder reads**, which drops GitLab's account of a refused mutation and reports success; the condition is the decoder and not the document, because a payload that selects its errors and decodes none loses them just as completely, while the reverse is already a hard failure of the always-empty leg. A finding is answered by an entry in `cmd/audit_graphql_shapes/sent_declarations.go`, keyed by package, schema type and field, and a stale declaration fails the run on the terms every declaration table here is held to; two of the 149 answer the work item a notes query names only to reach its notes widget, which is 68 rows. The record is deliberately uncommitted and not freshness-gated: a schema re-pin would churn it every time.

- **Does a list say where it ends.** R-PAGE, added because a blind spot was found by accident and every dimension above was green on it: `internal/tools/impersonationtokens` answered `user.list_impersonation_tokens` with a bare array of tokens while GitLab serves twenty at a time, so a caller could not tell it had one page and could not ask for the second. None of the six could see it, because all six compare a **published field** against the SDK struct, the documentation or the entity record, and GitLab's pagination is a field of no entity: an offset page arrives in the `X-Page`, `X-Next-Page`, `X-Per-Page`, `X-Total` and `X-Total-Pages` response headers, and a keyset page in a `Link`. The oracle is the same live record, read through its params for offset pagination and through its `keyset` field for keyset: 322 of its 2192 routes at 19.5.0 declare `per_page`, and the 312 with `page` beside it are offset (`paginated_routes`); GitLab reads `pagination=keyset` without declaring it, so the 53 routes whose code reaches a keyset paginator (`keyset_routes`, 39 of them among the 312) are what schema 5 of the record found by walking each route's code ([gen_api_live](cmd-utilities.md#gen_api_live)). A keyset page is followed by the `next_page_token` of the same block, the next link of GitLab's `Link` header, which `toolutil.PaginationFromResponse` publishes and `toolutil.KeysetContinuation` sends back on every list GitLab pages by keyset (issue 1165). The keyset half (`pagination.keyset`) judges it per action, joining each action to its routes through `docs/development/action-requests.json`: whether `page_token` is offered on a keyset route and only there, whether a list offering it publishes `next_page_token`, and whether a package serving it was ever recorded sending its route the parameter the next page is asked by. 20 actions offer `page_token`, every one of them on a keyset route, publishing `next_page_token` and seen following it; the 182 that offered it where GitLab pages by offset alone lost the keyset input in issue 1165, and the keyset half gates on any such finding no declaration answers. A route the record marks and GitLab serves this server no keyset page it can follow (`GET /groups`, whose keyset branch only a signed-out caller reaches, and the two service account token lists, which GitLab answers 405) is declared under `keyset-not-followable` in `pagination_declarations.go` and held to as offset. An action is judged when its output is a **collection envelope** (exactly one content field, a list of objects, with this server's own framing taken out), which is where "the route declares the params but the action reads a single object" is answered structurally rather than one declaration at a time: a project carrying `shared_with_groups` is a single-object read, and admitting those turned 24 findings into 79. Of 265 collection-reading actions (`collection_actions`), 241 publish a pagination block, 16 sit in a package no paginated endpoint was recorded for, and **8 are findings** (`collection_actions_without_pagination`), every one of them declared: the 15 that were not (issue 963) now offer `page` and `per_page` and publish the block GitLab answers with, ten of them through `toolutil.PaginationRequestOption` because their client-go method takes no options struct to carry a page in, and `merge_request.approval_rules` through a `gl.ListOptions` the package's own raw request encodes. `admin.system_hook_list` was the last of those to be found and shows what the join costs when an owner is coarse: it was in the not-asked-about count while its owner was `adminspecs`, which records nothing, and naming `systemhooks` as its owner put it against the one paginated endpoint that package records, `GET /hooks`, which is the endpoint the action itself calls. The join is the package, like the observation check's, and `pagination_endpoint_grain` says so beside the number; the 8 findings that matched a sibling's endpoint are declared in `cmd/audit_1to1/internal/paths/pagination_declarations.go` with the route the record holds for each (`GET /runners/:id/managers` declares neither param and its handler presents the managers without `paginate`; `GET /projects/:id/languages` answers with an object rather than an array; `project.target_branch_rule_list` is read over GraphQL and has no REST route at all), and there is deliberately no category for "GitLab pages this and we have decided not to": that is the finding. What the params cannot say is what the handler does: GitLab's paginator reads `page` and `per_page` from every parameter a request carries, so a handler ending in `paginate(...)` pages a route that declares neither, and four declarations stood on that misreading until issue 1024 (an issue's participants, a merge request's participants, reviewers and pipelines), with a fifth list, a merge request's context commits, never asked about at all; reading the not-asked-about lists against their handlers found a sixth, `attestation.list`, and the same class over GraphQL, `admin.terraform_state_list`, which read a connection GitLab caps at 100 nodes through client-go's document, with no `first`, `after` or `pageInfo`, and now sends a document of its own that takes `first` and `after` and publishes the connection's `count` and the forward half of `pageInfo` (issue 1341; upstream-bugs row 104 records the client-go half). A declaration in the `endpoint-declares-no-page` category has to cite the handler's body as well as the record; that is its author's obligation, since nothing in R-PAGE reads GitLab's source. The collection half **reports and does not gate**: a finding is a surface change, and `request_paginates` on each says whether the fix is one output field or an input that has to offer `page` and `per_page` first. The keyset half **gates** on the findings no route declaration answers (`keyset_findings_undeclared`), and R-INPUT leaves the two keyset fields of `gl.ListOptions` to it rather than answering them input by input. Its two declaration tables, the unpaginated collections and the keyset routes, gate like every other one here.

- **Is a param sent that the caller never asked to send.** The first of the two checks that read values, and the reason both exist: the recorder writes down that a body carried `package_name_pattern` and nothing about what was in it, so a field this server sends as `null` on every call reads exactly like one a caller filled in. client-go's option structs say which keys the request's encoder writes whatever the handler set, read transitively through every nested client-go struct and named the way Grape declares a nested param, `position[position_type]`: `encoding/json` for the body `NewRequest` builds for a PATCH, POST or PUT (no `omitempty` and no `omitzero`), and go-querystring, which reads the `url` tag and writes `name=` for a nil pointer without `omitempty`, for the query of every other verb and for every field of an `UploadRequest`. The live record says which params GitLab marks optional on the route receiving them. A key written unconditionally whose param GitLab **requires** is correct; one whose param GitLab lets a caller **leave out** is a value nobody can decline to send. A package is held to the option structs of the client-go methods its handlers call, read from `docs/development/action-requests.json`, so a route two methods reach with different structs charges each package with its own (issue 1104, which took the two `POST /groups/:id/share` rows charged to packages that send the omitempty options of `Groups.ShareGroupWithGroup`); an endpoint the record names no such method for, a body a handler builds by hand or a package whose tests drive other packages' handlers, is judged against every struct its route accepts and listed in `always_sent.not_narrowed_to_the_package` (116 endpoints). On the pinned record that separates **11 findings from 52 always-sent fields GitLab requires** (and 12 whose route does not declare them at all), over 453 option types and 614 recorded endpoints, with no declaration table doing any of the work, and the 11 include the case it was built against: `package.protection_rule_update` sends `"package_name_pattern": null` on a PATCH where GitLab marks it optional, while the POST beside it requires the same field and is right to send it always. The rule used to read the `json` tag for every body verb, DELETE included, and to pass over a GET on the premise that a query leaves a nil pointer out whatever the tag says; reading each request by its encoder added no finding, since every key a query writes on every call is one GitLab requires or one the route does not declare. Two blind spots are stated rather than absorbed: a field whose type is a plain struct carrying `omitempty` is still written on every call, because under v1 semantics a struct is never empty (client-go has none today, since its nullable values are `Nullable[T]`, a map, which `omitempty` does omit); and a request option that edits the body client-go wrote is not read, which is why the release update's title and notes, which `releases.Update` drops when the caller left them out, are two of the 11. It **reports and does not gate**: the tag belongs to client-go, so almost every fix is an upstream merge request, and whether GitLab minds a null in a given position is per endpoint.
- **Was the path ever built out of anything but the fixture.** The other value check, and the one paid for in the recorder. Templating `/projects/1/issues` into `/projects/:project_id/issues` is what makes a row an endpoint, and it is also what hides a hard-coded identifier: with one fixture value a handler that reads the caller's project and one with the fixture's id written into it produce the same row, which is why the class had to be found by hand in `runnercontrollers`, `snippetdiscussions`, `repository`, `runnercontrollerscopes` and `securityscanprofiles`. The recorder now counts, per row and per placeholder, how many distinct raw values it templated away (a running count, written as a new line whenever it rises, since the recorder has no shutdown hook; the merge takes the highest), and this reads it back: a placeholder seen with exactly one value is a **lead**, never a verdict, because a fixture that makes one project and drives forty endpoints against it produces forty innocent ones. The leads are printed sharpest first (a row where another placeholder did vary) and capped at 50, with the true count beside them. It **reports and will keep reporting**: what would make it gateable is fixtures that vary their identifiers wherever they can, which is a change to hundreds of tests rather than to this rule, and there is deliberately no cheap static form, since a lint over numeric literals in test files would fire on every fixture in the tree.

What none of it can do is check that GitLab answers a **specific request** the way our output struct expects: the shape check reads what GitLab's document says an endpoint returns, never what an instance returned for a call we made, Orbit aside, whose recording is exactly that and only for the thirteen calls it makes. The layers stack: the pinned schema and the inventory catch a request that cannot work, a real instance catches a response we misread, and the other five rules keep catching the surface we failed to expose. One more limit is worth knowing because it hid a defect: the inventory records which parameter names an endpoint was sent, never which of them were sent together, so a combination GitLab refuses is invisible here. `gitlab_get_catalog_resource` was in that state (`id` and `full_path` are both optional and GitLab accepts exactly one), and the answer to that class is a handler that refuses the combination and a schema that says so, not an inventory of every combination the fixtures happen to use.

**None of that machinery may reach the server binary.** `internal/graphqlschema` embeds the pinned schema, close to a megabyte of SDL text, for two readers, the test transport and the audit, and neither runs in the server; `internal/testutil` carries it plus `net/http/httptest`. Both stay out today only because nothing in the import graph happens to reach them, and `TestDependencies_TestSupport_NeverReachesTheServerBinary` in `cmd/server/main_test.go` makes that hold on purpose by asking the toolchain for `go list -deps`, since an indirect import through any of the 250 packages in between is exactly what a source scan would miss.

## Fine-grained grants (R-GRANT)

The seventh dimension asks of every action what a fine-grained personal access token has to be granted for it to work, in GitLab's own words, and which actions no grant can make work at all (issue 952, [ADR-0024](adr/adr-0024-fine-grained-token-authority-per-action.md)). It is the one dimension whose answer the server **enforces**: the table it holds to GitLab is the one the binary compiles in and judges every fine-grained session by. Three facts with three owners are kept apart and joined by a generator. **What each action requests** is this repository's: `cmd/gen_action_grants` loads the program, resolves each action's handlers through `cmd/internal/actionrequests` and what each client-go method sends through `cmd/internal/sdkroutes`, reads the statements as sequences, alternatives and optional requests, and writes `docs/development/action-requests.json`, so a handler change shows as a reviewable diff. **What GitLab demands of each route and GraphQL element** is GitLab's, recorded from a booted 19.5.0 into schema 5 of `docs/development/gitlab-api-live.json` (`cmd/gen_api_live`). **How an action's requests combine** is the handler author's, declared at the call site with `//gitlab:request mandatory|optional|alternatives: <reason>` where the syntax reads it wrongly, or in `request_declarations.go` where the walk cannot reach (the client-go work item list, whose template is filled from what the handler asks for, a `fmt.Sprintf` path, the redirect GitLab answers a permalink with, a request a function of ours sends through an HTTP client of its own rather than client-go, such as the read of the instance version that the auto-merge cancel branches on). The join is `internal/tools/actiongrants/table_gen.go` (keyed literals of constants, so the server runs no code to build it) and the generated [fine-grained permissions reference](https://docs.jmrp.io/gitlab-mcp-server/reference/fine-grained-permissions/). A REST requirement is GitLab's route declaration, primary and additional scopes; a GraphQL one is judged along the **answer spine**, the objects from the root field down to the first that selects more than one field, because a wrong "yes" on GraphQL is silent (a null, an emptied connection) where on REST it is GitLab's own 403: an undeclared type on the spine, an undeclared mutation, a payload type that declares nothing (the write commits and answers null) and an object that never resolves to its declared boundary each make the action denied, a non-null chain carries a denial onto the spine, an abstract position is judged as its worst member, and anything denied off the spine is a part served empty. A request the action sends on some calls only (the derivation's `optional` class: a fallback, a lookup its input or an earlier answer calls for) is held beside the ways rather than on one, as `Optional` and `OptionalDenied` on the row, worded as `optional_needs` in the detail and as **Some calls also need** on the reference page (issue 1242). What the walk or the record cannot answer is declared with a category and a reason (`grant_declarations.go`: the raw file `HEAD` the probes measured and the integration routes named by a slug; the epic positions GitLab declared at the project boundary only left it when the record was taken from 19.5.0, which declares `WorkItem` at the group boundary too), and a declaration that answers nothing is a finding. Three gates sit in `make analyze`: step 26, `make check-action-grants-derivation` (every action derived or declared, a second mandatory request on a path qualified, every denial, an optional request's included, naming an element the record holds, a mandatory request on every way that sends anything, one classic scope across an action's ways and optional requests, and every action whose read or write classification departs from what `read_api` reaches declared; never deferred, since it derives from the tree); step 27, `make check-action-grants` (the three artifacts fresh, under the `FRESHNESS` deferral like every committed artifact); and step 28, `make audit-1to1-grants` (`go run ./cmd/audit_1to1/ -scope=grants -gaps-only`, which loads no program and holds the committed table to the live record and the catalog: the release, the vocabulary, the public sets, every denial's element, every REST operation's route declaration, every operation's and row's classic scope against its kind, its route's skip reason, its ways and the request record, and one row per action of both Ultimate builds with the standalone actions). `make audit-1to1-grants-report` writes the rest to `plan/1to1-grants.json` and gates nothing: per action the permissions and the directive or declaration that shaped them, the phase A set by cause (55 of 1103 actions at 19.5.0, all through GraphQL), the parts served empty, the REST operations a public project or group serves with nothing granted, the worklist of upstream register row 87, the 21 GraphQL types and mutations GitLab declares nothing for at 19.5.0 with their REST leads (`graphql_worklist_elements`), and the derivation held to the request inventory and, with `-e2e-calls`, to the route of every client span a Docker run's traces reached, which is the one per-action oracle for a request the derivation missed. A change to a `finegrained` type regenerates the table in the same change: the generator builds itself and loads the program with `table_gen.go` replaced by `table_stub.go.txt` through `-overlay`, so a table a type change broke cannot stop its own regeneration.

## Route params (R-PARAM)

The dimension that asks, of every route this server reaches, whether anything here can send each param GitLab declares on it (`-scope=params`, `cmd/audit_1to1/internal/params`). R-INPUT compares an input with the client-go struct it fills and R-PATH compares what was sent with what GitLab answers, so a param client-go's option struct does not model was seen by neither: client-go cannot send it, so no input offers it, so no recorded request carries it. The params [row 133](upstream-bugs.md#seven-response-keys-and-twelve-parameters-gitlab-195-added-that-client-go-does-not-model) of the upstream register lists came from a review of the diff between two records that no gate read.

**How a param is judged.** Per route, over the union of every action the request record says reaches it, a route whose derived spelling leaves a segment to the input (an integration's slug) reaching every route that spelling meets. A param is covered when a recorded request of the route carries it (`docs/development/request-inventory.json`), or when a request sends it on every call (the file field of a method that always uploads). The inventory names every part of a multipart form, so an upload's options are recorded as they are spelled (`override_params[visibility]`), and the top-level keys of a JSON body and not what was nested in them, so a recorded key covers a param nested under it only where an option struct the route's requests carry models that param: `approval_rules` is recorded on `POST /projects/:id/protected_environments`, and its `approval_rules[id]` is still `unmodeled`, because `EnvironmentApprovalRuleOptions` has no field to write it. A param that is not covered is a finding of one of four classes:

- `unmodeled`: no option struct the route's requests carry models it and no input offers it. The fix starts in client-go.
- `not_offered`: an option struct the action already hands client-go models it and no input offers it. An input can offer it today.
- `offered_unrecorded`: an input offers it and no recorded request carries it, a hint of a handler that drops it or of a test that never sends it.
- `unjudged`: no input offers it, on a route one of whose requests carries options the walk cannot read: a free map, a struct of the tool package's own that embeds no client-go struct, a method client-go does not declare, or a request through no site. The redirect GitLab answers another route with (`follows-redirect` in the request record, as `release.get_latest` reaches `GET /projects/:id/releases/:tag_name`) carries no options of the action's, so it leaves its route's params judged.

What an option struct carries is read by `cmd/audit_1to1/internal/sdkoptions`, the reader the always-sent check shares, walked into every client-go struct a field carries (`[]*HookCustomHeader` is `custom_headers[key]`), through a type defined on an option struct (`CreateProjectForUserOptions`), with the encoder the request's constructor uses (`json` for a `NewRequest` PATCH, POST or PUT, `url` for every other verb and for every field of an `UploadRequest`), and with the form field an upload sends its file under (`avatar`, `file`). A raw request is read through the static type of its options, as the sdk scope's walk of the tool packages records it (`sdk.RawRequests`): a client-go struct, a struct of the package's own that embeds one with the keys it carries beside it, and for a function that forwards its options (`projects.doProjectRequest`) the call of it the action's handler makes. An input offers a param by name, under the field an alias of the requiredness scope names, flattened the way the negated filters are spelled (`not[author_id]` as `not_author_id`), or through the nested schema of the field it sits under. A path param and an attribute Workhorse fills for an uploaded file (`file.sha256`) are not judged, a container is covered when one of its members is, and a container none of whose members is covered stands for them as one finding when they share its class.

**What gates.** The findings are a report: almost every `unmodeled` one is a client-go merge request, and GitLab adds params every week. The scope fails on a declaration in `declarations.go` that answers nothing, names no known category or no reason, or, for an `upstream` one, names a row the register does not hold. An `upstream` declaration answers an `unmodeled` param alone, so it goes stale the day client-go models the param; a `map-input` one answers a param a map input can carry (an option struct the map is decoded into models it, or the map is sent as it is), never one nothing can send. The other categories are `declared-not-applied` (GitLab declares the param and drops it, as a project create drops four `duo_*` flags, a deployment's merge request list three presenter flags, four project lists the two checksum filters, and an import's tree restorer the 34 `override_params` keys `import_export.yml` does not permit for a project and fails on the two it permits and cannot assign, `topics` and `jobs_enabled`), `webhook-payload` (the GitHub pull request payload `POST /projects/:id/mirror/pull` declares) and `branch-not-taken` (a route client-go sends only for an argument the handler never passes, as the four label collection routes). A `declared-not-applied` or `webhook-payload` declaration answers a param no input offers, so an input that starts offering a key GitLab drops is a finding again rather than an offer the declaration hides, while a `branch-not-taken` one answers any class, since what its route's input offers goes to the route the method takes instead. The scope reads the committed request record, so in CI it runs beside R-GRANT under the `FRESHNESS` rule (`make audit-1to1-params`) and in `make analyze` as step 30; `make audit-1to1-params-report` writes the whole report to `plan/1to1-params.json`.

On the pinned record (19.5.0) and client-go v3.30.0 it judges 5791 params of 1101 routes and covers 2864. The counters of the summary count findings, and a container that stands for its members is one finding: 773 `unmodeled` findings on 168 routes (893 params), no `not_offered` one, 496 `offered_unrecorded` on 92 (510) and 3 `unjudged`, beside 1491 declared (1510 params, 1371 findings by the map inputs of the settings update and of every integration). The scope first reported 71 `not_offered` findings on 9 routes, and each is answered: the avatar of seven create and edit actions and 39 of the 61 `override_params` keys of the file import are offered now, and the other 22 keys and three list flags of a deployment's merge requests are declared `declared-not-applied`, which `TestRun_Repository_OffersOrDeclaresTheParamsNoInputOfferedOnV3300` pins. So are `repository_checksum_failed` and `wiki_checksum_failed` on the four project lists that declare them, which no input offers since GitLab reads neither, and `TestRun_Repository_DeclaresTheChecksumFiltersNoProjectListReads` pins them. Those figures are on the committed request inventory, so what was offered since it was last generated counts as `offered_unrecorded` until it is generated again. Among the `unmodeled` are `source_project_id` and the filters GitLab 19.5 added on the four merge request lists, `url_variables` and `custom_headers` of the system hooks, `url_variables` of the project and group hooks, and the seven lock fields `POST /projects/:id/terraform/state/:name/lock` requires, which client-go's `TerraformStates.Lock` sends none of, so `admin.terraform_state_lock` is refused with `ID is missing` on every call.

## Live routes (R-ROUTE)

The dimension that asks, of every route the live record mounts, whether an action of the catalog sends it, and when none does, why (`-scope=routes`, `cmd/audit_1to1/internal/routes`). R-ACTION and the sdk scope start from client-go and R-PATH from what the unit suite recorded, so a route client-go does not model was seen by none of them: no method to call, so no action, so no request recorded. `GET /pipelines` and the two `placeholder_reassignments` routes of a group were in the 19.5.0 record from the day it was pinned and surfaced only when client-go modeled them.

**How a route is classified.** A route mounted twice is one route (the record mounts 2192, 2137 of them distinct). The request record already spells each route an action sends as the live record does, so the join is exact. In order, the first rule that holds decides:

1. `reached`: an action's request sends it.
2. `outside-api`: it is not mounted under `/api/:version` (the SCIM routes).
3. `skip`: it skips the fine-grained check for a reason `skipReasons` excludes, or a `skipExceptions` row takes it out. The table is closed over the whole record: a reason a route carries that no row holds fails the gate whatever the route's class, a reached or a SCIM route included, and on a route this step reaches it is a finding too (`unknown-skip-reason`); a row no route carries is stale. Each row carries a category and the reason read from the GitLab code that sets it. `public` (`public_endpoint`) and `user-token` (a reason GitLab's code lets a user's token call: `modular_service_token_exchange`, `usage_data_auth`, and the two Duo workflow reasons, whose classes add the `ai_workflows` scope to the `api` scope every API class allows and only authenticate the user) exclude nothing; `other-credential`, `inbound-webhook`, `workhorse`, `removed`, `client-protocol`, `internal-testing` and `catch-all` exclude their routes, except a reason some reached route carries: a credential this server already sends there is one it can send beside it, so `DELETE /runners/managers` and `POST /jobs/request` (`runner_token_auth`) go on to the rules below. That is evaluated on every run. A `skipExceptions` row names a route such a reason leaves in whose handler refuses a user's token all the same, with the category and the reason that handler gives: the three Duo routes that call `verify_flow_composite_identity!`. An exception whose route is reached, carries no reason or a reason that excludes it on its own answers nothing and is stale.
4. A route under `/internal` no skip excludes is a finding: `internal-without-skip` when it carries no skip reason, which every route of the internal API does, and `internal-not-excluded` when its reason excludes nothing.
5. `slug-from-input`: a `slugRules` row names the action whose request derives a spelling that leaves a segment to the input (an integration's slug, `project.integration_set` and `project.integration_set_group`), and the route is one that spelling meets.
6. `deprecated-alias`: a `/services/` route whose `/integrations/` twin of the same verb is reached or answered.
7. `inherited`: every client-go method that sends the route (read through `cmd/internal/sdkroutes` and found in the record by `apilive.RouteIndex`, as a request is) is decided in a way that holds for a route no request sends: `COVERED_GRAPHQL` with the GraphQL actions `graphqlActions` names for the method, each in the catalog and sending GraphQL in the request record, `SUPERSEDED_UPSTREAM` in `acceptedMissingMethods` or the service declarations, `UNWRAPPED_TRACKED`, or a waits entry `url-built`. A `COVERED_GRAPHQL` decision says the domain goes over GraphQL, so the operation is covered only when an action does it: a method that table does not name does not carry, which leaves `POST /projects/:id/vulnerabilities` to a family row, since no action creates a vulnerability. `COVERED_GENERIC` says another route covers the capability, which is the question this scope asks, and does not carry; `COVERED_VARIANT` and `COVERED_RAW` say the route is sent, so on a route no action reaches they are a finding (`contradicted`); a method an action calls whose route this is not, an `INTENTIONAL_SKIP_*` and a method nothing decides do not carry either, and the decisions are kept on the route. A `COVERED_GENERIC` or `INTENTIONAL_SKIP_*` decision on a route a tracked row answers fails the gate (below): the row says an action is still to implement and the decision that the route needs none.
8. `declared`: a `routeFamilies` row answers it. A row names its verbs (every verb when empty), a pattern of the record's path matched against every spelling `apilive.ExpandOptional` gives it (`*` one segment, a last `**` any tail), a category (`client-protocol`, `covered-by-graphql`, whose GraphQL actions it names, or `tracked`, whose issue it names), a reason, and the number of routes it answers, pinned.

Anything else is a finding (`unanswered`), with the client-go methods that send the route: none means the fix starts in client-go or with a raw request ([ADR-0021](adr/adr-0021-captured-response-for-fields-the-sdk-does-not-model.md)). An `/integrations/` finding whose deprecated `/services/` twin an action reaches names it as its `twin`, since the capability is offered through the spelling GitLab deprecates. `GET /projects/:id/integrations` was one, which `project.integration_list` reaches as `GET /projects/:id/services`; on the pinned record a tracked row answers it and names that twin in its reason, since a route a family row answers carries no `twin`.

**How the family rows are decided.** A REST route whose operation an action of the catalog does over GraphQL is `covered-by-graphql`, with that action: the epic routes of the `/-/` spelling and the child epic links, the five work item operations and the attachment and detachment of a child over the REST API GitLab serves behind the `work_item_rest_api` flag, a group's work item's discussions, notes and children, which the `group.epic_*` actions read by the work item's iid whatever its type, a vulnerability's confirmation, dismissal, resolution, revert and read, and a pipeline's findings. The protocol a package manager's or MLflow's own client speaks is `client-protocol`, except a download: a route that serves what a package or a model version holds (one of its files, its archive, its source or a file inside it, such as a Go module's `go.mod`) is `tracked`, so the action that downloads it stays in view, while an index or a metadata document a client reads to find and resolve packages (Debian's `Release` and `Packages` files, Helm's `index.yaml`, RPM's `repodata`, RubyGems' spec indexes and gemspecs) and the URL or the location of the content are the protocol's. Everything else GitLab serves to a caller with a token is `tracked` by the issue of its domain, one per domain, an administrator's, a GitLab.com and a tier's route among them, and so are the fifteen `public_endpoint` routes, which a token reaches as any other. A decision that does not carry stays on the route beside the row that answers it. The seventeen routes whose methods `acceptedMissingMethods` decided `COVERED_GENERIC` (a group's and a project's direct members, a group's subgroups, the delete of an LDAP link by its `cn`, a merge request's changes and the `PUT` of the error tracking settings) or `INTENTIONAL_SKIP_*` (nine downloads, the streamed repository archive and the deprecated write of a merge request's approvals) are tracked rows, and their entries left that table: a route still to implement is no method R-ACTION may settle, so R-ACTION lists those methods as its backlog.

**What gates.** Every finding, of any class: a route no action reaches is answered by a rule, an inherited decision or a family row, so a re-pin that brings one, or an action that stops sending one, fails the gate until the change that causes it decides the route. And every declaration that no longer describes the tree: a family row that answers no route, answers another number of routes than it pins (named with the routes it answers), answers a route another row answers, lacks what its category needs (a tracked row's issue, a covered-by-graphql row's actions, each in the catalog and sending GraphQL in the request record), is `client-protocol` over a route client-go sends, which is R-ACTION's, or is `tracked` over a route whose client-go method `acceptedMissingMethods` decides `COVERED_GENERIC` or `INTENTIONAL_SKIP_*`; a skip row no route carries or whose category the table does not define, and a reason a route carries that no row holds; a skip exception that answers no route, gives no reason or excludes nothing; a `graphqlActions` row that answers no route, names no action, or names one the catalog does not hold or that sends no GraphQL; a slug rule that answers nothing or names an action the catalog does not hold. A re-pin that adds a route under a family changes its count, and an action that starts sending a tracked route leaves its row answering less, so both are decided in the change that causes them. The scope reads the committed request record, so in CI it runs beside R-GRANT under the `FRESHNESS` rule (`make audit-1to1-routes`) and in `make analyze` as step 31; `make audit-1to1-routes-report` writes the whole report to `plan/1to1-routes.json`, the answered routes with what answers them, ordered by family, which is the work list a triage reads.

On the pinned record (19.5.0) and client-go v3.30.0: 1007 routes reached, 20 outside the API, 186 skipped (3 of them by a skip exception), 94 by an integration's slug, 49 deprecated aliases, 48 inherited (28 `SUPERSEDED_UPSTREAM`, the Geo nodes, the three certificate-based cluster services and the five Orbit routes GitLab.com removed in favour of GraphQL and its Orbit MCP endpoint, and 20 `COVERED_GRAPHQL`, the epic, epic note, epic discussion and epic issue routes and a project's vulnerability list) and 733 declared by 331 family rows: 534 `tracked` under 32 domain issues (thirty of the catalog's domains and two it does not hold yet, the virtual registries and GitLab Duo), 150 `client-protocol` and 49 `covered-by-graphql`. No route is a finding, no skip reason is unknown, no internal route is left in, no decision is contradicted and no tracked route is settled by a decision. `TestRun_Repository_AdjudicatesEveryRouteNoActionReaches` pins those counts, the fifteen tracked `public_endpoint` routes, a reason that says a route is public exactly when it is, and the rule that keeps a download out of `client-protocol`: every `client-protocol` route whose summary says download is one the test names with what it serves instead, and every name and protocol root the test holds answers a route; `TestRun_Repository_HoldsTheWorkItemRoutesToTheActionsThatDoTheirOperation` the work item routes by scope, a group's discussions, notes and children covered by the `group.epic_*` actions; `TestRun_Repository_HoldsTheRoutesClientGoLaterModels` the three routes client-go models later as tracked with no client-go method and the reassignment upload's authorization as `skip:workhorse_pre_authorization`; `TestRun_Repository_DeclaresTheRoutesADecisionDoesNotCarryOnto` the seventeen routes whose decisions left `acceptedMissingMethods`, now sent by methods nothing decides, the creation of a vulnerability, the two runner routes, and the integrations list whose reason names its reached twin, each tracked with the decisions that do not carry, and the vulnerability list and the five Orbit routes as inherited; and `TestRun_Repository_HoldsTheDuoWorkflowRoutesToTheTokenThatCallsThem` the three Duo routes the composite identity takes out and the fourteen a user's token calls, which the Duo domain's row tracks. They change with the client-go bump, which is the evidence the scope was run again.
