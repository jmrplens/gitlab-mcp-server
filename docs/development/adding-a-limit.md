# Adding or Changing a Limit

**The procedure for a new limit, or a change to one**: where its row goes in the tenant policy register, what pins its value, which gate holds the layer to it, and what proves the change.

> **Diátaxis type**: How-to · **Audience**: 🛠️ Contributors & maintainers

The register and the invariants it holds every row to are specified in [Tenant Policy](tenant-policy-spec.md); this page is the procedure a change follows.

---

Every decision about who a caller is and what it may hold, spend or be told (a ceiling, a rate, a budget, a lifetime, what zero means for a setting, a refusal with its channel and code) is **decided in the tenant policy register, `internal/tenancy`** ([ADR-0023](adr/adr-0023-tenant-policy-is-declared-once.md)), and enforced where the resource is counted: the register decides and never enforces, and the layer applies the answer it reads there. A limit written as a literal in the layer that enforces it is the shape [issue 565](https://github.com/jmrplens/gitlab-mcp-server/issues/565) retired, because the question that decides the hardest of them, whether a caller can mint another value of the key the limit is counted on, had to be rediscovered by hand every time. The procedure:

1. **Write the row** in the family file of `internal/tenancy` for the question it answers (`decisions_identify.go`, `decisions_admit.go`, `decisions_authorize.go`, `decisions_allow.go`, `decisions_end.go`, or `decisions_request.go` for a bound on one request), and its values in `values.go` (a refusal code in `codes.go`), each with the typedness of the literal the layer would have written. Choose its `Key` from `key.go`; a key that is not there is added there with its mint cost, its unit and its evidence, which amends the specification's key table (`docs/development/tenant-policy-spec.md`).
2. **Pin the value and name the requirement.** The constant gets its pin in the table `TestValues_HoldTheirPins` reads, and the row's ID joins `specRequirementIDs`, which `TestDecisions_EveryRequirementHasOneRow` holds one for one against the register. Both lists started as the decisions and values the code held at `cb6379f53` and are the current pins now, so a new limit adds its lines to them in the same change.
3. **Run `go test ./internal/tenancy`.** `Validate` holds the row to what issues 540 and 561 each had to discover, in the three ways the specification's [invariants](tenant-policy-spec.md#invariants-any-limit-must-satisfy) list rule by rule. Some it refuses with no exception: a share on any key a caller can mint, the tenant included; a charge to anything but a budget before admission; a refusal on a channel its method cannot carry, or with a status, a code (one in the range MCP reserves and does not define, or in the legacy `-32000` range, among them), a `Retry-After` or a challenge the channel forbids; a process partner that is configurable or not keyed on the process, and a reason about the process on a row that does not say it protects one; a valued row that does not say what zero means; a variable without the `GITLAB_MCP_` prefix, or a configurable value with no flag, variable or malformed-value policy. Three pass with a recorded decision: a holding taken across keys; a process partner switched off with the per-key row it stands beside, where the row's `OffWithBy` names the decision and `Decided` records it (`RTC-007` follows `RTC-003`, issue 951); and a zero refused at startup or replaced by the default, the row's own or one of its `SettingZeros`, where `ZeroBy` names the decision the same way (issue 958). `Validate` reads the decision and not its reason, so the row's comment states why that zero does not mean off. A `ZeroBy` on a row whose every zero means off is refused, so the decision leaves with the zero it decided, and so are `SettingZeros` that state one setting's zero twice or leave no setting to the row's own `Zero`. The rest pass only by carrying the finding recorded for the invariant: a per-caller number protecting a process resource with no process partner; an in-band code of the server's own that is not the status the gate answers the same class of refusal with, times `-100` (`-42900` for too many, `-50300` for cannot serve now, issue 956); any other zero that does not mean off; a reason whose unit differs from the key or misstates its own; a structure keyed on a mintable value with no capacity; a value only an environment variable or a Go option reaches; a ceiling nothing bounds. `tenancy.FindingIssue` names that finding's issue; the finding is fixed in its issue, never on the way.
4. **Make the layer read the constant, and declare its sites** on the row (`Alias`, `Arg`, `Pin`, `Enforce`, `Refuse`, `Reason`, `Charge`, `Derive`, each a symbol and never a line). **`make check-tenancy` is the gate** (`cmd/audit_tenancy`, step 23 of `make analyze` and a CI step), and every one of its fourteen rules applies to every row: it refuses a literal handed to a limit constructor, a constructor or options literal outside a declared Enforce site, a `-42900` or `-50300` refusal or a 429 or 503 gate failure (or status write) that no refusal declared in its function carries, a package-level name that reads as a limit and no row or exemption declares in a package holding an `Alias`, `Arg`, `Pin` or `Enforce` site of a row that is not a request bound, a declared site that matches nothing, a register value nothing reads and an alias only other aliases read, a refusal whose text, status, code or headers differ from its row, an authentication refusal charged where its row says it is not or the reverse, a number on a mintable key called fair, and a variable a row names that is missing from `prefixedNames` or read by anything but `internal/config`. Among what it does not see, two things are yours to check on every change: a place that stops reading the constant while another place still reads its alias, which fails only where it writes the literal straight into a listed constructor or options literal (G10), is itself a declared `Alias` (G2), changes the call a declared `Arg` names at its index (G3), or is an `Enforce` site declared to read the constant that no longer refers to it or a declared alias of it anywhere (G5). To hold one such place, make it a declared `Alias` when it is a package-level value, or read the constant in a call a declared `Arg` names at its index, since G2 judges every declared alias and G3 every such call; an `Enforce` site declared to read the constant holds only the last reference left in its body, and G10 needs no declaration, since it fails a literal written into a listed constructor or options literal wherever it is written. The other is a new limit built with none of the listed constructors or options types that refuses through a refusal its function already declares, or by calling a function whose refusal a row declares, and is named where the name rule does not read it: with no limit word, in a package that holds no `Alias`, `Arg`, `Pin` or `Enforce` site of a row that is not a request bound, or as a value local to a function. The full list, with G8's reading of a switched sentinel and the rest, is in [`cmd-utilities.md`](cmd-utilities.md#audit_tenancy) under What it cannot see.
5. **Answer the rest in the pull request**: the specification's [validation checklist](tenant-policy-spec.md#validation-checklist), of which VAL-010 (telemetry carries the reason only) and VAL-012 (a measurement, `make bench-fairness`, when the limit claims to protect one population from another) cannot be declared in a row.

**What proves the change depends on what it is.** A change of value is a change of policy and is its own pull request: the constant and its frozen pin, two lines in one package. **A change that claims to move policy without changing it is proved by `make tenancy-code-identity`**, and the base it is compared against is the whole of that proof: its parent (`BASE=<ref>`) when it inserts no line into the server's source and gives the register no new importer, and otherwise its parent with the change's own import lines of `internal/tenancy` added as blank imports at the same positions, exported and passed as `BASE_TREE=<dir>`. The import alone moves sections: the inserted lines resize the line table, which can move what the linker lays out after it, and a new importer changes where the linker places read-only data. Every value layer of issue 565 failed against its parent and was byte-identical to that base. A change to the register's own rows or text is a third case: code the server never reaches still changes the package's object and so where the linker places read-only data, and it is compared against its parent with `internal/tenancy` replaced by its own, which proves nothing outside the register moved. A rule moves into the register only when it is a pure function of values the enforcing site already holds, calling it changes neither what is evaluated nor in what order, its inputs can be enumerated or fuzzed, and the site's allocation and lock profile stays the same; it is proved by an oracle test and a fuzz target against a verbatim copy of the code it replaced, with its allocations pinned, never by the binary, since a layer now calls it (`MeterFor`, `Busy` and the three budget switches, whose measured cost is in the ADR's NEG-006). A rule written into the register from the start replaced no code, so there is nothing to copy: `CoverableAt` (row AUT-008, issue 952), the sixth rule the layers call, is held instead to the source it transcribes, GitLab's applicability table, case by case over its whole input space, with its allocations pinned at none.
