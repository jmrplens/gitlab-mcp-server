# Tier Gating

**How the licensing tier decides which actions, tools and schema fields a session is served**: the detection order, the field-level pruning, and what each surface gates at Premium and Ultimate.

> **Diátaxis type**: Reference · **Audience**: 🛠️ Contributors & maintainers

How the tier is detected is described under `GITLAB_MCP_TIER` in [Environment Variables and Flags](configuration.md), and the tier of every action is printed on its group's page of the generated [tool reference](https://docs.jmrp.io/gitlab-mcp-server/reference/tools/).

---

`GITLAB_MCP_TIER` controls access to GitLab Premium/Ultimate features in stdio mode (Enterprise tools are gated when the resolved tier is Premium or Ultimate). In HTTP mode, the `--tier` flag forces the tier; when omitted, it is detected per token+URL pool entry by the steps `GITLAB_MCP_TIER` describes in [Environment Variables and Flags](configuration.md): the instance license, then the namespace plans, then on GitLab.com the top-level groups the token is a member of, falling back to `free`. The catalog effect is the same in individual and meta-tool modes.

The tier affects tool registration (input/output schemas and tool lists) through `pruneSchemaFieldsByTier` in `internal/tools/action_catalog.go`: every registered action has its input schema pruned strictly (lower-tier clients never see higher-tier input fields, even though the SDK type still carries them, and the pruned names travel on the route as `ActionRoute.TierPruned`, so a call sending one is refused on every surface with the tier it needs before anything is sent, issue 1239) and its output schema pruned leniently (`lenientExtra=true`: higher-tier output fields are kept but omitted from the model-facing schema, so a Premium client reading an Ultimate response sees the data; an Ultimate client reading a Premium response does not). The 3-tier field-level gating is described per-field with `tier:"premium"` / `tier:"ultimate"` struct tags throughout `internal/tools/*/action_specs.go` and `internal/tools/*/shapes.go`.

**Individual mode** (`GITLAB_MCP_TOOL_SURFACE=individual`) gates the same actions through the same catalog metadata, one tool each: every action of the dedicated groups and the paid actions of the seven base groups listed under meta-tool mode below. An action's minimum tier is its `ActionSpec.Edition` (`premium` or `ultimate`), set by the domain package or, for a whole package, by `editionTaggedSpecs` in `internal/tools/action_specs.go`; an empty one is Free. The generated tool reference states the tier of every action on its group's page, measured by building the catalog at each tier. Group releases and group service accounts are Free.

**Meta-tool mode** (`GITLAB_MCP_TOOL_SURFACE=meta`) gates 17 dedicated Enterprise/Premium catalog groups:

- gitlab_merge_train, gitlab_audit_event, gitlab_dora_metrics, gitlab_dependency, gitlab_external_status_check, gitlab_group_scim, gitlab_member_role, gitlab_enterprise_user, gitlab_attestation, gitlab_compliance_policy, gitlab_project_alias, gitlab_geo, gitlab_vulnerability, gitlab_security_attribute, gitlab_security_category, gitlab_security_finding, gitlab_security_scan_profile

and an eighteenth on GitLab.com alone, `gitlab_orbit` (Premium, contributed by `buildOrbitActionSpecs` only for a GitLab.com client).

Plus paid actions that join 7 base meta-tools; each action listed is served from the tier named, and the rest of its group is Free:

- `gitlab_project` → approval_config_*, approval_rule_*, push_rule_*, pull_mirror_*, start_mirroring, target_branch_rule_*, dependency_firewall_evaluate (Premium); security_settings_* (Ultimate). The push mirror routes, mirror_*, are Free
- `gitlab_group` → epics with their issues, notes, discussions, links, boards and label events; wikis; protected branches and environments; webhooks (hook_*); push rules; LDAP and SAML links and SAML users; provisioned users; billable members; SSH certificates; the analytics counts; the milestone burndown; creating and deleting a group board (Premium); credentials (credential_*) and security_settings_update (Ultimate). Group releases and service accounts are Free, and group iterations are served by `gitlab_issue`
- `gitlab_issue` → project and group iterations (iteration_list_project, iteration_list_group) and the iteration and weight resource events (Premium)
- `gitlab_merge_request` → approval rules, approval state and the project and group approval settings, and merge request dependencies (Premium)
- `gitlab_environment` → protected environments, protected_* (Premium)
- `gitlab_storage_move` → group repository storage moves, the *_group actions (Premium); project and snippet moves are Free
- `gitlab_runner` → runner controllers with their scopes and tokens, controller_* (Ultimate)

**Dynamic mode** (default): the same catalog gating applies: `gitlab_find_action` never lists and `gitlab_execute_action` never runs an action above the resolved tier, so the tier changes which `domain.action` IDs exist rather than which tools are registered. Execute answers such an action as withheld rather than unknown, naming the tier it needs and the tier the session was built for, and asks the operator to pin the tier (issue 956); an action the operator excluded by name stays unknown whatever its tier.

## A provisional tier

A step of the probe either answered or was not read, and the two are told apart before the tier is (issue 1782, register rows `AUT-003` and `AUT-010`). `internal/gitlab.Client.ResolveTier` returns a `TierResolution`: the tier, whether any step `Answered`, whether it is `Provisional`, and the `Unresolved` steps by name (`license`, `namespaces`, `membership`). `tierReadUnresolved` decides per request: no status at all (a deadline, a cancellation, a network or TLS failure, a body that does not decode), a redirect, `408`, `429` or a `5xx` after the retries is not read, while `401`, `403`, `404` (`gl.ErrNotFound`) and every other `4xx` are answers. The membership step adds two of its own: an answer with no `groups` connection is not read, and a document answered with `data: null`, or a page with a node null beside its errors, is not read unless every error in it is GitLab's permission refusal (`documentRefusalError.permissionOnly`), since a field that runs out of time nulls its node as a refused one does and the null node may be the group that raises the tier; the groups such a page resolved still count, as the floor of the step. An empty page, a page of null nodes refused for the permission alone (a fine-grained token), a page that resolved a group beside the permission refusal and the page bound are answers. A step not read lowers nothing, and the result is provisional unless it is Ultimate, which nothing can raise.

`ResolveTier` stores nothing on the client, so the pool can ask it of a client whose catalog is registered; `DetectTier` stores the tier and warns at WARN, naming the unresolved steps, when it is provisional, and then asks no edition, since the budget that left a step unanswered would be spent again on `/version`. The enterprise warning stays for a tier every step read and none answered, and `warnUnresolvedTier`, which reads the edition through `readEdition` and stores nothing, says at DEBUG that the edition could not be read rather than calling the instance CE. The membership query is a POST that only reads: it is sent with `gl.WithContext(ctx)` and then `gl.WithRequestRetry(c.membershipRetry)`, go-retryablehttp's default policy under `RTC-006`'s two retries and backoff (in that order, since `WithContext` replaces the context the retry check reads), and none on a client built without retries. It runs under `TierMembershipTimeout` (8 s), measured from the membership base `ResolveTier` and `DetectTier` take beside the context the other steps share, the pool's lifetime or the stdio process context, so the license and namespace steps cannot spend its clock, which is what raised the worst entry build on GitLab.com from about 20 s to about 28 s (the credential probe's 5, the shared 10, the membership's 8 and the identity read's 5).

In HTTP mode an entry built on a provisional tier carries a mark (`serverpool.provisionalTier`), logs `tier_source=detected_provisional` with `tier_unresolved`, and is asked again by `ServerPool.StartTierRedetection`, a sweep of its own beside the revalidation and idle sweeps, started whatever `--revalidate-interval` says and not at all under `--tier`. Each tick (`TierProvisionalRetry`, 1 minute) asks the entries whose wait ends no later than half a tick after it (`dueTiers`), so an ask falls on the tick nearest the end of its wait even though the wait is measured from when the previous ask's answer arrived, each under a credential probe slot taken without waiting (`POL-006`), and the wait doubles from `TierProvisionalRetry` up to `TierProvisionalRetryMax` (15 minutes) while the answer stays provisional. `settleTier` keeps the same tier answered whole and clears the mark; a higher tier, or another answered whole, goes to `replaceTier`, which builds a server for the new shape outside the lock, then puts a new entry under the key (`assembleEntry` from the old entry's `seed`: the same client, identity, token facts, credential handle and credential age, a new owner), calls the insert hook, moves the client's tier and 401 hook to it and evicts the old entry with `CauseTierResolved` (`tier_resolved`), which `watchEndForCause` ends as `credential_reset`. A refused insert, a failed build and a missing server keep the old entry and ask again later. A 401 naming the credential reaches the client's hook only once, so one handed to the old entry in the window around the swap, and a below-minimum verdict the revalidation sweep reaches for the old entry from a snapshot taken before it, end the replacement: `dropRejectedEntry` and `dropBelowMinimumEntry` act on the entry under the key that carries the same client (`holderLocked`), as `learnTokenFacts` writes there, and leave alone an entry rebuilt with a client of its own. A provisional answer never lowers the tier, so an entry is replaced at most twice. Stdio warns a second time that the process keeps the tier until it ends; asking again there and re-registering the catalog in place is a follow-up.
