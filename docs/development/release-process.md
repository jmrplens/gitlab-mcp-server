# Release Process

**How a release is rehearsed, cut and published**: the order of the release workflow's jobs, what moves the "latest" pointers, and the rules each publishing channel holds a release to.

> **Diátaxis type**: How-to & Reference · **Audience**: 🛠️ Contributors & maintainers

How each artifact is built and what refuses a bad one is in [Distribution](distribution.md), and the settings this workflow depends on that live on GitHub rather than in the tree are in [Repository Settings](repository-settings.md).

---

**Major-version policy**: the server's major tracks client-go's major: when client-go moves to v3, this project moves to v3 in that same dependency bump (removing the deprecated compatibility fields kept during v2, e.g. the flat copies in the dual-shape group Datadog output). All other dependency updates ship as minor/patch.

**Rehearse before tagging.** `gh workflow run release.yml --ref <branch>` releases the dispatched tree, as the version its `VERSION` file carries, without publishing anything (an optional `-f tag=v<VERSION>` states the version explicitly, and preflight holds the two to each other as it does for a real tag): the E2E gate boots a GitLab, GoReleaser builds every binary as a snapshot carrying that version (`snapshot.version_template` in `.goreleaser.yml`), the image is built for both platforms, smoke-tested, its Alpine packages held to Trivy's database (`cmd/audit_image_vulns`, issue 1129) and exported to an OCI layout so the digest `server.json` is stamped with is the real index digest, and the publishers take that build from a workflow artifact (`REHEARSAL_ARCHIVE` in `scripts/fetch-release-assets.sh`), validate it and run their publish commands dry. Skipped is exactly what cannot be undone: the image push and signatures, the GitHub release and attestations, the npm, PyPI and NuGet uploads, the tap push, the registry publish, the commit to main, winget; `verify-published` has nothing to read and says so. The publisher jobs of a rehearsal run in the `release-rehearsal` environment and never in `release` (issue 1322): every trusted publisher (npm, PyPI, nuget.org) binds this repository, `release.yml` and the `release` environment and none can bind a ref, so the environment is what keeps a dispatched branch from minting the release's identity, and `release-rehearsal` holds no secret and no publisher names it. The NuGet login is skipped in a rehearsal for the same reason; it used to run there to prove the nuget.org policy still matches, which is now read off nuget.org's settings instead (`docs/development/repository-settings.md`). What binds `release` to release tags is two settings on GitHub, both applied on 2026-10-20: the environment's deployment policy, admitting only tags matching `v*` with administrator bypass off, and the `Create release tags` ruleset, restricting who creates such a tag. Each has its `gh api` check on that page, and nothing in the tree notices when one is removed, so the page's **Current state** entries are the record to check them against. A dispatch is always a rehearsal; there is no input that makes it publish. The tree is the dispatched ref, never the tag: the publisher jobs were added after 2.7.5, and the first rehearsal, run against that tag's tree, found half the scripts the workflow calls missing.

**Only the newest stable release moves "latest"** (issue 1323). Preflight asks `scripts/release-order.sh` before anything publishes, from the tags `git ls-remote --tags` lists and `sort -V`: a tag that is not a plain `vX.Y.Z` (a prerelease, a build suffix) is refused there, and its `newest` output is false for a backport, a stable tag lower than one already released. A backport publishes under its own version on every channel and moves no pointer: `:latest` is pushed to `ghcr.io` and Docker Hub only for the newest release and so is the Docker Hub repository description, the GitHub release is published with `--latest=false` (the installers read `/releases/latest`), npm publishes under the `release-X.Y` dist-tag rather than `latest` (`scripts/publish-npm.sh --tag`), and the `homebrew`, `mcp-registry` and `commit-manifests` jobs are skipped, so neither the tap, the registry entry nor `main`'s manifests (and with them the site's `%%VERSION%%`) go back; `scripts/update-homebrew-tap.sh` also refuses on its own to write a version older than the tap's. PyPI and NuGet resolve the highest version whatever was published last. A rehearsal computes the same outputs from `VERSION`. `TestLoadWorkflows_ReleaseWorkflow_OnlyTheNewestReleaseMovesAPointer` in `cmd/audit_supply_chain` holds `release.yml` to reading the answer at each of those steps and jobs, so one that drops its condition fails the build; a pointer added later has to be added to that test as well. [Distribution](distribution.md) has the rule in full.

**Every release opens with a written summary.** From 3.0.0 to 3.3.0 a release's notes were only the commit list GoReleaser generates (`changelog: use: github` in `.goreleaser.yml`), one line per commit, which tells a user nothing about what breaks, what to do when upgrading, or which vulnerabilities the release fixes; the releases before them carried a generated list of changes or notes written by hand, in no fixed shape. Each release now has `.github/release-notes/vX.Y.Z.md`, written in the pull request that moves `VERSION` and reviewed there, with four sections: `## Summary` (the changes that matter to a user, with their pull requests), `## Breaking changes`, `## Upgrading` (what to change, in order) and `## Security` (every advisory or CVE the release fixes, by its identifier, and the dependency advisories it takes; `None.` where there is nothing). A parameter or response field withdrawn under the versioning policy's withdrawal row is named there with its tools, as the site's [Releases and versioning](https://docs.jmrp.io/gitlab-mcp-server/changelog/) page promises. Three places hold it, each for a different failure:

- `cmd/audit_supply_chain` (property 7, `make check-supply-chain`, so CI and `make analyze`) fails a tree whose `VERSION` has no notes, and holds every file of the directory to the four sections, in order, each non-empty, and to carrying no em or en dash, no command that makes GitHub skip workflows and no credit to an assistant. The pull request that moves `VERSION` fails CI without the file.
- Preflight's `Hold the release to its written summary` step fails the run when `.github/release-notes/<tag>.md` is missing or blank, in a rehearsal too, before the E2E gate boots a GitLab. GoReleaser reads the file only outside a snapshot, so without this step a rehearsal would pass on a tree whose tag push then fails at GoReleaser, after the image is pushed.
- The GoReleaser step passes the file with `--release-header`, on both sides of its `args`, with the path built by a workflow expression from `needs.preflight.outputs.release_tag`, since goreleaser-action splits `args` into words and expands no shell variable. The release body is the summary, then GoReleaser's `## Changelog`, then the configuration's footer. It is the flag rather than the `from_file` form of the configuration's release header, which is GoReleaser Pro's and not in the OSS release the workflow pins, and the file is tracked because GoReleaser refuses a dirty tree.

The summaries of v3.0.0 to v3.3.0 were written after those releases, and are put above their published notes by hand: `gh release edit <tag> --notes-file <file>`, the file holding the summary and then the body the release already carries, with `--latest=false` on every release but the newest so that the edit cannot move `/releases/latest`. An immutable release allows it, since it changes the body and neither the tag nor an asset. A summary that needs correcting after its release is edited in this directory first and then published the same way. `TestReleaseNotes_Repository_KeepThePublishedSummaries` in `cmd/audit_supply_chain` keeps the notes of v3.0.0 to v3.3.0 in the tree, and those of the newest published release, the version the release stamps into `server.json`, which the gate alone stops requiring once the pull request that prepares the next release moves `VERSION` past it; a release older than the newest and later than v3.3.0 is kept by review.

**Every release binary is rebuilt and compared.** The `reproduce` job of `release.yml` runs after `release`, on `ubuntu-24.04-arm` while the release builds on x86_64, fetches the published assets the way the publishers do (`scripts/fetch-release-assets.sh`, and in a rehearsal the rehearsal's own build) and runs `make check-reproducible TAG=<tag> REF=HEAD PUBLISHED=<dir>`. [`cmd/reproduce_release`](cmd-utilities.md#reproduce_release) clones the commit, reads `.goreleaser.yml` at it, holds each published binary to `checksums.txt` and to the commit, clean tree and toolchain its build information records, rebuilds it with that toolchain, joins the universal darwin binary in the order the published one's header lists its slices, and fails on any binary whose bytes differ. It runs beside the publishers rather than in front of them, because by the time it can read the release the release is public and immutable, and stopping npm, PyPI and NuGet halfway would unpublish nothing: a failure is a release that does not rebuild, which is an issue to open. Up to 3.3.0 `.goreleaser.yml` stamped `{{.ShortCommit}}`, which git abbreviates to as many characters as the clone's object count needs (3.3.0 was stamped `f8813193`, and a full clone abbreviates that commit to nine characters today), so a rebuild from another clone could differ; it stamps `{{.FullCommit}}` now, like the image. `cmd/reproduce_release`, given the 3.3.0 assets fetched and verified by `scripts/fetch-release-assets.sh` and `-short-commit f8813193` (what `make check-reproducible TAG=v3.3.0 SHORT_COMMIT=f8813193 PUBLISHED=<dir>` runs), rebuilt all seven 3.3.0 binaries bit for bit on 2026-10-25, `gitlab-mcp-server-linux-amd64` as `24fb56e2ef04520c0a576fd227454203f79cd16a5700e77d6f38216dc632a6dc`, and `make check-repeatable` builds every target of a checkout twice, the second time with an empty build cache, without git or a release. The image is not covered: its build is not byte-reproducible (see the invariants at the top of `release.yml`) and its binary is a separate musl build without `-trimpath`, for the reason the `Dockerfile` gives.

When creating a new release and uploading binaries to GitHub Releases:

1. Build cross-platform binaries with `make release` (uses GoReleaser locally, flattens `dist/` to match GitHub Release asset names). In CI, GoReleaser creates the GitHub release **as a draft** and a dedicated staging step copies each binary from its per-target subdirectory to `dist/<release-asset-name>` (driven by `dist/artifacts.json`), and the npm steps read those paths. The draft is published (`gh release edit --draft=false`) only after the bundles are attached and every artifact is attested with `actions/attest-build-provenance`, so no installer observes a partial release. Each release also ships one SPDX SBOM per binary (`<asset>.sbom.json`, listed in `checksums.txt` before cosign signs it as `checksums.txt.sigstore.json`), and `THIRD_PARTY_NOTICES`, the license, notice and patent texts of every module the binaries link, which `cmd/gen_third_party_notices` writes as the `third-party-notices` entry of GoReleaser's `sboms` (the one hook placed after the builds and before the checksums and signing), so the file is a release asset in the signed `checksums.txt` and a generation that fails fails the release. Every package carries it: `scripts/fetch-release-assets.sh` requires it among the default patterns, the npm, PyPI and NuGet builders verify it against `checksums.txt` and their validators hold each copy to the digest the builder recorded, `scripts/build-mcpb.sh` packs it from `dist/` into every bundle, and the image's builder generates its own from the image's binary into `/usr/share/licenses/gitlab-mcp-server/` beside `LICENSE`, which `scripts/smoke-test-image.sh` checks. The Linux binaries are PIE and so name a loader in `PT_INTERP`, which Go's linker otherwise picks by stat-ing whatever host builds them; `.goreleaser.yml` names the glibc loaders in per-target `overrides` (`/lib64/ld-linux-x86-64.so.2`, `/lib/ld-linux-aarch64.so.1`, the values every Linux channel promises), and `scripts/check_elf_interp.py` holds both staged binaries to them right after GoReleaser, once for every channel that ships them (tested by `scripts/check_elf_interp_test.py`, which also holds its table to the overrides).
2. **Release link names MUST be exact filenames** (e.g. `checksums.txt.sigstore.json`, `gitlab-mcp-server-linux-amd64`). Never add descriptive suffixes like `(GPG signature)`: the Homebrew formula, winget, the installers and `scripts/fetch-release-assets.sh` look assets up by exact name and will not find a decorated one
3. The tag-triggered release workflow also publishes derived artifacts automatically:
   - `gitlab-mcp-server-darwin-all`: macOS universal (fat) binary from GoReleaser `universal_binaries`
   - `gitlab-mcp-server-darwin.mcpb`, `gitlab-mcp-server-windows.mcpb` and `gitlab-mcp-server-linux.mcpb`: the Claude Desktop extension, one bundle per operating system, each carrying only its own system's server, `LICENSE`, and a manifest listing only its own platform (derived from `mcpb/manifest.json` by `mcpb/platform.jq`). Built by `scripts/build-mcpb.sh`, which prints each bundle's download and unpacked size, fails on Claude Desktop's own limits (512 MiB per entry, 2048 MiB unpacked, 50 times the archive's size, 100,000 entries) and warns when a declared bundle passes 50 MiB to download or 256 MiB unpacked, the sizes past which directories stop reading a bundle (3.1.0's single bundle, at 73 and 285 MiB, lost its provenance, licence and maintenance signals on verifymcp.io that way). Validate with `make check-mcpb`, build locally with `make mcpb`
   - `gitlab-mcp-server.mcpb`: the universal bundle, all three systems' servers in one file, built from the same outputs and uploaded under the name it always had so that links outside this repository keep working. It is attested like the others and declared nowhere
   - Homebrew formula update pushed to `jmrplens/homebrew-tap` by `scripts/update-homebrew-tap.sh` (secret `TAP_DEPLOY_KEY_B64`)
   - winget version PR to `microsoft/winget-pkgs` via komac (secret `WINGET_TOKEN`), fetched at a pinned version and held to a recorded SHA-256 in the `winget` job rather than run through `winget-releaser`, whose pinned commit installed cargo-binstall from a branch head and the newest komac with the token in hand (issue 1232); a rehearsal runs the same `komac update` with `--dry-run` and the job's own token
   - Version stamping of `server.json`, `plugin.json` (Agent Plugins), `.plugin/plugin.json` (legacy Open Plugins), `mcpb/manifest.json`, and `lhm.plugin.json` (LobeHub Marketplace) committed back to main by `scripts/update-server-json-sha.sh`, which also pins the OCI image tag and re-derives each mcpb entry's hash from the per-OS bundles passed, comma-separated, as its third argument
4. **LobeHub Marketplace is a manual publish step.** The stamping script keeps `lhm.plugin.json`'s version current on every release, but the LobeHub CLI (`@lobehub/market-cli`) has no non-interactive publish path (browser OIDC login + GitHub connect are required once), so it cannot run in CI. After a release, run `make publish-lobehub` from a machine with `lhm login` + `lhm github connect` already completed (the target runs `lhm plugin update`; the CLI's `plugin publish <gitUrl>` verb is for first-time listings only). The listing is `jmrplens-gitlab-mcp-server`.
5. **The manifest's capability arrays are generated, its version is not.** LobeHub derives the listing's capability badges from the `tools`, `prompts`, and `resources` arrays in `lhm.plugin.json`, since its scanner cannot introspect a server shipped as a binary or an image, so a manifest without them advertises zero tools. `make gen-lhm-manifest` rewrites those three arrays from a live `tools/list` + `prompts/list` + `resources/list` round-trip and leaves every other field, `version` included, to the release stamp. `make check-lhm-manifest` gates freshness in CI and runs before `make publish-lobehub`.

   The generator declares the **default** surface: it pins `dynamic` and talks to an in-process stub client instead of reading `GITLAB_MCP_TOOL_SURFACE`, `GITLAB_URL` or `GITLAB_TOKEN`. Anything a generator reads from the environment ships in the committed file, so a developer machine with `GITLAB_MCP_TOOL_SURFACE=individual` exported would otherwise publish a different manifest than CI checks. New environment-sensitive inputs belong in `cmd/internal/mcpsurface`, pinned there once for every generator, not read at the call site.

6. **npm publishes automatically via an OIDC trusted publisher, with no stored token.** The distribution is a launcher package (`@jmrp.io/gitlab-mcp-server`) plus six per-platform packages that each carry a release binary, the esbuild/biome model, so `npx` works, `--ignore-scripts` works, and nothing is downloaded at install time. The `npm` job of `release.yml`, which runs after the `release` job, fetches the binaries the release published with `scripts/fetch-release-assets.sh` (a rehearsal takes its own build from the workflow artifact instead), verifies them against the cosign-signed `checksums.txt`, validates the packages and publishes them in its `Publish to npm` step. It authenticates through [npm trusted publishing](https://docs.npmjs.com/trusted-publishers): the job's `id-token: write` lets npm mint an OIDC token, and npm ≥ 11.5.1 (the step upgrades the setup-node 22 default) performs the exchange, so no secret is stored anywhere and provenance is attached automatically (no `--provenance` flag). `scripts/build-npm.mjs` assembles the packages from `dist/` (Node's `win32`/`x64` names mapped to Go's `windows`/`amd64` in one table there); `scripts/publish-npm.sh` publishes the platform packages first, then the launcher (that order matters, or an install racing the publish resolves optional dependencies not on the registry yet), and it **skips any version already published** so re-running a release job does not die on npm's 409. **`scripts/validate-npm.mjs` runs before the publish step** (a published npm version is permanent): it packs all seven tarballs and checks their file set, the binary's executable bit and platform magic number, a size floor, and the os/cpu/name/version, then installs the launcher plus the host-native platform package and drives a real MCP handshake asserting stdout is pure JSON-RPC (`--no-install` stops after the structural checks, for `scripts/validate_npm_test.py`), and on Linux starts that package through `npx` twice, in stdio mode and with `--http`, and requires a SIGTERM sent to the `npx` process alone to end the server within ten seconds. That is the launcher's (`npm/gitlab-mcp-server/cli.js`) job: npm passes the signal only to the `sh -c` it runs the launcher through, so the launcher passes SIGTERM, SIGINT and SIGHUP on to the server and, when npm started it, sends the server SIGTERM once its parent changes; up to 3.1.0 it blocked in `spawnSync` and an HTTP server started with `npx` kept its port. `scripts/npm_cli_js_test.py` holds the launcher to that against a stand-in binary. Every one of the seven tarballs carries the repository's `LICENSE`, held to it byte for byte: `build-npm.mjs` copies it into each platform package and into the checked-in launcher directory, where the copy is git-ignored so the text has one source. `make validate-npm NPM_BINARIES=dist` runs it in a clean `node:22` container so a developer's machine is never touched; the `npm` job runs `make validate-npm-local` on the ephemeral runner. **Bootstrap constraint:** a package cannot have a trusted publisher configured until it exists, so the first version (v2.7.5) was created by a one-time tokened `make publish-npm`; the trusted publisher on npmjs.com is then configured **per package** (all seven) naming this repo, the workflow file `release.yml`, and the `release` environment (the job runs in `release` for a tag push and in `release-rehearsal`, which no publisher names, for a dispatch), after which the token is removed and every later tag publishes with no credential. The launcher's version and its optionalDependency pins move together via `build-npm.mjs --sync-only`, wired into `scripts/update-server-json-sha.sh` so the committed `npm/gitlab-mcp-server/package.json` stays current with the release stamp. For an out-of-band publish, `make publish-npm NPM_BINARIES=dist` from a machine with an npm token (rehearse with `make publish-npm-dry`). The unscoped name `gitlab-mcp-server` was already taken on npm, hence the scope.

7. **PyPI publishes beside npm, from the same published binaries.** The `pypi` job of `release.yml` runs after the `release` job, in parallel with the `npm` job, and fetches and verifies the release's binaries the same way before `make validate-pypi-local` builds and checks the wheels. The distribution is six platform wheels (`scripts/build_pypi.py`, standard library only) with the native binary in the wheel's `.data/scripts` directory, the uv/ruff model, so the installer places it on the scripts path as the `gitlab-mcp-server` command itself and no Python runs on the hot path (`uvx jmrplens-gitlab-mcp-server` works via a console-script wrapper named after the distribution, and the installed command stays `gitlab-mcp-server`; a `gitlab_mcp_server` module remains for `python -m` and programmatic lookup). Two traps the validator (`scripts/validate_pypi.py`, run before every upload because a published PyPI file name is burned forever) pins: the binary's zip entry needs `S_IFREG` in `external_attr` (pip's `zip_item_is_executable` requires `S_ISREG` before honoring the 0o111 bits; permission bits alone install it non-executable), and the manylinux_2_17 tag is verified against the binary's actual glibc symbol demands (none: Go internal linking). The wheel METADATA embeds `pypi/README.md`, which must keep the `mcp-name: io.github.jmrplens/gitlab-mcp-server` token the MCP Registry validates for pypi ownership. The licence is declared as core metadata 2.4 defines it (PEP 639): `License-Expression: MIT` and a `License-File` for each text the wheel carries under `.dist-info/licenses/`, with neither the legacy `License` field nor a `License ::` classifier, since the specification makes the field and the expression mutually exclusive and PyPI refuses a file carrying both; the validator holds each text to the repository's own file byte for byte and runs `twine check --strict` when twine is installed. METADATA also links the issue tracker and the security policy under the well-known `Issues` and `Security` labels. The distribution name is `jmrplens-gitlab-mcp-server`: the unprefixed PyPI name is an empty registration held by an unrelated account, under a PEP 541 reclamation request; when reclaimed, the rename is `DIST_NAME` in `scripts/build_pypi.py` and `scripts/validate_pypi.py`, the `server.json` identifier, and the docs. CI publishes with `scripts/publish-pypi.sh --trusted-publishing` rather than an action (issue 1243): twine and `pypi-attestations` come from the hash-pinned `.github/requirements/pypi-publish.txt`, each wheel gets a PEP 740 publish attestation signed with the job's identity, and the upload token is minted from the job's OIDC token under the trusted publisher (configured on pypi.org naming this repo, `release.yml`, environment `release`, as [Repository settings](repository-settings.md#pypi-trusted-publisher) records) and handed to twine alone, with `--skip-existing`, so re-runs are safe; a rehearsal runs the script with `--dry-run`, which stops before anything is signed or minted, and `verify-published` holds every wheel to the provenance PyPI serves for it ([Distribution](distribution.md#the-other-channels) has the steps). `make publish-pypi PYPI_BINARIES=dist` is the tokened out-of-band path (`PYPI_TOKEN`, no attestation), and `make validate-pypi PYPI_BINARIES=dist` runs the whole check in a clean `python:3.14-slim` container.

8. **A `server.json` `remotes` URL must be globally unique across the whole MCP Registry, and the comparison is on the literal string.** The registry refuses a publish whose remote URL any other server already claims, templates included. This repository used to declare `https://{host}:{port}/` as a self-hosted form; the sibling `libgen-mcp` copied that pattern and its v1.5.2 publish was rejected with `remote URL https://{host}:{port}/ is already used by server io.github.jmrplens/gitlab-mcp-server`. Checking that nothing claims your _hostname_ is not the check: the string is. Generic templates are therefore not worth claiming: the self-hosted HTTP mode they advertise is documented on the site's [HTTP server page](https://docs.jmrp.io/gitlab-mcp-server/operations/http-server/) anyway, and holding one blocks every other server you publish. `make check-server-json` validates the schema only; uniqueness is a registry-side property no local gate can see.

9. **`server.json`'s `packages` array says what a client should install, and almost nothing about it is schema-checkable.** The package entries declared are the Claude Desktop bundles (one per operating system from the first release that builds them; main declares the single universal bundle until then), the `ghcr.io` image, the Docker Hub image, the npm launcher, the pypi distribution, and the nuget tool. Three traps, each of which passed `make check-server-json` while being wrong:
   - **`registryType: "mcpb"` means the bundle, not a binary.** Up to v2.7.5 the manifest declared six `mcpb` packages pointing at the raw per-platform executables (`7f 45 4c 46`) while the real bundle (`50 4b 03 04`) shipped in the same release, undeclared. Every directory that scores a server by installing what it declares scored the raw ELF.
   - **The mcpb entries are written by the stamp, one per bundle, and never by hand.** A registry entry has no platform field, so a client cannot choose between bundles by system; what tells them apart is the `compatibility.platforms` list inside each one, which also makes Claude Desktop refuse a bundle opened on the wrong system. `scripts/update-server-json-sha.sh` takes the bundles as a comma-separated third argument and rebuilds the mcpb entries from them, copying the first mcpb entry's transport and environment variables and giving each its own identifier and `fileSha256`; it refuses, before writing anything, a set that does not serve darwin, win32 and linux exactly once each, which keeps the universal bundle out. Editing the entries by hand ahead of a release would declare URLs that 404 until it exists and hashes nobody can know, and `check-server-json-packages` runs on every push to main.
   - **The OCI entry must declare no `packageArguments` at all.** Any argument after the image name replaces `CMD` wholesale, so an entry that names one is opting out of whatever the image's command does. While `CMD` was `--http --http-addr 0.0.0.0:8080`, opting out was exactly what the entry wanted: a client running `docker run -i` with no argument override got an HTTP listener and hung at `initialize` forever, and the entry carried `packageArguments: [{"type": "positional", "value": "--http=false"}]` to undo it. `CMD` is now `--transport auto --http-addr 0.0.0.0:8080`, which reads the transport off file descriptor 0, so the `-i` implied by the entry's stdio transport hint is enough on its own and an argument would only take the `--http-addr` away with it. `scripts/validate-server-json-packages.sh` therefore accepts an argument-free entry only when `CMD` reaches stdio by itself, and still demands an explicit stdio argument from any entry that declares arguments at all. It reads that `CMD` from the image the entry pins, which is a _published_ image and so lags this repository by a release; when the published one predates the inference it falls back to the `Dockerfile` here and says so, the same transitional shape the npm branch uses for `mcpName`. A `Dockerfile` regressed to a bare `--http` fails either way.
   - **An OCI entry must NOT carry `version`, `registryBaseUrl` or `fileSha256`.** The registry rejects them at `mcp-publisher publish`, server-side, long after the schema check passed. Its version lives in the image reference, which `scripts/update-server-json-sha.sh` pins separately from the URL rewrite. Ownership is validated through the image's `io.modelcontextprotocol.server.name` label, which the `Dockerfile` sets.
   - **The image is pinned as `<repo>:<tag>@sha256:<digest>`**, the third form the registry's OCI validator accepts. The tag stays readable and matches every doc; the digest is what a client actually resolves, so re-pushing a published version tag cannot change what gets installed; it was the last mutable pointer in the manifest (the bundle has `fileSha256`, an npm version is immutable). The digest comes from the docker job's `docker-push` output, which is why `release` depends on `docker`; the stamper takes it as a fourth argument and **refuses to stamp** a digest-pinned identifier without one, since pinning the new tag beside the previous release's digest would be worse than either alone.

   - **There are two OCI entries, ghcr.io and Docker Hub, and they carry the same digest.** The multi-platform build is pushed once to both registries, so both hold the byte-identical index and one `docker-push` digest pins both; the ownership label the registry validates is the same label on the same image. That is why the stamper rewrites each OCI identifier **inside jq, per entry**, instead of computing one identifier in the shell and assigning it to every OCI entry, which is what it did while there was only one and which would have republished the ghcr.io reference under the Docker Hub entry. Docker Hub is a declared channel rather than a mirror: it is documented as an install route, its repository description is pushed from this repository on every release, and the image is signed and attested there on the same terms as ghcr.io. Two mechanical differences, both handled in the gate and in the workflow: Docker Hub's registry API is not on the hostname the reference names (`https://docker.io/v2/` redirects to the marketing site, and both the gate and `actions/attest` canonicalize to `registry-1.docker.io`), and its token endpoint is a separate host taking a `service` parameter. The registry's own validator pulls the image anonymously, so a Docker Hub anonymous-pull 429 is possible; it fails closed with "please retry shortly", which the publish job's retry loop already matches.
   - **A cosign signature is not build provenance.** The signature over the image index has an empty in-toto predicate: it says the release workflow pushed this index, not which commit or run produced it. `actions/attest-build-provenance` answers the second question and runs three times per registry with `push-to-registry: true`, over the index and each of the two platform manifests it lists, so every attestation is a referrer on its subject as well as a record in GitHub's attestation store, which a scanner reading a registry cannot see. The platform manifests are attested because verifiers disagree about which digest the image is: `gh attestation verify oci://` resolves a tag to the index, while a scanner that pulls the image for its own platform resolves the index to one manifest and reads that digest's referrers (verifymcp.io's scan of 3.0.0 reports the linux/amd64 manifest as its subject, and found the cosign signature there only because `cosign sign --recursive` signs every manifest the index lists). It changes the subjects' referrers and never the subjects, so the digest `server.json` pins is unaffected and no re-stamp is needed. `cosign-release` is pinned on all eleven `cosign-installer` steps for a related reason: the cosign major decides how a signature is attached, and a 2.x client reports "no signatures found" on an image a 3.x client verifies. **None of this runs in the job that builds the image.** `sign-attest` holds the two cosign signatures and all twelve attestations, and `release` names it in `needs` so that a signature or attestation that fails still stops every publisher, which the old arrangement got for free by living inside `docker`. `docker` keeps `packages: write` and loses `id-token`: the build is not byte-reproducible (BuildKit's own `provenance: true` attestation carries timestamps whatever the build args say), so a re-run of the build job pushes a new index under the same `3.0.0` and `latest` tags and orphans the one already signed, which `server.json` is by then pinning. With the split, a failed attestation costs a re-run of three minutes of signing against the published image and no tag moves. The GitHub release being immutable does not cover this: what moves is a registry tag. The SBOMs are still generated in `docker` and cross as an artifact, because a rehearsal has no pushed image to scan and does have the two smoke images in that job's daemon.
   - **The image's SBOM is published twice, on purpose.** `sbom: true` on the build writes an SPDX document into the index as an attestation manifest, one per platform, and a client reading the registry's referrers never sees it: those `unknown/unknown` manifests are part of the index rather than referrers of anything. `actions/attest` publishes the same information as a referrer, so both readers are served and neither document replaces the other; it is the action itself rather than the deprecated `actions/attest-sbom` wrapper, pinned to the version the provenance wrapper delegates to, so all twelve attestation steps run one credential lookup. It is given `predicate-type` and `predicate-path` rather than `sbom-path`, because `sbom-path` derives the predicate type from the document's `spdxVersion` and emits `https://spdx.dev/Document/v2.3`, while Trivy matches the unversioned `https://spdx.dev/Document` by exact string equality and finds nothing under the versioned spelling; the in-toto specification lists both Type URIs, so the unversioned one is passed explicitly. It runs **six times, over the index and each platform manifest on each registry**, which reverses an earlier reading that an SBOM over an index would be a document about nothing. That reading is right about an index having no contents of its own and wrong about what a scanner does: `trivy image <repo>:<tag>` resolves the tag to the index and reads that digest's referrers and nowhere else, so an index carrying no SBOM reads as a server that publishes none. The index attestation carries the amd64 document by convention; the platform attestations are what a reader that already resolved a platform for itself finds. `gh attestation verify oci://…:<tag> --predicate-type https://spdx.dev/Document` therefore answers on the tag as well as on a platform digest. The same documents are attached a second time with `oras attach` as bare `application/spdx+json` referrers, because what `actions/attest` writes is a sigstore bundle and a reader looking for the plain media type does not match it; those sit beside the attestations and replace neither. syft is fetched by hand in the docker job for the same reason the release job fetches it that way, its bytes pinned by SHA256 and its provenance checked with cosign, since `anchore/sbom-action` downloads an install script from a branch head and this job holds the OIDC identity the attestation store trusts. A generated document listing no packages fails the step rather than attesting an empty claim. A rehearsal runs the install, the scan and that guard against the two smoke images the daemon already holds, since it pushes nothing to scan; only the attest steps stay skipped.

   `make check-server-json-packages` (`scripts/validate-server-json-packages.sh`) gates all of this by downloading each declared artifact: it hashes each bundle, opens it as a zip, checks every path its manifest names, holds the declared bundles to serving darwin, win32 and linux exactly once each between them, checks each image tag resolves on its own registry and its ownership label matches, and rejects the fields the registry rejects. CI runs it on pushes to main only, since the bundles are about 75 MB to download in all. A bundle's SHA256 cannot come from GoReleaser's `checksums.txt`: the bundles are not GoReleaser artifacts, and appending them there would invalidate the cosign signature over it, `checksums.txt.sigstore.json`. The release workflow therefore builds the bundles **before** the stamp and passes the three per-OS ones as the stamper's third argument. `scripts/fetch-release-assets.sh` holds every bundle it fetches to its own build-provenance attestation, and its default patterns fetch the binaries by operating system (`gitlab-mcp-server-<os>-*`) precisely so that they leave the per-OS bundles, which a plain `gitlab-mcp-server-*` matches, to the jobs that ask for them.

   The npm entry declares the launcher (`@jmrp.io/gitlab-mcp-server`, `runtimeHint: "npx"`). The registry validates npm ownership through an `mcpName` field in the **published** `package.json`; the field is committed in `npm/gitlab-mcp-server/package.json`, and release.yml publishes npm **before** `mcp-publisher` runs, so the version the registry fetches always carries it. The gate's npm branch checks the identifier/mcpName/version lockstep against the committed launcher and warns (rather than fails) while the published version still predates `mcpName`. Like the OCI entry, the npm entry must not carry `fileSha256`; unlike it, a `version` is required and the stamp's step 2 bumps it with every release.

   The NuGet entry declares the tool (`registryType: "nuget"`, identifier `gitlab-mcp-server`, `runtimeHint: "dnx"`, `registryBaseUrl` exactly `https://api.nuget.org/v3/index.json`, which the registry demands for that type). Ownership is validated the way pypi's is: the registry reads the published version's README through the v3 feed's readme resource and looks for `mcp-name: io.github.jmrplens/gitlab-mcp-server` on a boundary (whitespace, a tag, or an HTML comment close; the token in `nuget/README.md` sits inside an HTML comment). The gate's nuget branch downloads the pointer package and checks that README, the tool manifest and `.mcp/server.json`, and notes rather than fails while nuget.org does not list the version, since the gate runs on main before the release that publishes it. The stamp's step 2 bumps its `version` with the others.

10. **NuGet publishes beside npm and PyPI, from the same published binaries, with no stored credential.** The distribution is the .NET 10 SDK's layout for a tool whose entry point is a native executable (tool manifest version 2): a pointer package `gitlab-mcp-server` (package types `DotnetTool` and `McpServer`, carrying `tools/net10.0/any/DotnetToolSettings.xml` that maps each runtime identifier to a package, the README with the ownership token, and an `.mcp/server.json` derived from `server.json` and stamped with the build's version, since the repository file is stamped only after the packages are pushed) plus six `gitlab-mcp-server.<rid>` packages (`linux-x64`, `linux-arm64`, `osx-x64`, `osx-arm64`, `win-x64`, `win-arm64`; package type `DotnetToolRidPackage`) that each carry the binary at `tools/any/<rid>/` as an `EntryPoint` with `Runner="executable"`, zip mode 0755. All seven carry the repository's `LICENSE` at their root beside the nuspec's MIT expression, a plain file rather than `<license type="file">`, since a nuspec declares one licence form or the other; the validator holds each copy to the repository's text byte for byte. Nothing in the packages is .NET code and no SDK is needed to pack: `scripts/build_nuget.py` (standard library only) writes the OPC container by hand, verifying every binary against the release's cosign-signed `checksums.txt` first. `scripts/validate_nuget.py` runs before every push, because a pushed NuGet version can be unlisted but never replaced: OPC skeleton, nuspec ids, versions and package types, the pointer's runtime map, the ownership token on the boundary the registry accepts, `.mcp/server.json`, the binary's magic number and machine per RID, the executable bit, a size floor and the digest recorded at pack time, an archive layout nuget.org's repository signature leaves intact (no entry with a data descriptor, nothing in zip64 form, no archive comment, no `.signature.p7s` already in it, any of which would leave the attested digest one no verifier recovers), then a real `dotnet tool install` from the packages and a `dotnet dnx` run, each driven through an MCP initialize handshake asserting stdout is pure JSON-RPC. `make validate-nuget NUGET_BINARIES=dist` runs all of it in the SDK container pinned by digest (10.0.403, because dnx's behaviour is an SDK property); the `nuget` job of `release.yml`, which fetches and verifies the release's binaries like the `npm` and `pypi` jobs, runs `make validate-nuget-local` after `actions/setup-dotnet` installs that same exact version. The job then attests all seven `.nupkg` files with `actions/attest-build-provenance` (`subject-path: nuget/dist/*.nupkg`, skipped in a rehearsal like every other attestation) **before** the NuGet login, so no package is pushed unattested. nuget.org adds its own repository signature (`.signature.p7s`) to every package it serves, so the served file's digest is never the attested one: a verifier removes that entry the way NuGet defines an unsigned package and looks up the SHA-256 of what is left, which is the attested file byte for byte. Up to 3.1.0 only the binaries inside the runtime packages were attested, through `checksums.txt`, which no NuGet verifier reads, since the package also carries the nuspec, the pointer's `DotnetToolSettings.xml` (what runs) and `.mcp/server.json`. `scripts/publish-nuget.sh` pushes the six runtime packages **before** the pointer that names them (the npm ordering rule, for the same reason) with `dotnet nuget push --skip-duplicate`, so a re-run lands on already-pushed versions without failing. CI authenticates through nuget.org **trusted publishing**: `NuGet/login` exchanges the job's OIDC token for a one-hour API key under the account-level policy recorded in `docs/development/repository-settings.md` (owner `jmrplens`, repository `gitlab-mcp-server`, workflow `release.yml`, environment `release`, scope "push new packages and package versions", glob `gitlab-mcp-server*`), so the first release creates the seven ids with no bootstrap token, unlike npm and PyPI; a rehearsal skips the login, since it runs in the `release-rehearsal` environment no policy names (issue 1322). `make publish-nuget NUGET_BINARIES=dist` with `NUGET_API_KEY` is the only tokened path, for an out-of-band push from a machine with the SDK. Two dnx facts the docs rely on, both verified against 10.0.400, again against 10.0.401, 10.0.402 and 10.0.403: dnx parses its own options anywhere on the line, so arguments for the server go after `--` (`dnx gitlab-mcp-server -- --version`); and it installs without asking when stdin is not a terminal, so a client configuration is `dnx gitlab-mcp-server` with configuration in `env` (Microsoft's docs show `--yes`, which both accept though their help does not list it). dnx also resolves the version against the feed on every launch, cached or not, and `@latest` is not a NuGet version. `scripts/verify_published_packages.py` reads the six runtime packages back from the flat container after the push and compares each binary with the signed `checksums.txt`, and, handed the seven digests the nuget job attested (its `nupkg_sha256` output, through `--nuget-digests`), removes nuget.org's repository signature from all seven packages the way NuGet defines an unsigned package and holds each to its attested digest, which is the lookup a verifier makes and needs neither `gh` nor a new permission; the registry's nuget validator answers "wait for validation to complete" while nuget.org is still validating a fresh push, which the mcp-registry job's retry loop treats as lag.
