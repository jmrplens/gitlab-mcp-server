# Localization

**How the texts a person reads directly are localized**: which texts count, the `internal/i18n` API, how to add a text or a language, the Spanish glossary, the tests and gates that hold a translation to its source, and what stays English on purpose.

> **Diátaxis type**: Explanation & How-to · **Audience**: 🛠️ Contributors & maintainers

The decision is [ADR-0027](adr/adr-0027-person-facing-text-is-localized-from-a-compiled-catalog.md), the setting is `GITLAB_MCP_LANGUAGE` in [Environment Variables and Flags](configuration.md), and what a user sees is on the site under [In which language are the questions asked?](https://docs.jmrp.io/gitlab-mcp-server/capabilities/elicitation/#in-which-language-are-the-questions-asked) ([issue 1547](https://github.com/jmrplens/gitlab-mcp-server/issues/1547)).

---

## Which texts are localized

A text is localized when a client puts it in front of a person **without the model reading it first**. That is three channels and nothing else:

| Channel                                          | Texts                                                                                                                                                                                                                                                                                                           |
| ------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `elicitation/create`, or `inputRequests` on MRTR | The questions of the four `interactive.*` flows and their consent summaries; the confirmation of a destructive action on the meta and individual surfaces (`toolutil.ConfirmDestructiveAction`); the questions of the pull mirror overwrite guard (`projects`) and the work item list clear guard (`workitems`) |
| `requestedSchema` of the same requests           | The `title` of each property (`Confirm`, `Selection`, `Selections`, and the title a text or number field is given), and its `description`, which repeats the question                                                                                                                                           |
| `notifications/progress`                         | The progress messages of the four flows, the file upload and download readers (`toolutil`), the pipeline and job waits, the group and project transfers, and the package publish                                                                                                                                |

Everything else stays English, in four groups, each for its own reason:

- **What the model reads**: tool, parameter and schema descriptions, results, hints, refusals (the answer to a client that cannot elicit and the refusal of a destructive call without `confirm`), cancellation results, `instructions` and the bodies of `prompts/get`. The model answers the person in the person's language whatever it reads, so translating its input changes its behavior and gains nothing; SEP-2792 leaves that text a MAY with the same warning.
- **The listed catalog**: `tools/list`, `prompts/list`, `resources/list` and `resources/templates/list`, the titles in them included, and the server cards and `serverInfo`. See [Why the listings stay English](#why-the-listings-stay-english).
- **What an operator reads**: startup errors, the `--help` text and every log line. They are searched for in the documentation and in issues, and `GITLAB_MCP_LANGUAGE` is itself read by the load that can fail.
- **Errors a client shows as they are**, which the issue named: a JSON-RPC `Error.message` (`toolutil.InvalidParams`, the HTTP gate's refusals and their `WWW-Authenticate` descriptions, `capguard`, the body and line limits) and a tool result with `isError`. A client logs the first and forwards it to the model, several are written before a request context with a language exists, and SEP-2792 leaves `Error.message` a MAY; the second is read by the model. If `Error.message` is ever translated, it will be per request under SEP-2792, with `contentLanguage` in `error.data`, never under this setting.

Completions return values only (paths, branches, IDs), so there is nothing to translate there.

Some texts reach both audiences: a destructive confirmation and the two guards' questions are asked of the person and, when the client cannot ask, become the refusal the model reads. They are built as an unrendered `i18n.Message` and rendered twice: `Text(ctx)` for the person, `English()` for the refusal and the log.

## The package

`internal/i18n` uses the standard library alone, because `internal/config` reads the setting through it and does not depend on the MCP SDK.

| Symbol                                                          | What it is                                                                                                                                                                                                                                              |
| --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Language`, `English`, `Spanish`, `Default`                     | A primary language subtag in lower case; `Default` is `English`                                                                                                                                                                                         |
| `Supported()`, `Parse(value)`                                   | The languages a catalog exists for, and the reader of the setting: blank is `Default`, a BCP 47 tag is read without regard to case with its subtags after the language dropped, anything else is an error naming the accepted values                    |
| `WithLanguage(ctx, lang)`, `FromContext(ctx)`, `Requested(ctx)` | The request's language on its context. `FromContext` answers `English` for a context that carries none or one no catalog holds, so a path the middleware does not cover is served what it was served before                                             |
| `Key`                                                           | A typed key, declared only as a constant in `keys.go` with a stable dotted value (`interactive.issue_create.prompt.title` is `InteractiveIssueCreatePromptTitle`)                                                                                       |
| `S`, `N`, `M`, `L`                                              | The arguments that fill a `{name}` placeholder: a text already escaped for where it lands, an integer in base ten without grouping, another catalog message in the same language, and a list joined with the language's conjunction like `strings.Join` |
| `New(key, args...)`, `Concat(parts...)`                         | A `Message`, unrendered, and a message whose parts render one after another; a consent summary is a `Concat` of its base row and its optional rows, each its own key starting with a line break                                                         |
| `Message.In(lang)`, `Message.Text(ctx)`, `Message.English()`    | Render in a language, in the request's, or in English for the model and the logs. Substitution is one pass (`strings.NewReplacer`), so a value carrying `{title}` is inserted as written                                                                |
| `Text`, `T(ctx, key, args...)`                                  | The rendered type every person-facing sink takes, which only this package makes non-empty, and `New(...).Text(ctx)` in one call                                                                                                                         |
| `Verbatim(s)`                                                   | A `Text` without a catalog entry, for tests only                                                                                                                                                                                                        |
| `Templates(lang)`, `EnglishTemplate(key)`                       | A copy of one catalog for the external character test, and the English template the audits judge a call by                                                                                                                                              |

A lookup falls back to English when a catalog lacks a key and to the key itself when English lacks it too, so a render is never empty; the tests make both impossible in a build.

The sinks take the type, so a literal at a call site does not compile: `elicitation.Flow` and `elicitation.Client` (`Confirm`, `PromptText`, `SelectOne`, `SelectMulti`, `SelectOneInt`, `PromptNumber`, `GatherData`, `ElicitURL`) take `message i18n.Text`, and `PromptText` and `PromptNumber` take an `elicitation.Field{Name, Title}` whose zero `Title` means its `Name`; `progress.Tracker.Update`, `Step` and `Done` take `i18n.Text`, as do `waitpoll.UntilOptions.Message` and `waitpoll.Options.ProgressMessage`; `toolutil.ConfirmDestructiveAction` and `toolutil.ConfirmAction` take the `i18n.Message` unrendered. The language reaches them through `cmd/server.languageMiddleware`, a receiving middleware `newServerShell` installs on every server, which puts the process's language on each request's context.

## Adding a text

1. Declare the key in `internal/i18n/keys.go`, in the block of its family, with a doc comment: a dotted value (`<family>.<flow>.<kind>.<name>`) and the CamelCase name of that value.
2. Write the English template in `catalog_en.go`. English is the source: a new text is written here first, with `{name}` placeholders whose names are lower-case letters, digits and underscores, and braces used for nothing else. A text that replaces a literal the server already sent keeps that literal byte for byte; add its row to `frozenEnglishRows` in `catalog_en_test.go`, which every English entry needs.
3. Write the Spanish template in `catalog_es.go` in the same change, with the same placeholders, the same number of line breaks, `**`, backticks and `->`, and the glossary below.
4. Render it at the call site with `i18n.T(ctx, key, i18n.S("name", value))`, or `i18n.New` where the message is rendered later. Write every argument inline with a literal name: an `Arg` built elsewhere or a list expanded with `args...` cannot be tied to its placeholder, and `make check-i18n` refuses it. A GitLab or model value that lands in Markdown is escaped first, as `toolutil.EscapeConsentValue` does for a summary row.
5. Run `go test ./internal/i18n/`, then `make check-i18n` and `make check-md-escaping`.

Where the person-facing text sits beside text the model reads, only the first goes to the catalog: the step label in a flow error, the cancellation result and the refusal stay English literals.

## Adding a language

1. Add the constant beside `English` and `Spanish` in `language.go` and append it to `supported`, which is the order a refusal names the languages in.
2. Add `catalog_<lang>.go` with exactly the English keys, each with the same placeholders and Markdown structure, and register it in `catalogs` in `catalog.go`. The completeness and parity tests fail until every key is there.
3. Add the language's characters to `beyondASCII` in `catalog_characters_test.go`; a language with no entry has no policy and its catalog is refused.
4. Add its catalog file and its test to the `misspell` exclusion of `.golangci.yml`, a path `internal/i18n/catalog_<lang>(_test)?\.go` the way `catalog_es(_test)?\.go` is excluded, since the glossary test is written in that language too; the `dupl` exclusion already covers every `catalog_[a-z]+.go`.
5. Write a glossary test like `TestSpanishCatalog_FollowsItsGlossary`, taken from the site's pages in that language if it has them, and a composition test like `TestSpanishCatalog_RendersEachCompositionInSpanish`.
6. Update the setting's accepted values wherever they are listed: `server.json`, the `--language` help in `cmd/server`, `docs/development/configuration.md`, the environment table of `CLAUDE.md` and of `.github/copilot-instructions.md`, the row in `llms-install.md`, and the site's environment, CLI, configuration, HTTP server and elicitation pages in both languages.

A language added to the catalog is a language the language policy allows in a Go file: the file and the tests that compare against it are named in the first paragraph of `CLAUDE.md`, in `CONTRIBUTING.md`, `AGENTS.md`, `.github/copilot-instructions.md` and `.github/agents/documentation-writer.agent.md`, the way `catalog_es.go` is.

## The Spanish glossary

The translation follows the Spanish half of the documentation site, which a person reads beside these texts:

- **Address**: `tú` and the imperative (`Escribe`, `Selecciona`), never `usted`.
- **GitLab nouns kept in English**, with the gender the site gives them: `el issue`, `el merge request` or `el MR`, `la release`, `el tag`, `el pipeline`, `el job`, `el work item`, `el README`, `squash`, `merge`, `mirror`, `commit`.
- **Translated terms**: labels are `etiquetas`, source branch `rama origen`, target branch `rama destino`, default branch `rama predeterminada`, visibility `visibilidad`, confidential `confidencial`, polling `sondeo`, file `archivo`, upload `subida`, diverged branches `ramas divergentes`, assignees `asignados`; "or leave empty" is `o deja el campo vacío`.
- **Field titles** are words (`Título`, `Rama origen`) where English shows the property key. The key itself is never translated.
- **Typography**: three ASCII dots for an ellipsis, no dash, no typographic quotes, no semicolon.
- **Plurals**: there is no plural engine. The one count that would need one is written without inflection: `todos los asignados actuales ({count})`.

`TestSpanishCatalog_FollowsItsGlossary` refuses the variants the catalog decided against (`escriba`, `seleccione`, `incidencia`, `rama de destino`, `fichero`, `usted` and the rest).

## Tests and gates

The catalog's own tests, in `internal/i18n`:

| Test                                                                                                                         | Holds                                                                                                                                                                                                                                                                                 |
| ---------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `TestCatalogs_EverySupportedLanguageHasOne`, `TestCatalogs_EachHoldsExactlyTheEnglishKeys`, `TestCatalogs_NoTemplateIsEmpty` | Completeness: every supported language has a catalog of exactly the English keys, none empty                                                                                                                                                                                          |
| `TestCatalogs_BracesAreOnlyPlaceholders`, `TestCatalogs_EachTranslationFillsTheEnglishPlaceholders`                          | The placeholder grammar, and the same set of placeholders per key in every language                                                                                                                                                                                                   |
| `TestCatalogs_EachTranslationKeepsTheEnglishStructure`                                                                       | The same line breaks, `**`, backticks and `->` per key, so a translation lands in the Markdown constructions the escaping audit judged in English                                                                                                                                     |
| `TestEnglishCatalog_MatchesTheLiteralsItReplaced`, `TestEnglishCatalog_EveryEntryHasAFrozenRow`                              | English is what the server sent before the catalog, byte for byte, for every entry                                                                                                                                                                                                    |
| `TestCatalogs_EachTemplateKeepsItsLanguagesCharacters` (external, `package i18n_test`)                                       | English is printable ASCII and the line break with no semicolon, by the predicate `cmd/audit_gateway_chars` uses (`gatewaycompat.OffendingRune`); Spanish adds `á é í ó ú ü ñ`, their capitals, `¿` and `¡`, and neither carries a dash, an ellipsis character or a typographic quote |
| `TestSpanishCatalog_*`                                                                                                       | Each way a text is composed renders the reviewed Spanish and still renders English for the model, and the glossary                                                                                                                                                                    |
| `TestMessageIn_*`, `TestConcat_*`, `TestParse_*`, `TestFromContext_*`                                                        | Rendering in one pass, nested messages and lists in the asked language, the fallbacks, and the reader of the setting                                                                                                                                                                  |

The character test is external because `internal/gatewaycompat` imports `internal/config`, which imports `internal/i18n`: an internal test importing it would be an import cycle.

Beyond the package: `cmd/server` holds that every method runs under the configured language and that `tools/list` on the three surfaces, `prompts/list`, `resources/list` and `resources/templates/list` are identical under no setting, `en` and `es` (`TestCreateServer_UnsetEnglishAndSpanish_ListTheSameCatalog`), and that the model is still answered in English under `es`; `internal/config` holds that a Spanish machine locale (`LANGUAGE=es_ES:es`, `LANG`, `LC_ALL`, `LC_MESSAGES`) loads `en` and warns about nothing (`TestLoad_TheMachinesLocale_IsNeverTheLanguage`, `TestGetenv_Language_IsNeverGettextsVariable`); and the transport modules drive the real binary, `test/e2e/stdio/language_test.go` and `test/e2e/http/language_test.go`, through the first question of a wizard in each language, the refusal of `fr` before anything is served, the flag beating the variable, and the listings that do not change.

Two gates read the call sites:

- **`make check-i18n`** (`cmd/audit_i18n`, step 33 of `make analyze` and a step of CI's `generated` job): a render fills exactly its English template's placeholders through inline `S`, `N`, `M` or `L` calls with literal names (I1), names its key with a key constant of the catalog and converts nothing to `Key` outside it (I2), every English entry is used from a non-test file outside the catalog files and every used key exists (I3), `i18n.Verbatim` appears only in tests (I4), and no `i18n.Text` or `i18n.Message` literal is written outside the package (I5). [Command-Line Utilities](cmd-utilities.md#audit_i18n) has every rule's detail.
- **`make check-md-escaping`** (`cmd/audit_md_escaping`): a render is a sink whose template is its key's English one, each placeholder a hole filled by the value its `S` names, so a GitLab-authored value that reaches a summary row unescaped is found in the catalog as it was in the `fmt.Sprintf` the catalog replaced, and the `//gitlab:allow-card` directives of the four flows still answer.

## Why the listings stay English

The titles in `tools/list` are on SEP-2792's SHOULD list, and a person sees some of them, so leaving them English is a decision rather than an omission:

1. **They are what a strict gateway validates.** The listed catalog is pure ASCII prose with no semicolon, which `make check-gateway-chars` gates, and Spanish does not fit that policy without dropping its accents.
2. **The prompt catalog is cached as public** (`internal/cachehints`), and a listing that varied by language would need the language as a cache key, which only SEP-2792 defines.
3. **The model reads them too**, and the generated reference, the token footprint and the surface-quality audit compare the listing between deployments; a listing that changed with an operator setting would break that contract for text no person needs translated.

Nothing translated reaches those four listings, so `GITLAB_MCP_DESCRIPTION_SUBSTITUTIONS`, which rewrites only them, never sees a translated text. Extending it to elicitation would be worse than useless: a summary embeds GitLab values, and a substitution meant for descriptions would corrupt them in front of the person deciding. This decision is revisited with SEP-2792 in issue 1013.

## The setting, and the client's own language

`GITLAB_MCP_LANGUAGE` (flag `--language`, both transports) is read once by `config.LanguageFromEnv`, in `config.Load` for stdio and in the HTTP overlay for HTTP mode, and refuses the start on a language without a catalog. It is on `prefixedNames` because the bare `LANGUAGE` is GNU gettext's and Linux desktops export it, and it is not on `hadOldSpelling`, so that bare name is never reported. The machine's locale is never read, and neither is an HTTP `Accept-Language` header, which Node clients send as `*` when nobody sets it. The language is per process: it is in `ServerConfig.Language` and in `serverShapeKey` as the effective language, and every credential of an HTTP deployment is served the same one. It has no tenant register row, since it is presentation per deployment and decides nothing about who a caller is or what it may hold.

**SEP-2792** ([modelcontextprotocol#2792](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2792)) is where a client's own language will come from: `params._meta["io.modelcontextprotocol/acceptLanguage"]` on each request, with `Accept-Language` grammar, answered with `_meta["io.modelcontextprotocol/contentLanguage"]`. The core maintainers accepted it on 2026-10-17, and it was not merged, not in a published revision and not in any SDK when this was written; issue 1013 holds the trigger at the merge. The change is one place, `languageMiddleware`:

1. Read the request's `acceptLanguage` from its `_meta`; a malformed value is an absent preference, never an error.
2. Look it up among `i18n.Supported()` the RFC 4647 way, falling back to `GITLAB_MCP_LANGUAGE`, which becomes the server-defined default.
3. Put the result on the request's context, as today, and write `contentLanguage` in the `_meta` of the result and of the progress notifications it localized, and `Content-Language` on an HTTP JSON answer.

Nothing is kept on the session, which the proposal forbids: on MRTR each round uses its own request's language. Because a value the client declares then changes the output, that change adds a tenant register row, the way `IDN-013` records the response profile chosen from a session's `clientInfo`. Whether the listing titles follow is the separate decision above.

**The GitLab profile language** is the one per-user signal available today: `GET /user`, which admission already sends, answers `API::Entities::UserPublic` with `preferred_language`, recorded in `docs/development/gitlab-api-live.json`. client-go's `User` does not model the field, so reading it would take the captured response ([ADR-0021](adr/adr-0021-captured-response-for-fields-the-sdk-does-not-model.md)), a language per pool entry in HTTP mode, and a register row, and none of the three is needed to serve Spanish. It is left for an issue of its own after this work, should a value such as `gitlab` that follows the profile be wanted.
