This page says where the project is going through December 2027: what it intends to do, and what it has decided not to do. It is a statement of direction rather than a schedule or a promise. Work lands when it is ready, the open [milestone](https://github.com/jmrplens/gitlab-mcp-server/milestones) on GitHub holds the issues planned for the next release, and the maintainer sets the priorities as [GOVERNANCE.md](https://github.com/jmrplens/gitlab-mcp-server/blob/main/GOVERNANCE.md) describes.

Last reviewed on 2026-10-31. The page is reviewed at least once a year, and whenever a major release changes direction.

## What the project intends to do

### Keep up with every GitLab release

GitLab ships a release every month. For each one, the project records again what a running GitLab sends (its REST answers, the permissions a fine-grained token needs per action, its GraphQL schema), runs the end-to-end suite against it, and follows what changed: new endpoints, parameters and response fields become actions, inputs and outputs, released as the [versioning policy](/gitlab-mcp-server/changelog/#what-the-version-number-means) says. Re-recording on GitLab 19.6 is [issue 1492](https://github.com/jmrplens/gitlab-mcp-server/issues/1492).

The aim stays the same: one action for every operation GitLab's REST and GraphQL APIs offer, on every tier from Free to Ultimate and on GitLab.com, with the parameters GitLab accepts and the fields it sends, and an audit that holds the catalog to it.

### Move with client-go and the MCP specification

The server's major version tracks the major of [client-go](https://gitlab.com/gitlab-org/api/client-go), the GitLab API client it is built on. When client-go publishes its next major, the server moves to its own next major in the same dependency update, and every other dependency update ships as a minor or a patch release. client-go sets that date, so this page gives none.

Each revision of the [MCP specification](https://modelcontextprotocol.io/) is adopted as the [MCP Go SDK](https://github.com/modelcontextprotocol/go-sdk) supports it. A proposal that would change what the server sends, such as letting each request name the language its user reads in ([issue 1013](https://github.com/jmrplens/gitlab-mcp-server/issues/1013)), is watched until it is merged into the specification and implemented then. Until then the language is the operator's, one for the whole process: since 3.4.0, `GITLAB_MCP_LANGUAGE=es` serves [the texts a person reads directly](/gitlab-mcp-server/capabilities/elicitation/#in-which-language-are-the-questions-asked), such as the questions of the guided flows and the progress messages, in Spanish.

### Close what a fine-grained token cannot reach

A [fine-grained token](/gitlab-mcp-server/operations/fine-grained-tokens/) is judged action by action from its grant. GitLab still leaves part of its API outside every grant, and the project follows as it extends them: serving an action over REST where a fine-grained token cannot reach its GraphQL ([issue 1054](https://github.com/jmrplens/gitlab-mcp-server/issues/1054)), reading the grant from the token's own answer where GitLab sends it there ([issue 1400](https://github.com/jmrplens/gitlab-mcp-server/issues/1400)), and letting the actions that create tokens send the fine-grained permissions GitLab accepts ([issue 1115](https://github.com/jmrplens/gitlab-mcp-server/issues/1115)).

### Hold every limit of a shared deployment to one rule

In [HTTP mode](/gitlab-mcp-server/operations/http-server/) one process serves many callers, and what each may hold, spend or be told is a limit. Limits are decided in one register that the server's layers read. Since 3.4.0 every limit has one documented default, a stated meaning for zero and one rule for what happens at capacity ([issue 958](https://github.com/jmrplens/gitlab-mcp-server/issues/958)), and every limit an operator sets is read under the configuration's own naming and parsing rule ([issue 957](https://github.com/jmrplens/gitlab-mcp-server/issues/957)). A limit added later is written as a row of the register, whose checks hold the row to the same rules.

### Finish the documentation and the tooling

The documentation is being reorganized around five end-to-end paths, from a first local run to an HTTP deployment behind a reverse proxy ([issue 529](https://github.com/jmrplens/gitlab-mcp-server/issues/529)), in English and Spanish together. The repository's own tooling is moving into Go commands, so every check a contributor runs works the same on Linux, macOS and Windows ([issue 1114](https://github.com/jmrplens/gitlab-mcp-server/issues/1114)).

## What the project will not do

### Receive webhooks

The server runs no webhook receiver, in stdio mode or in HTTP mode. [Resource subscriptions](/gitlab-mcp-server/capabilities/subscriptions/) are honored by polling GitLab with the subscriber's own token. Receiving deliveries would give the server its first unauthenticated inbound endpoint and a secret to keep across restarts, would make subscribing create a hook in GitLab as a side effect that read-only and safe mode never see, and would still need a read through each subscriber's own token, since a delivery carries none. The decision is [ADR-0016](https://github.com/jmrplens/gitlab-mcp-server/blob/main/docs/development/adr/adr-0016-no-webhook-ingestion.md).

### Take change notifications from other event sources

The Events API, GraphQL subscriptions over ActionCable and conditional requests were surveyed against running instances and declined. The Events API records nothing for pipelines and jobs, GraphQL subscriptions are undocumented for API consumers and lose what happens during a disconnect, and a conditional request costs as much of GitLab's rate limit as a full read. Polling stays the only source. [ADR-0017](https://github.com/jmrplens/gitlab-mcp-server/blob/main/docs/development/adr/adr-0017-pull-safe-event-sources-surveyed.md) records the survey and what would reopen it, such as GitLab documenting its GraphQL subscriptions for API consumers.

### Update itself

The server does not check for updates and never replaces its own binary. The self-updater was removed in 3.0.0. A new release is installed through the channel that installed the server (npm, PyPI, NuGet, Homebrew, winget, the container image or the Claude Desktop extension) or downloaded again from the Releases page, as the [installation guide](/gitlab-mcp-server/install/overview/) describes.

## How this roadmap changes

The maintainer updates this page in a pull request when the direction changes, and its Spanish twin in the same pull request. Reversing anything under "What the project will not do" takes an architecture decision record that gives the reason, and that supersedes ADR-0016 or ADR-0017 where it reverses one of them.
