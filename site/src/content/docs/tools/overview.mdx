GitLab MCP Server exposes GitLab operations as MCP tools that AI assistants can invoke directly. It offers **three tool modes**: dynamic, meta-tool, and individual. All three reach the same GitLab API surface. They differ only in packaging, so the choice trades context cost against tool-list granularity — never capability.

Every mode is projected from one **canonical action catalog**. That gives all three identical handlers, typed schemas, and safety rules, apart from how a destructive call is confirmed. Otherwise only the presentation changes. Dynamic mode searches and executes canonical `domain.action` IDs. Meta-tool mode groups actions by domain. Individual mode registers one tool per operation.

## Which tool mode should I use?

**Dynamic mode is the default, and the right choice for most assistants.** It keeps two tools in the model's context and still reaches every GitLab operation. Choose meta-tool mode when your client works better with a fixed, domain-level tool list. Choose individual mode only when a client needs every operation enumerated up front.

| Mode                    | Public tools exposed                                                                                                     | Best for                                      | Relative token cost |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------- | ------------------- |
| **Dynamic** _(default)_ | 2: `gitlab_find_action`, `gitlab_execute_action`                                                                         | Most assistants; lowest context overhead      | Lowest              |
| **Meta-tool**           | {stats.meta.base} on Free/CE, {stats.meta.premium} on self-managed Premium, up to {stats.meta.gitlab_com} on Ultimate    | A fixed, discoverable, domain-level tool list | Medium              |
| **Individual**          | {stats.tools.free} on Free/CE, {stats.tools.premium} on self-managed Premium, up to {stats.tools.gitlab_com} on Ultimate | Clients that need every operation pre-listed  | Highest             |

Set the mode with the `GITLAB_MCP_TOOL_SURFACE` environment variable (`dynamic`, `meta`, or `individual`). Dynamic mode is used when `GITLAB_MCP_TOOL_SURFACE` is unset.

## Operating modes

### How does individual mode work?

Individual mode registers **one MCP tool per GitLab operation**: **{stats.tools.free} tools** on Free/CE, **{stats.tools.premium} tools** on self-managed Premium, **{stats.tools.ultimate_self_managed} tools** on self-managed Ultimate, or **{stats.tools.gitlab_com} tools** on GitLab.com Ultimate, where Orbit is available. This gives an AI assistant maximum granularity (every operation is a distinct, individually described tool) at the cost of significant context tokens spent listing and disambiguating tools during discovery.

### How does meta-tool mode work?

Meta-tool mode (`GITLAB_MCP_TOOL_SURFACE=meta`) consolidates related operations into **domain-level meta-tools**. Each meta-tool accepts an `action` parameter that routes to the appropriate handler, reducing the tool count to **{stats.meta.base} meta-tools on Free/CE**, **{stats.meta.premium} on self-managed Premium**, **{stats.meta.self_managed_enterprise} on self-managed Ultimate**, or **{stats.meta.gitlab_com} on GitLab.com Ultimate**, where Orbit is available. This dramatically improves token efficiency over individual mode while keeping a fixed, browsable tool list.

```json
{
  "tool": "gitlab_issue",
  "arguments": {
    "action": "create",
    "params": {
      "project_id": "my-group/my-project",
      "title": "Fix login redirect",
      "description": "Users are redirected to 404 after login",
      "labels": ["bug", "priority::high"]
    }
  }
}
```

### How does the dynamic toolset work?

Dynamic mode (`GITLAB_MCP_TOOL_SURFACE=dynamic`) is the low-token default. It exposes only two public tools — `gitlab_find_action` and `gitlab_execute_action` (the singular `gitlab_execute_action` name is intentional) — while keeping every GitLab action reachable through the canonical catalog. The assistant first finds an action and its exact schema, then executes the canonical `domain.action` ID.

```mermaid
flowchart LR
	A[Find action and schema] --> B[Execute domain.action]
	B --> C[Existing GitLab handler]
```

Because all three modes share the canonical action catalog, **the safety rules come from one place**: read-only filtering, safe mode, token-scope filtering, the destructive classification, schemas, and result formatting are the same on every surface. How a destructive call is confirmed differs in one way: the dynamic surface never prompts, so it needs `confirm: true` on every one unless `GITLAB_MCP_YOLO_MODE` skips the confirmation, as it does on every surface, which [Destructive actions](/gitlab-mcp-server/operations/security/#destructive-actions) explains.

## Tool naming convention

All tools follow a consistent naming pattern:

- **Individual tools**: the prevailing form is `gitlab_{domain}_{action}` (e.g., `gitlab_issue_create`, `gitlab_project_list`), domain first; a legacy set is verb first instead (`gitlab_list_issue_discussions`, `gitlab_add_ssh_key`), and each name is declared in the action's catalog spec rather than derived, so read it from `gitlab://tools` instead of inferring it
- **Meta-tools**: `gitlab_{domain}` (e.g., `gitlab_issue`, `gitlab_project`)
- **Dynamic actions**: canonical `domain.action` IDs executed through `gitlab_execute_action` (e.g., `issue.create`, `merge_request.list`)

Eleven more arrive with Ultimate, for {stats.meta.self_managed_enterprise} on a self-managed instance:

`gitlab_attestation` (2), `gitlab_compliance_policy` (2), `gitlab_dependency` (4), `gitlab_dora_metrics` (2), `gitlab_external_status_check` (8), `gitlab_member_role` (6), `gitlab_security_attribute` (5), `gitlab_security_category` (3), `gitlab_security_finding` (1), `gitlab_security_scan_profile` (3), `gitlab_vulnerability` (8)

On GitLab.com with a Premium or Ultimate tier, the catalog also registers `gitlab_orbit` with six read-only Knowledge Graph actions: `status`, `schema`, `tools`, `dsl`, `query`, and `graph_status`. That makes {stats.meta.gitlab_com} meta-tools on GitLab.com Ultimate.

A group that needs `admin_mode` is left out for a token without that scope ([Scope-based tool filtering](/gitlab-mcp-server/operations/security/#scope-based-tool-filtering)). What the two tiers add to the base dispatchers is listed under [Enterprise mode](/gitlab-mcp-server/tools/meta-tools/#enterprise-mode).

:::note
Enterprise tools require a GitLab Premium or Ultimate license on your instance. Forcing the Enterprise/Premium catalog on a Community Edition instance will register the tools, but their API calls fail: Community Edition does not serve those endpoints and answers 404, and an unlicensed Enterprise Edition refuses them.
:::
