Lo que necesita un token de acceso personal de grano fino para cada acción que ofrece este servidor, tal como lo declara GitLab 19.4.1. Las peticiones salen de los handlers ([`docs/development/action-requests.json`](https://github.com/jmrplens/gitlab-mcp-server/blob/main/docs/development/action-requests.json)) y los permisos, de la autorización que GitLab registra para cada ruta, tipo GraphQL y mutación ([`docs/development/gitlab-api-live.json`](https://github.com/jmrplens/gitlab-mcp-server/blob/main/docs/development/gitlab-api-live.json)). Los permisos se nombran con las palabras del propio GitLab, tal como los muestra su página de creación de tokens, con el ámbito en que se concede cada uno: un token cuya concesión cubre todos los permisos de una línea, en uno de los ámbitos nombrados, puede ejecutar la acción. Cuando una acción tiene varias líneas, basta con cualquiera de ellas, porque la acción envía una petición distinta según su entrada. Cuando una de esas peticiones es una que ningún token de grano fino supera, la entrada lo dice después de lo que necesitan las demás: la acción se ejecuta, salvo con una entrada que le haga enviar esa petición.

Una acción para la que GitLab no declara nada no se puede ejecutar con un token de grano fino en esta versión, diga lo que diga la concesión: el motivo está en la segunda columna, y la salida es un token de acceso personal clásico. **Se sirve vacío** nombra una parte de la respuesta que GitLab omite para un token de grano fino mientras sirve el resto: siempre, o salvo que la concesión tenga también lo que figura tras ella. Cada parte se escribe como la selección GraphQL que llega a ella desde el campo que pide la acción.

Los tokens de acceso personal clásicos no se juzgan aquí: sus scopes deciden lo que pueden hacer, como hasta ahora. El mismo requisito se sirve para cada acción en el bloque `fine_grained` de su detalle `gitlab://tools/{id}`. [Tokens de grano fino](/gitlab-mcp-server/es/operations/fine-grained-tokens/) explica cómo crear un token, qué necesita de él el servidor al arrancar y cómo se lee un rechazo.
