Más allá de las herramientas, GitLab MCP Server expone **recursos** y **prompts** — dos primitivas MCP adicionales que proporcionan contexto y plantillas reutilizables a los asistentes de IA. Las herramientas ejecutan acciones; los recursos aportan contexto de solo lectura bajo demanda; los prompts empaquetan un flujo de recopilación de datos en una única plantilla reutilizable.

## ¿Qué son los recursos MCP?

Los recursos MCP proporcionan **datos de contexto de solo lectura** que los clientes pueden solicitar en cualquier momento sin invocar una herramienta. Los recursos son útiles para aportar información de fondo —los metadatos de un proyecto, sus miembros, etiquetas o el último pipeline— que ayuda al LLM a tomar mejores decisiones antes de actuar.

El servidor expone **{stats.resources} recursos** en varias categorías:

:::note
MCP lista por separado los recursos fijos y las plantillas de URI. En modo `full`, los clientes que solo inspeccionan `resources/list` ven 8 URIs fijas: usuario actual, grupos, el manifiesto de herramientas y 5 guías de flujo. Las 37 entradas restantes son plantillas de URI devueltas por `resources/templates/list` y se leen sustituyendo IDs de proyecto, grupo, issue, MR u otros valores en tiempo de ejecución.
:::

Los recursos de datos de GitLab y los dos recursos del manifiesto de herramientas devuelven `application/json`; las cinco guías de flujo de trabajo devuelven `text/markdown`. La columna **Nombre** es el nombre con el que aparece cada recurso en `resources/list` o en `resources/templates/list`, y cada descripción indica lo que devuelve el manejador del servidor.

### Recursos estáticos (3)

| Recurso                 | Nombre          | Descripción                                                                                                                                                            |
| ----------------------- | --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `gitlab://user/current` | `current_user`  | Perfil del usuario autenticado: nombre de usuario, nombre visible, email, estado (activo/bloqueado), si es administrador y URL web                                     |
| `gitlab://groups`       | `groups`        | Grupos a los que puede acceder el usuario autenticado, hasta una página (100): ID, nombre, ruta completa, descripción, visibilidad y URL web de cada uno               |
| `gitlab://tools`        | `tool_manifest` | Manifiesto dependiente de superficie de las herramientas y acciones ejecutables que ofrece esta instancia; `gitlab://tools/{id}` da la forma de llamada de una entrada |

### Plantilla de recurso de manifiesto de herramientas (1)

| Recurso               | Nombre        | Descripción                                                                        |
| --------------------- | ------------- | ---------------------------------------------------------------------------------- |
| `gitlab://tools/{id}` | `tool_detail` | Forma de llamada aceptada y schema de entrada para una entrada de `gitlab://tools` |

Usa el manifiesto de herramientas cuando un cliente necesite la forma exacta de los parámetros de una entrada en cualquier superficie sin expandir todos los schemas en `tools/list`: IDs canónicos `domain.action` en la superficie dinámica predeterminada, entradas `gitlab_<domain>.<action>` con `GITLAB_MCP_TOOL_SURFACE=meta` y nombres de herramienta con `GITLAB_MCP_TOOL_SURFACE=individual`.

1. Lee `gitlab://tools` para obtener la superficie activa, herramientas visibles y entradas ejecutables.
2. Sustituye `{id}` en `gitlab://tools/{id}` para leer el JSON Schema y la forma de llamada de esa entrada.
3. Llama a la herramienta que indica la forma `call` devuelta: `gitlab_execute_action` con `{ "action": "merge_request.create", "params": { ... } }` en la superficie dinámica, o la meta-herramienta con `{ "action": "create", "params": { ... } }` cuando `GITLAB_MCP_TOOL_SURFACE=meta`.

Por ejemplo, `gitlab://tools/merge_request.create` devuelve el schema de parámetros y la forma de llamada de `merge_request.create` en la superficie predeterminada; con `GITLAB_MCP_TOOL_SURFACE=meta` la misma acción es `gitlab://tools/gitlab_merge_request.create`. Estos recursos de manifiesto están disponibles con `GITLAB_MCP_CAPABILITY_SURFACE=full` o `minimal`, sin importar el modo de `GITLAB_MCP_META_PARAM_SCHEMA`. `gitlab_find_action` devuelve el mismo schema inline en la superficie dinámica, con descubrimiento ordenado además.

El ID canónico de una acción se resuelve en **todas** las superficies, no solo en la dinámica, donde es la clave de la entrada: `gitlab://tools/project.get` también responde con `GITLAB_MCP_TOOL_SURFACE=meta` y con `GITLAB_MCP_TOOL_SURFACE=individual`, y la entrada que devuelve nombra la llamada que esa superficie acepta de verdad (`gitlab_project.get` en meta, la herramienta `gitlab_project_get` en individual). Así, un ID sacado de una pista, de un enlace cruzado o de esta documentación se puede consultar sea cual sea la superficie servida.

#### Qué contiene el detalle de una entrada

| Campo                                       | Qué contiene                                                                                                                                                                                                                                                                                                                                                       |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `id`, `kind`, `tool`, `action`              | La clave de la entrada en esta superficie; su tipo (`dynamic_action`, `meta_action`, `individual_tool` o `visible_tool`); la herramienta a la que llamar; y, en las superficies dinámica y meta, la acción que hay que nombrar                                                                                                                                     |
| `title`, `description`, `domain`            | Qué hace la entrada y el dominio del catálogo al que pertenece                                                                                                                                                                                                                                                                                                     |
| `destructive`, `read_only`                  | Si la acción es destructiva y si solo lee                                                                                                                                                                                                                                                                                                                          |
| `required_params`, `required_params_any_of` | Los parámetros que necesita toda llamada, cada uno con su tipo de JSON Schema, y los grupos alternativos de los que una llamada debe cumplir al menos uno                                                                                                                                                                                                          |
| `alias_of`                                  | La entrada principal, cuando este ID es un alias deliberado de otra acción que se mantiene para el descubrimiento                                                                                                                                                                                                                                                  |
| `call`                                      | La herramienta a la que llamar y dónde va cada parte: en dinámica, la acción en `action`, los parámetros en `params` y la confirmación en un `confirm` de primer nivel; en meta, la acción en `action`, y los parámetros y el flag `confirm` juntos en `params`; en individual, los parámetros son los propios argumentos de la herramienta, `confirm` entre ellos |
| `input_schema`                              | El JSON Schema de los parámetros que acepta la entrada                                                                                                                                                                                                                                                                                                             |
| `fine_grained`                              | Lo que necesita un token de acceso personal de grano fino para ejecutar la acción (abajo)                                                                                                                                                                                                                                                                          |
| `withheld`                                  | Por qué una sesión de grano fino no puede ejecutar la acción, solo para esa sesión (abajo)                                                                                                                                                                                                                                                                         |

`call` indica dónde va la confirmación solo en una entrada destructiva. En la superficie individual los argumentos van directamente a la herramienta, sin envoltorio `action` ni `params`.

#### El bloque `fine_grained`

El detalle de una acción del catálogo lleva un bloque `fine_grained` en todas las sesiones, también con tokens clásicos, porque el detalle es donde un modelo consulta lo que necesita una acción. Indica lo que necesita un token de acceso personal de grano fino para ejecutar la acción, tal como lo declara la versión de GitLab indicada en `gitlab_version`, con las palabras de la página de creación de tokens de GitLab. A un token clásico no se le juzga por él: lo que puede hacer lo deciden sus scopes.

| Campo                 | Significado                                                                                                                                                                                                                                                                       |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `gitlab_version`      | La versión de GitLab en la que se registró el requisito                                                                                                                                                                                                                           |
| `any_of`              | Las formas de ejecutar la acción, de las que basta cualquiera, porque la acción envía una petición distinta según su entrada. Cada forma enumera sus `needs`: los permisos que comprueba GitLab, con todos los permisos de una necesidad concedidos en uno de los ámbitos de `at` |
| `not_judged_by_grant` | Se marca en una forma que envía una petición que GitLab deja a las demás propiedades del token en lugar de a su concesión                                                                                                                                                         |
| `denied_ways`         | Las formas que ningún token de grano fino ejecuta en esa versión, cada una con la `cause`, el `element` y el `effect` de su denegación: la acción se ejecuta, salvo con una entrada que le haga enviar una de esas peticiones                                                     |
| `always_empty`        | Partes de la respuesta que GitLab sirve vacías a todo token de grano fino, cada una escrita como la selección GraphQL que llega a ella desde el campo que pide la acción                                                                                                          |
| `empty_without`       | Partes de la respuesta que GitLab sirve vacías salvo que la concesión incluya también lo que nombran los `needs` de cada entrada, con la parte escrita en `selection`                                                                                                             |
| `denied`              | Aparece en lugar del resto cuando ningún token de grano fino puede ejecutar la acción en esa versión: la `cause`, el `element` que lo decide (una ruta, un tipo GraphQL o una mutación) y el `effect` que GitLab aplica a la petición                                             |

El bloque se deriva de los manejadores de la acción y de un registro de lo que declara un GitLab arrancado, mediante `cmd/gen_action_grants`, y es la misma tabla que decide [lo que se muestra a una sesión de grano fino](/gitlab-mcp-server/es/operations/fine-grained-tokens/#lo-que-se-muestra-a-una-sesión). Las herramientas independientes que las superficies meta e individual registran junto a su catálogo, entre ellas los flujos guiados, llevan el bloque de la acción que es cada una; una entrada que no nombra ninguna acción, como las dos herramientas de la superficie dinámica o un despachador meta, no lleva ninguno.

#### Una acción retenida

Una sesión con un token de grano fino lee los dos recursos del manifiesto acotados a lo que puede ejecutar. `gitlab://tools` omite las entradas y las herramientas visibles que omite su `tools/list`. `gitlab://tools/{id}` de una acción omitida se sirve en lugar de responder que no existe, con un bloque `withheld` que lleva la `cause` (`not-granted` cuando la concesión del token no alcanza la acción, o una de las causas de denegación cuando ningún token de grano fino la alcanza) y el `message` con el que se rechaza una llamada a la acción. Cuando la acción se omite del listado pero una llamada a ella se sigue pasando a GitLab (una lectura que GitLab sirve en un proyecto o grupo público o, en la versión preliminar posterior a la registrada, una llamada que no se retiene a todo token de grano fino), el mensaje lo dice. En la superficie meta, el detalle de una herramienta con todas sus acciones retenidas también lleva el bloque, sin causa propia y con una lista `actions` que da el `id`, la `cause` y el `message` de cada acción, porque las acciones de un grupo no tienen por qué compartir motivo. Las lecturas de un token clásico nunca se acotan. [Leer una respuesta retenida](/gitlab-mcp-server/es/operations/fine-grained-tokens/#leer-una-respuesta-retenida) cita los dos textos de rechazo.

### Recursos de guías de flujo de trabajo (5)

Guías estáticas de mejores prácticas para asistentes de IA, escritas en el propio servidor: leer una no hace ninguna petición a GitLab, y cada una declara su tamaño en bytes en el listado, para que un cliente pueda reservar contexto antes de leerla. Una guía nombra cada llamada por su ID canónico de acción (`pipeline.get`), que se lee igual sea cual sea la superficie servida.

| Recurso                                    | Nombre                     | Título                         | Descripción                                                                                                |
| ------------------------------------------ | -------------------------- | ------------------------------ | ---------------------------------------------------------------------------------------------------------- |
| `gitlab://guides/git-workflow`             | `git_workflow`             | Git Workflow Guide             | Buenas prácticas de estrategias de ramas Git con GitLab (ramas de funcionalidad, trunk-based, GitLab Flow) |
| `gitlab://guides/merge-request-hygiene`    | `merge_request_hygiene`    | Merge Request Hygiene Guide    | Pautas para crear y revisar merge requests de calidad                                                      |

| `gitlab://guides/pipeline-troubleshooting` | `pipeline_troubleshooting` | Pipeline Troubleshooting Guide | Problemas habituales de los pipelines CI/CD de GitLab y cómo diagnosticarlos y corregirlos                 |

### Las colecciones devuelven una página

`resources/read` no tiene continuación. MCP limita la paginación a los métodos de listado (`resources/list`, `resources/templates/list`, `tools/list`, `prompts/list`) y no define ni un cursor ni una forma de resultado parcial para una lectura, así que un recurso de colección no puede devolver un token de página y un cliente no puede pedir la página siguiente.

Por eso los 13 recursos de colección (`gitlab://groups` y todas las plantillas de arriba cuya descripción dice "hasta una página") piden a GitLab una página de 100, el máximo de GitLab, e indican si están completos en `_meta`, bajo la clave con espacio de nombres del proveedor `io.github.jmrplens/pageInfo`:

```json
{
  "_meta": {
    "io.github.jmrplens/pageInfo": { "returned": 100, "total": 137, "complete": false }
  },
  "contents": [{ "mimeType": "application/json", "text": "[…]" }]
}
```

`returned` es el número de elementos del cuerpo. `total` es cuántos existen, y se omite cuando GitLab no envía el total, como ocurre en los endpoints con paginación keyset. `complete` es el campo por el que decidir: vale `false` siempre que GitLab indica una página siguiente. Cuando vale `false`, lee los mismos datos desde la superficie de herramientas, cuyas acciones de listado paginan y devuelven `total_items`, `next_page` y `has_more`.

Esto también limita lo que ve una vigilancia: una suscripción a una de las tres listas suscribibles recibe avisos de los cambios dentro de la página que lee, no de los que quedan fuera ([ADR-0015](https://github.com/jmrplens/gitlab-mcp-server/blob/main/docs/development/adr/adr-0015-polled-resource-subscriptions.md), NEG-005).

### ¿Qué recursos se pueden vigilar?

26 plantillas aceptan una suscripción: todas las plantillas de un solo objeto de GitLab de arriba salvo el commit, que nunca cambia, más las tres listas que pertenecen a un único padre (los jobs de un pipeline, las notas de una merge request y sus discusiones). Los recursos estáticos, las demás colecciones, los dos recursos del manifiesto de herramientas y las guías no la aceptan.

Cada plantilla suscribible lo indica dos veces en `resources/templates/list`. Su descripción termina con la frase `Subscribable: subscriptions/listen (protocol 2026-07-28). Resources/subscribe on stateful sessions.`, que lee el modelo, y su `_meta` lleva `"io.github.jmrplens/subscribable": true`, por el que un cliente genérico puede filtrar sin conocer este servidor. La lista legible por máquinas se publica en dos sitios más, ambos solo en la superficie de capacidades completa:

- la sección `subscriptions` de `gitlab://tools`: `supported`, `subscribable_uri_templates` y la `notification` que envía un cambio;
- el bloque `subscriptions` de la [ficha del servidor](/gitlab-mcp-server/es/operations/http-server/#ficha-del-servidor) enumerativa que el modo HTTP sirve en `/.well-known/mcp/server-card.json`, junto a un objeto `capabilities` copiado del handshake. También indica qué método atiende este despliegue (`subscriptions/listen` en el transporte sin estado predeterminado, `resources/subscribe` con `--stateless=false`) y enumera los motivos por los que puede terminar una vigilancia. La ficha SEP-2127 de `/server-card` solo lleva la identidad y los datos de conexión, nada de esto.

[Suscripciones a recursos](/gitlab-mcp-server/es/capabilities/subscriptions/) explica la cadencia de sondeo, el coste y el ciclo de vida.

### Codificar un valor en una URI

Todas las variables salvo `{+path}` son expansiones simples de RFC 6570, y cada una ocupa exactamente un segmento de la ruta. Por eso un valor con cualquier carácter fuera de `A-Z a-z 0-9 - . _ ~` se codifica en porcentaje una sola vez antes de entrar en la URI: `group/project` se escribe `group%2Fproject`, la rama `feature/login` es `feature%2Flogin` y la etiqueta con ámbito `priority::high` es `priority%3A%3Ahigh`. El servidor decodifica cada variable exactamente una vez antes de consultar a GitLab, así que el valor que recibe GitLab es el que codificaste. Una barra sin codificar en una de estas variables, o bien no encaja con ninguna plantilla, y la lectura responde que el recurso no existe, o bien se lee como separador, como ocurre con el `{ref}` de la plantilla de archivos antes de `{+path}`, y se pide otro objeto. Codifícala. Los bloques de recurso que incrustan los resultados de las herramientas ya se escriben así, de modo que sus URIs pueden pasarse tal cual a `resources/read`.

`{+path}` es una expansión reservada: sus barras se quedan como están, y cada segmento se decodifica una vez como cualquier otra variable. La expansión reservada deja pasar un escape en porcentaje que ya exista, así que un archivo cuyo nombre contiene uno literalmente (`a%20b.txt`) debe llevar su `%` codificado como `%25` (`a%2520b.txt`), o se lee como `a b.txt`. Lo mismo vale para un nombre enviado sin codificar que contenga un escape válido, como una rama `fix-%41`: se decodifica, y nombra `fix-A`.

### Autocompletado de parámetros de URI

Mediante `completion/complete`, el servidor sugiere valores de `project_id` y `group_id` mientras se escriben, y de `merge_request_iid` e `issue_iid` a partir de las merge requests e issues abiertos del proyecto una vez que `project_id` está relleno en la misma petición. Ningún otro parámetro de URI recibe sugerencias, ni tampoco uno cuyos datos haya excluido un operador con `GITLAB_MCP_EXCLUDE_TOOLS`. [Autocompletado](/gitlab-mcp-server/es/capabilities/completions/) describe el mecanismo.

### ¿Cómo leo un recurso?

Los clientes MCP pueden solicitar recursos en cualquier momento usando el método `resources/read`:

```json
{
  "method": "resources/read",
  "params": {
    "uri": "gitlab://user/current"
  }
}
```

El servidor devuelve el contenido del recurso como JSON, o como Markdown en una guía de flujo de trabajo; una colección añade su información de página en `_meta`.

Para inspeccionar las formas de llamada aceptadas, lee primero el manifiesto de herramientas adaptado a la superficie y después el schema de la acción:

```json
{
  "method": "resources/read",
  "params": {
    "uri": "gitlab://tools"
  }
}
```

```json
{
  "method": "resources/read",
  "params": {
    "uri": "gitlab://tools/merge_request.create"
  }
}
```

Con `GITLAB_MCP_TOOL_SURFACE=meta` la entrada es `gitlab://tools/gitlab_merge_request.create`, y con `GITLAB_MCP_TOOL_SURFACE=individual` es el nombre de la herramienta, `gitlab://tools/gitlab_mr_create`: usa el ID que `gitlab://tools` haya listado para la superficie activa.

## ¿Qué son los prompts MCP?

Los prompts MCP son **plantillas reutilizables** que guían a los asistentes de IA a través de flujos de trabajo comunes. Cuando un cliente solicita un prompt, el servidor recopila los datos relevantes de GitLab y devuelve contexto estructurado que el LLM usa para producir una salida de alta calidad —una revisión de código, un borrador de notas de release o un informe de equipo— sin que el usuario tenga que volver a explicar la tarea cada vez.

El servidor proporciona **{stats.prompts} plantillas de prompts** organizadas en categorías. Cada tabla enumera los argumentos de un prompt, leídos del propio registro del servidor: un argumento marcado con \* es obligatorio, y cualquier otro puede omitirse, con los valores predeterminados de [Argumentos comunes](#argumentos-comunes). Todo argumento de prompt es una cadena, como los define MCP. Un prompt lee una página de cada lista paginada que recopila, así que en un proyecto o grupo con mucha actividad su informe cubre parte de los datos; las acciones de listado equivalentes de la superficie de herramientas sí paginan. La página contiene 100 elementos en la mayoría de las listas de los prompts por categoría, 50 miembros del grupo en `team_overview` y `reviewer_workload`, 20 merge requests en `mr_discussion_health`, y el valor predeterminado de GitLab, 20, allí donde un prompt no indica tamaño de página: todas las listas de los prompts principales y los archivos modificados que lee `mr_description_quality`. Por eso `review_mr` y `summarize_mr_changes` ven como mucho 20 archivos modificados ([#1169](https://github.com/jmrplens/gitlab-mcp-server/issues/1169)).

| Resumir las MRs dirigidas a una rama                           | `branch_mr_summary`      |
| Revisar el estado de las MRs de un grupo                       | `group_mr_dashboard`     |
| Redactar notas de release                                      | `generate_release_notes` |
| Comprobar mensajes e historial de commits antes de una release | `audit_commit_hygiene`   |
| Auditar la gobernanza de un proyecto en conjunto               | `audit_project_full`     |
| Auditar solo etiquetas, milestones y plantillas                | `audit_project_workflow` |

### Autocompletado de argumentos de prompts

Mediante `completion/complete`, el servidor sugiere valores de `project_id`, `group_id` y `username` mientras se escriben. `merge_request_iid` (de las merge requests abiertas del proyecto), `from` y `to` (nombres de ramas y tags), `branch` y `target_branch` (nombres de ramas) y `milestone` (títulos de milestones) se sugieren una vez que `project_id` está relleno en la misma petición. `days`, `stale_days` y `state` no reciben sugerencias. Un autocompletado que nombra un prompt que este servidor no sirve se rechaza con `-32602`. [Autocompletado](/gitlab-mcp-server/es/capabilities/completions/) describe el mecanismo.

### ¿Cómo uso un prompt?

Los prompts se solicitan mediante el método MCP `prompts/get`:

```json
{
  "method": "prompts/get",
  "params": {
    "name": "review_mr",
    "arguments": {
      "project_id": "my-group/my-project",
      "merge_request_iid": "42"
    }
  }
}
```

El servidor devuelve un prompt estructurado con contenido consciente del contexto que el LLM usa para guiar su flujo de trabajo.

## Configuración

| Variable                        | Predeterminado | Descripción                                                                                      |
| ------------------------------- | -------------- | ------------------------------------------------------------------------------------------------ |
| `GITLAB_MCP_CAPABILITY_SURFACE` | `full`         | `full` registra recursos, guías, prompts y `gitlab://tools`; `minimal` mantiene `gitlab://tools` |

`GITLAB_MCP_EXCLUDE_TOOLS` acota también las superficies de esta página, no solo las herramientas: no se registra un recurso que devuelve los mismos datos de GitLab que una acción excluida, ni un prompt que lee esos datos, y el autocompletado que depende de ellos no responde nada. Consulta [Configuración](/gitlab-mcp-server/es/configuration/).

:::tip
Los recursos son particularmente útiles para proporcionar contexto del proyecto al inicio de una conversación. El recurso del proyecto le dice al LLM el propósito del repositorio, su ubicación y su rama predeterminada; `project_members` añade el equipo y `latest_pipeline` el estado de la rama predeterminada.
:::
