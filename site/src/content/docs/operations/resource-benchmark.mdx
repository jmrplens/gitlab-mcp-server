Nothing else published about this server says what it costs to run. This page
does: resident memory, processor time, goroutine count and per-method latency,
measured on both transports across the settings that move them.

<Aside type="tip" title="At a glance">

- **HTTP mode sizes by credentials that are calling.** An idle process holds no
  tool catalog; the first credential of a configuration builds one, and it is
  then shared by every other credential of that configuration.
- **Holding a credential and serving one differ by three orders of
  magnitude.** The concurrency series reports both at every step: 29 to 52 KiB
  of settled live heap per credential held, 0.84 to 4.05 MiB of peak resident
  set per credential calling.
- **`--max-http-clients` is therefore not a memory setting.** Its default of
  100 bounds about five mebibytes of tenancy. Size from concurrent callers.
- **The first call of a configuration pays for registration**, and it is
  hundreds of milliseconds to a second and a half. No later call pays it again,
  though on `individual` a warm `tools/list` still costs a third of a second.
- **The tool surface no longer changes what a credential costs to hold**, and
  still decides everything about the responses: a `tools/list` is 12 KB on
  `dynamic` and 3.2 MB on `individual`.

</Aside>

## How this was measured

The real binary, built from the current checkout and started the way a client
starts it, on both transports. GitLab is stood in by an HTTP server inside the
harness, so a run needs no instance, no credentials and no network, and two
people re-measuring compare this server rather than their GitLab
installations. The tool surface is passed explicitly rather than read from the
environment, so a developer machine and CI measure the same thing.

Everything below is regenerated by one command, `make bench-resources`, which
runs the benchmark and redraws the charts from the record it writes. The
machine, the build and the method are named in the text under the heading,
because a resident-set figure without them is a number nobody can act on.

The point scenarios stop at eight credentials. A shared deployment meets
hundreds, so the benchmark also runs a **concurrency series** per surface:
one HTTP process, given 1, 2, 5, 10, 20, 50, 100, 200, 500 and 1000 distinct
credentials in turn, each warmed with a `tools/list`, and measured over a
ten-second steady phase at each count in which every credential keeps calling
`tools/call` and `tools/list`. Each step records the resident set (mean and
peak), processor time per call, the p50 and p99 of both methods and the
goroutine count, and captures a CPU and a heap profile of the server through
its `--pprof-addr` listener, which the analysis reads and the site does not
publish.

**Each step is then measured a second time, with the load stopped.** The two
readings answer different questions: the resident set over the steady phase is
what N credentials cost while all of them are calling, and the settled reading,
taken after the load ends with a collection forced, is what they cost to hold.
The first is measured in megabytes per credential and the second in kilobytes,
so publishing the first as the second, which this page did, overstates a pooled
credential by three orders of magnitude. The settled resident set is recorded
beside the settled heap and lags it, because freeing a heap does not hand the
pages back: Go's scavenger returns them on its own schedule.

A series stops early rather than take the host down: before each
step the resident set it would reach is estimated from the steps so far, and
the rest of the list is skipped when the estimate exceeds the memory budget
(80% of the host's available memory unless one is given); a step whose
`tools/call` p99 passes 30 seconds is the last one run. Where a series
stopped, and why, is printed under its table. In the run published here none
of them stopped: all three reached a thousand credentials.

## What changed since the previous run

The figures on this page used to come from an earlier run on the same host, and
they moved by two orders of magnitude. Both runs measured the peak resident set
under load the same way, so that is the fair comparison between them; the
tenancy column below has no predecessor, because the earlier run took no
settled reading at all.

| Run                                | Commit     | Load, peak resident set per calling credential      | Tenancy, settled live heap per credential | Series reached    |
| ---------------------------------- | ---------- | --------------------------------------------------- | ----------------------------------------- | ----------------- |
| One MCP server per credential      | `afecf6ce` | 130.9 MiB `dynamic`, 63.5 `meta`, 90.8 `individual` | not measured                              | 100, 200 and 100  |
| One server per configuration shape | `2a92f7ec` | 4.05 MiB `dynamic`, 0.84 `meta`, 4.00 `individual`  | 50.9 KiB, 52.1, 29.1                      | 1000 on all three |

The earlier run's slope carried the tool catalog every pooled credential built
for itself; what is left is the requests in flight, which no amount of sharing
removes. Note that the earlier 130.9 MiB was a load figure too, and was
published on this page as though it were a tenancy one. That reporting error is
what the settled reading exists to close, so do not read the new 50.9 KiB as
its successor: they measure different quantities.

<Aside type="caution" title="Read these as shapes, not as constants">
One machine, one operating system, one Go toolchain. The relationships between
the numbers should carry to your host; the absolute values will not. The
resident set also includes memory Go's collector has not returned yet, which
is the honest thing to size a limit against and not the same as the live heap.
</Aside>

## Sizing a deployment

**stdio.** One process per client, and the process builds its catalog as soon
as it starts, so there is no idle state to save memory in. Between 108 and 254
MiB per process depending on the surface, with peaks under load a little
higher. Nothing is shared between processes: a developer machine running one
client will not notice, and a host running four of them measured 438 MiB to
1.04 GiB together.

**HTTP.** Start from 36 to 40 MiB for a process serving nobody, then add one
catalog per distinct configuration, built by the first credential that asks
for it and shared by every other credential of that configuration. The
eight-credential scenarios measured 0, 1 and -3 MiB per extra credential on
`dynamic`, `meta` and `individual`, which is nothing above the noise of a
resident-set reading: eight credentials on `dynamic` cost the same 114 MiB as
one. What is left to size for is the concurrent work.

**There are two axes, and only one of them is the pool.** Holding a credential
costs 50.9 KiB of settled live heap on `dynamic`, 52.1 KiB on `meta` and 29.1
KiB on `individual`, so a thousand admitted credentials are 89, 83 and 117 MiB
of live heap and under a third of a gibibyte of resident set. Serving them is
where an instance runs out: with every credential holding two to four requests
in flight, the peak resident set grows 4.05, 0.84 and 4.00 MiB per credential,
and at a thousand it reached 3.9, 1.0 and 4.4 GiB.

A practical rule for HTTP: **budget for concurrent callers, at 1 to 4 MiB
each depending on the surface, on top of 40 MiB for the process and one
catalog per configuration**. `--max-http-clients` bounds pooled credentials and
is not a memory setting: at 50 KiB each, its default of 100 is five mebibytes.
Shorten `--pool-idle-timeout` if you want entries reclaimed sooner, but expect
the memory back in kilobytes rather than gigabytes.

<Aside type="note" title="Two at-rest figures, both correct">
The end-to-end test that runs on every push reports about **8 KiB** per
credential, and the series above reports **29 to 52 KiB**. They answer
different questions. The test's clients complete their `tools/list` and
disconnect, so it measures the pool entry with no connection open. The
benchmark driver keeps its sockets open, four per credential on `dynamic` and
`meta` and two on `individual`, so its figure also carries the buffers behind
those connections, at roughly 11 KiB each. Size against the series figure: a
credential you are sizing for is a connected one.
</Aside>

**Throughput.** In the series, the calls completed per step stop growing at
about five credentials on `dynamic` and `meta`: a call costs 8 ms of processor
time, so a sixteen-thread host completes 12,000 to 19,000 per ten-second step
whatever the number of credentials, and latency past that point is queueing,
with the p50 of `tools/call` on `dynamic` climbing from 10 ms at one credential
to 175 ms at a hundred and 2.2 seconds at a thousand. `individual` is a
different shape: a `tools/call` costs about a millisecond, but a call there
averages 105 ms of processor time, because every second call is a `tools/list`
serialising three megabytes of schemas, so a single credential with two
requests in flight already keeps three cores busy.

## What a client waits for

The process is ready in milliseconds and the surface behind it is not. On HTTP
`/health` answers in about 52 ms while the pool holds nothing; the first
credential of a configuration builds its catalog, and that is where the wait
is: 0.39 seconds on `dynamic`, 0.41 on `meta` and 1.27 on `individual` on the
host measured. On stdio the process is executed in well under a millisecond and
starts building immediately, so its first request waits on the same work, at
0.36, 0.37 and 1.18 seconds.

That wait is per configuration rather than per credential, since the built
server is shared, and it returns: when every entry of a configuration has been
reclaimed by `--pool-idle-timeout` or evicted at the pool's size bound, the
next request that needs it rebuilds from scratch.

Once warm, the picture inverts. A `tools/list` costs 1 to 3 ms on `dynamic`,
23 to 47 ms on `meta` and 0.19 to 0.33 seconds on `individual`, which is the
cost of serializing 12 KB, 599 KB and 3.2 MB respectively. A client speaking
protocol 2026-07-28 may serve repeat listings from its own cache and pay this
less often, but it pays it at least once per session.

## Telemetry

Exporting over OTLP costs a handful of goroutines and measurable processor
time, and no material memory. It is off by default; see
[OpenTelemetry](/gitlab-mcp-server/operations/telemetry/) for what it exports
and where it goes.

## Reproducing

```bash
make bench-resources          # measure, then redraw everything
make bench-resources-render   # redraw from the committed record, no measuring
make check-bench-resources    # verify the charts match the record
```

The point scenarios take a few minutes, most of it spent building one catalog
per client, which is the cost being measured rather than overhead of the
harness; the series then take as long as the host's memory lets them, up to a
quarter of an hour per surface. The series can also be measured on one host
and rendered on another: build the driver and the server, and on the host
with the memory run the driver with `-binary`, `-json`, `-profiles` and
`-no-render`, which reads nothing from a repository; then copy the record back
and run `make bench-resources-render`. The developer-facing details, including
what the harness deliberately does not measure, are in
[the resource benchmark reference](https://github.com/jmrplens/gitlab-mcp-server/blob/main/docs/reference/resource-benchmark.md).
