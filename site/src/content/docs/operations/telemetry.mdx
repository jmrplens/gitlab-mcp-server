    a: "Operations, never their contents. The MCP method called, the canonical catalog action such as `issue.list`, whether it succeeded, and how long it took.     a: "No. A collector that is down, refusing connections or rejecting your credential produces log lines on stderr and changes nothing else: the same status, the same body and the same latency for every client. This server can export traces, metrics and logs over OTLP to a collector you
run. It is **off by default**.

<Aside type="note" title="Two things to know first">
Telemetry goes to **your** collector. Nothing is ever sent to the maintainer of
this project, and there is no address you have to opt out of.

What is recorded describes **operations**, never their contents: the action
called, the outcome, the duration. Not the project you named, not the issue
body, not your search query, not your token.
</Aside>

## Turning it on

<Tabs>
<TabItem label="HTTP mode">

```

</TabItem>

        "GITLAB_TOKEN": "glpat-…",

        "OTEL_EXPORTER_OTLP_ENDPOINT": "http://localhost:4318"
      }
    }
  }
}
```

</TabItem>
</Tabs>

That is the whole surface this project owns. The endpoint, the credentials, the
sampling, the batching and the resource attributes all come from the standard
`OTEL_*` environment variables the OpenTelemetry exporters read themselves.
Reinventing that surface would mean maintaining a second, worse copy of a
configuration you already know, and it would break the ordinary case of a host
that exports `OTEL_EXPORTER_OTLP_ENDPOINT` once for every service on it.

### Four traps in the standard variables

These are not this server's doing, and they catch people. Three of them leave
telemetry running on something other than what you meant; the fourth,
`http/json`, is refused at startup with an `ERROR` line,
`telemetry disabled: it could not be started`, and the server goes on serving
without telemetry.

<Aside type="caution" title="`http://` is not the default">
The Go exporters default to `https://localhost:4318`. Turning telemetry on with
no endpoint set attempts TLS against a plaintext local collector, and every
batch fails for all three signals. Write the scheme explicitly:
`OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318`. Writing bare
`localhost:4318` also yields https.
</Aside>

<Aside type="caution" title="Durations are integer milliseconds">
"Any value that represents a timeout MUST be an integer representing a number of
milliseconds." So `OTEL_EXPORTER_OTLP_TIMEOUT=30s` does not mean thirty seconds:
it parses as nothing and the 10s default stands.

```bash
OTEL_EXPORTER_OTLP_TIMEOUT=30000   # thirty seconds
OTEL_EXPORTER_OTLP_TIMEOUT=30s     # nothing; the default is kept
```

The `OTEL_BSP_*` and `OTEL_BLRP_*` durations (`*_SCHEDULE_DELAY` and
`*_EXPORT_TIMEOUT`), `OTEL_METRIC_EXPORT_INTERVAL` and
`OTEL_METRIC_EXPORT_TIMEOUT` behave the same way, while every flag *this*
server defines takes a Go duration, which makes the inconsistency easier to
trip over rather than harder.
</Aside>

<Aside type="caution" title="`http/json` is refused at startup">
Since v1.46.0 the Go trace exporter implements it and the metric and log
exporters do not. Honoring it would give one deployment two encodings at once,
JSON spans beside protobuf metrics, from a single setting that reads as though
it selects one thing. It fails by name rather than silently downgrading or
silently splitting.
</Aside>

<Aside type="caution" title="`OTEL_EXPORTER_OTLP_INSECURE=true` overrides an `https` endpoint for traces and metrics">
The specification says the variable "only applies to OTLP/gRPC when an endpoint
is provided without the http or https scheme". The Go trace and metric
exporters do not read it that way: their environment configuration applies the
scheme first and the `INSECURE` options after, so the later one wins and an
`https` endpoint is downgraded to plaintext, taking whatever credential you set
with it. The log exporters resolve the scheme first and are correct, which is
why one deployment can end up exporting two signals in the clear and the third
over TLS.

```bash
OTEL_EXPORTER_OTLP_ENDPOINT=https://collector.example.com:4318
OTEL_EXPORTER_OTLP_INSECURE=true   # traces and metrics go out in plaintext anyway
```

The precedence runs the other way too: an `INSECURE=false` beside an `http`
endpoint upgrades traces and metrics to TLS. For those two signals any
non-empty value decides and only `true` (in any capitalization) means plaintext, so
`INSECURE=1` upgrades them as surely as `false` does; the log exporter accepts
only `true` and `false` and ignores anything else.
</Aside>

This server emulates that deviation per signal rather than reading the scheme
off the URL, so the [plaintext warning](#authenticating-to-your-collector) names
the signals that are actually affected. It does not refuse the configuration:
the endpoint is yours to choose.

## Authenticating to your collector

There is **no username and password option**, and none is missing: the
specification defines no such variable. Every scheme is a header.

| What your collector wants | What to set                                                                                              |
| ------------------------- | -------------------------------------------------------------------------------------------------------- |
| Nothing (the default)     | Set nothing. A supported configuration, not a fallback.                                                  |
| A bearer token            | `OTEL_EXPORTER_OTLP_HEADERS=Authorization=Bearer%20YOUR_TOKEN`                                           |
| Basic auth                | `OTEL_EXPORTER_OTLP_HEADERS=Authorization=Basic%20$(printf 'user:pass' \| base64)`                       |
| A vendor API key          | `OTEL_EXPORTER_OTLP_HEADERS=api-key=YOUR_KEY`                                                            |
| Several at once           | `OTEL_EXPORTER_OTLP_HEADERS=Authorization=Bearer%20tok,x-tenant=acme`                                    |
| Mutual TLS                | `OTEL_EXPORTER_OTLP_CLIENT_CERTIFICATE=/path/cert.pem` and `OTEL_EXPORTER_OTLP_CLIENT_KEY=/path/key.pem` |
| A private CA              | `OTEL_EXPORTER_OTLP_CERTIFICATE=/path/ca.pem`                                                            |

A header configured for a signal whose endpoint is plaintext and on another
host, either an `http://` endpoint or an `https://` one that
`OTEL_EXPORTER_OTLP_INSECURE` downgrades as described above, crosses the
network in the clear on every export. This server does not refuse that
configuration, because a collector on a trusted private network reached over
plaintext is a real deployment and the endpoint is yours to choose. It does say
so once at startup, naming the signals affected:

```json
{"level":"WARN","msg":"a collector credential is configured against a plaintext endpoint on another host; it crosses the network in the clear on every export","component":"telemetry","signals":["traces"]}
```

Loopback is exempt: a credential that never leaves the machine cannot be observed
on a network, so a sidecar collector raises nothing.

<Aside type="danger" title="The encoding is where this goes wrong">
The value is W3C Baggage format and is percent-decoded.

- A space must be written `%20`. `Authorization=Bearer abc` is a malformed pair,
  dropped silently, and your collector sees an unauthenticated export.
- A literal percent must be written `%25`, and a literal comma `%2C`, since a
  comma separates pairs.
- Base64 padding is safe: `=` separates a key from its value at the **first**
  occurrence only, so the trailing `==` of a basic credential survives.

</Aside>

This server never transforms that variable. Whatever you set is what your
collector receives, and it is never logged: a test asserts the credential never
appears in this server's own log output, including when an export fails.

It is read, once, and only in order to keep it out of that output. The SDK's own
header parser prints what it could not parse, and the log exporter hands the
entire variable to the error handler, so one malformed non-credential pair is
enough to print a perfectly well formed credential beside it. This server reads
the same variables the exporters do at startup and redacts those values, and
their percent-decoded spellings, out of every SDK diagnostic it emits. The
variable name is left in place, because an operator whose configuration is
malformed needs to know which one to fix.

## A worked example

Everything above stops at your collector. The repository ships the other side
of it under
[`examples/telemetry/`](https://github.com/jmrplens/gitlab-mcp-server/tree/main/examples/telemetry):
one collector configuration and one Docker Compose file that run this server,
an OpenTelemetry Collector and a
[`grafana/otel-lgtm`](https://github.com/grafana/docker-otel-lgtm) backend
together, so you can make a call and watch its traces, metrics and logs arrive
in Grafana. The two files below are the committed ones, not copies. The
collector end-to-end suite runs the real server binary through the
configuration and reads back what it forwards, and holds the Compose file to
the same pipeline, so neither can drift from a collector that still accepts
what this server sends.

The `otlp_http/lgtm` exporter forwards all three signals to the backend by its

### The Compose file

<Code code={composeFile} lang="yaml" title="examples/telemetry/compose.yaml" />

The server runs in HTTP mode against `GITLAB_URL`, `https://gitlab.com` when you
set nothing, and is given no token: in HTTP mode every client sends its own
with each request. `OTEL_EXPORTER_OTLP_ENDPOINT` names the collector service,
and `OTEL_METRIC_EXPORT_INTERVAL` is ten seconds rather than the default

[below](#what-the-example-records-about-callers). The health check is the
image's own `--probe` with the image's own timing, restated so the example
shows it: it reads the listener off the running server's command line and
exits 0 once `/health` answers 200. The collector also publishes 4317 and 4318
on the host, for a server you run outside Compose.

### Start it and make a call

From the repository root:

```bash
docker compose -f examples/telemetry/compose.yaml up -d
docker compose -f examples/telemetry/compose.yaml ps
```

`ps` shows the server `(health: starting)` and then `(healthy)` within half a
minute. Make a call with your own token, the way every client of an HTTP
deployment does:

```bash
curl -s http://localhost:8080/mcp \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -H "PRIVATE-TOKEN: glpat-your-token" \
  -d '{"jsonrpc":"2.0","method":"tools/list","id":1}'
```

Point an MCP client at `http://localhost:8080/mcp` with the same token and
every call it makes is recorded the same way. When you are done:

```bash
docker compose -f examples/telemetry/compose.yaml down
```

### Where to look

`docker compose -f examples/telemetry/compose.yaml logs collector` is the
first place to look: the `debug` exporter writes one line there per batch.
Grafana is at `http://localhost:3000`, with no login, and its **Explore** view
has one data source per signal:

- **Tempo** holds the traces. Search by the service name `gitlab-mcp-server`:
  each MCP operation is a span named after its method, such as `tools/list` or
  `tools/call gitlab_execute_action`, with a child span for every GitLab
  request it made. The `GET` traces that arrive every thirty seconds are the
  health check asking `/health`, and GitLab requests such as
  `GET /api/v4/user` outside any MCP operation are the server checking a token
  before it first serves it.
- **Prometheus** holds the metrics, under the names Prometheus gives them:
  `mcp_server_operation_duration_seconds_bucket` for
  `mcp.server.operation.duration`, `http_client_request_duration_seconds_bucket`
  for the time GitLab takes, and the job label `gitlab-mcp-server`.
- **Loki** holds the logs: `{service_name="gitlab-mcp-server"}`. A record
  written while serving a call carries that call's `trace_id` and `span_id`, so
  it leads to the span it happened inside.

### Authenticating the collector side

The [table above](#authenticating-to-your-collector) is the server's half of
each scheme. The collector's half is an authenticator extension on its
receiver: `bearertokenauth` for a bearer token, `basicauth` for basic auth, and
`bearertokenauth` again, with a header name of its own and no scheme, for an
API key. Each block below is an overlay. Save it beside the configuration,
mount it into the collector and start the collector with both files, which it
merges in order:

```bash
--config=/etc/otelcol-contrib/config.yaml --config=/etc/otelcol-contrib/auth.yaml
```

In the Compose file that is a `command:` with those two flags and a second
line under `volumes:` for the collector, the variable the overlay reads in its
`environment:`, and `OTEL_EXPORTER_OTLP_HEADERS` in the server's, in the form
the first line of each block gives. The collector suite runs every block below
this way, over gRPC and over HTTP alike: the receiver refuses an export with no
credential, and passes on one sent with the header the table gives.

```yaml title="auth-bearer.yaml"
# Server: OTEL_EXPORTER_OTLP_HEADERS=Authorization=Bearer%20<COLLECTOR_TOKEN>
extensions:
  bearertokenauth:
    token: ${env:COLLECTOR_TOKEN}
receivers:
  otlp:
    protocols:
      grpc:
        auth:
          authenticator: bearertokenauth
      http:
        auth:
          authenticator: bearertokenauth
service:
  extensions: [bearertokenauth]
```

```yaml title="auth-basic.yaml"
# Server: OTEL_EXPORTER_OTLP_HEADERS=Authorization=Basic%20<base64 of user:password>
extensions:
  basicauth:
    htpasswd:
      inline: |
        ${env:COLLECTOR_USER}:${env:COLLECTOR_PASSWORD}
receivers:
  otlp:
    protocols:
      grpc:
        auth:
          authenticator: basicauth
      http:
        auth:
          authenticator: basicauth
service:
  extensions: [basicauth]
```

```yaml title="auth-api-key.yaml"
# Server: OTEL_EXPORTER_OTLP_HEADERS=api-key=<COLLECTOR_API_KEY>
extensions:
  bearertokenauth/apikey:
    header: api-key
    scheme: ""
    token: ${env:COLLECTOR_API_KEY}
receivers:
  otlp:
    protocols:
      grpc:
        auth:
          authenticator: bearertokenauth/apikey
      http:
        auth:
          authenticator: bearertokenauth/apikey
service:
  extensions: [bearertokenauth/apikey]
```

Mutual TLS is not an extension: it is the receiver's own `tls` block, a
`cert_file` and `key_file` it serves with and a `client_ca_file` naming the CA
the client certificates come from, paired with the two certificate variables in
the table. Inside one Compose project a credential crosses a private network in
the clear, and the server says so once at startup with the
[plaintext warning](#authenticating-to-your-collector); a collector on another
machine wants that `tls` block whichever scheme you use.

### What the example records about callers

The Compose file leaves `GITLAB_MCP_TELEMETRY_IDENTITY` at `none`, so the
traces say what was done and nothing about who did it. With the backend on
your own machine, `pseudonymous` lets Tempo tell one caller's traffic from
another's without naming anybody, and `full` puts `user.id`, `user.name` and
`gitlab_mcp.instance` on every span. Choose before you start it:

```bash
GITLAB_MCP_TELEMETRY_IDENTITY=pseudonymous docker compose -f examples/telemetry/compose.yaml up -d
```

What each value exports, and why `none` is the default, is under
[Recording who made a call](#recording-who-made-a-call). A deployment with more
than one replica that wants one pseudonym per caller across all of them also
needs `GITLAB_MCP_TELEMETRY_IDENTITY_KEY`, described under [Logs](#logs).

### Without Compose for the server

To export from a server you already run, start the collector and the backend
alone and point the server at the collector's published port:

```bash
docker compose -f examples/telemetry/compose.yaml up -d collector lgtm
OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318 \
  gitlab-mcp-server --http --gitlab-url=https://gitlab.com --telemetry
```

## What is recorded

### Spans

One span per MCP request, plus one child span per GitLab API call it caused.
HTTP mode adds one span per inbound HTTP request, described after the table.

| Attribute                   | On                       | Meaning                                                                                                        |
| --------------------------- | ------------------------ | -------------------------------------------------------------------------------------------------------------- |
| `mcp.method.name`           | every span               | `tools/call`, `resources/read`, `prompts/get`, …                                                               |
| `gen_ai.tool.name`          | tool calls               | the tool the client named                                                                                      |
| `gitlab_mcp.action`         | tool calls               | the canonical catalog action, such as `issue.list`                                                             |
| `gitlab_mcp.tool_surface`   | every span               | `dynamic`, `meta` or `individual`                                                                              |
| `network.transport`         | every span               | `pipe` for stdio, `tcp` for HTTP                                                                               |
| `gen_ai.prompt.name`        | `prompts/get`            | the prompt the client named                                                                                    |
| `mcp.protocol.version`      | when it is known         | the MCP revision the request is speaking                                                                       |
| `mcp.session.id`            | stateful sessions only   | absent under the default stateless HTTP transport                                                              |
| `error.type`                | failures only            | a JSON-RPC code, or `tool_error`                                                                               |
| `rpc.response.status_code`  | when a code was returned | the JSON-RPC code                                                                                              |
| `gitlab_mcp.domain`         | tool calls               | the catalog domain, such as `issue`; bounded, so it survives on metrics where the action id is too many values |
| `gitlab_mcp.refusal_reason` | refusals                 | why the call was declined without reaching GitLab                                                              |

`gitlab_mcp.action` is the one worth understanding. On the default dynamic
surface every tool call names the same two tools, so `gen_ai.tool.name` is
`gitlab_execute_action` whether the server listed issues or deleted a branch.
The action attribute is the only thing that tells them apart.

The child span of a GitLab call carries `http.request.method`, the host and
port it was sent to and the response status, and, when the route is one the
server's fine-grained permission table holds, `url.template`: the route as
GitLab declares it, such as `/api/v4/projects/:id/issues`, which also names the
span (`GET /api/v4/projects/:id/issues`). The template carries the placeholders
and never the values a request filled in. An instance installed under a path of
its own (a relative URL root, `https://host/gitlab`) gets the same template: the
path in front of `/api/` is the instance's and is left out. A request to a route
the table does not hold, `/api/v4/version` among them, carries no template, and
its span is named by its method alone. The template is a span attribute only:
it is not a dimension of `http.client.request.duration`, whose series it would
multiply by every route GitLab serves.

In HTTP mode every inbound HTTP request also gets a server span of its own,
opened before host validation, CORS and the credential check. The MCP span
starts after authentication, so this is the one that records a request refused
before it reached MCP, as its status code. It is named by the method and
carries `http.request.method`, `url.scheme` (read from the connection, never
from `X-Forwarded-Proto`), `network.protocol.name` and
`http.response.status_code`. A method outside the convention's list is recorded
as `_OTHER`, with the verb as sent, cut at 32 characters, in
`http.request.method_original` on the span only. It records no path, because on
a published endpoint the path is whatever a scanner sends. A `4xx` leaves the
span status unset, as the convention requires of a server span, and a `5xx`
marks it as an error.

### Metrics

| Instrument                             | Unit         | What it answers                                                                                                     |
| -------------------------------------- | ------------ | ------------------------------------------------------------------------------------------------------------------- |
| `mcp.server.operation.duration`        | `s`          | how long requests take, by method, domain and, where the tool name is kept, action                                  |
| `mcp.client.operation.duration`        | `s`          | how long this server waits on the client for what it initiates (elicitation, sampling, `roots/list`, notifications) |
| `http.client.request.duration`         | `s`          | how long GitLab takes                                                                                               |
| `gitlab_mcp.upstream.requests`         | `{request}`  | how many requests the process has sent GitLab, retries and redirect hops included, by `server.address`              |
| `mcp.server.session.duration`          | `s`          | how long a client stays connected (stdio and `--stateless=false`)                                                   |
| `gitlab_mcp.credential_pool.entries`   | `{entry}`    | how many credentials the pool holds (HTTP mode)                                                                     |
| `gitlab_mcp.credential_pool.capacity`  | `{entry}`    | how many it may hold, which is `--max-http-clients`                                                                 |
| `gitlab_mcp.credential_pool.evictions` | `{eviction}` | entries dropped, split by `gitlab_mcp.credential_pool.eviction.reason`                                              |
| `http.server.request.duration`         | `s`          | how long an inbound HTTP request takes, the credential check included and refused requests too (HTTP mode)          |
| `gitlab_mcp.auth.blocks`               | `{request}`  | requests refused before their credential was read, split by `gitlab_mcp.auth.block.reason` (HTTP mode)              |

`GITLAB_MCP_TELEMETRY_TOOL_NAME` (`--telemetry-tool-name`) decides two metric
dimensions together, `gen_ai.tool.name` and `gitlab_mcp.action`, because on the
individual surface each tool is one action and keeping either keeps as many
series as keeping both. `auto` keeps both on the dynamic and meta surfaces and
drops both on individual, `off` drops both on every surface and `on` keeps both.
`gitlab_mcp.domain` stays under every value, so a panel built on it survives,
and a panel built on the action shows one series per domain once the action is
dropped. Spans always carry both, whatever the setting.

`mcp.server.session.duration` is deliberately not recorded under the default
stateless HTTP transport, where each POST is its own session: the histogram
would be a copy of `mcp.server.operation.duration` under a name promising
something else.

`http.server.request.duration` is measured by the HTTP span above, and its
dimensions are that span's method, scheme, protocol name and status code, the
original verb left out. `gitlab_mcp.auth.blocks` counts each refusal under the
budget that answered it, as `gitlab_mcp.auth.block.reason`: `failure_lockout`
and `distinct_tokens` are the per-address
[authentication budgets](/gitlab-mcp-server/operations/security/#authentication-budgets),
`network_aggregate` is the one over the `/64`s of an IPv6 `/48`, and
`transport_source` is a coarser one charged to the address the connection
came from rather than to the one a trusted proxy header names, which exists
only when such a header is trusted. All four are exported from startup, zeros
included. The address refused is deliberately not a dimension: it would make
the series identify people, and grow without bound under exactly the traffic it
measures.

`gitlab_mcp.upstream.requests` counts every request the process sends GitLab,
and every redirect hop it follows from there, on both transports: the tool
calls' and the watchers', the OAuth verifier's and the health probes', which
`http.client.request.duration` does not see. Each attempt is one request, so a
request sent again after a `429` or a server error counts each time, because
GitLab counts each of them against its own limits
([What GitLab counts](/gitlab-mcp-server/operations/http-server/#what-gitlab-counts)).
A request the
[outbound guard](/gitlab-mcp-server/operations/security/#outbound-connections)
refused never left the process and is not counted. Its one dimension is
`server.address`, bounded as on `http.client.request.duration`: a host this
deployment is configured for is named, and every other one, an instance a
caller names under `--allow-any-gitlab-url` and a redirect off the instance
included, is `_OTHER`. A configured host is exported from startup, at zero.
No credential, user or path is on it: it is the deployment's count, which is
what GitLab.com's limit of 2,000 requests a minute per IP address is kept
against, and it limits nothing.

The three credential-pool instruments carry this server's own namespace rather
than the convention's `mcp.`, because a credential pool is this deployment's
concept and not the protocol's, and a name under `mcp.` would claim part of a
namespace the semantic convention owns. They are published by HTTP mode only,
and `capacity` is published beside `entries` so "how close to the bound" is
answerable without typing the flag's value into a dashboard query.

`gitlab_mcp.credential_pool.eviction.reason` takes one of eight values, one per
removal path, and every one of them is exported from process start whether it
has fired or not, zeros included, so a panel is never empty for the ambiguous
reason:

| Reason                | What happened                                                                                                                                                                                                                                                                                                                                                                                                                        |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `size_pressure`       | The pool was full and dropped the least recently used entry that was doing nothing                                                                                                                                                                                                                                                                                                                                                   |
| `size_pressure_busy`  | The pool was full, **every** entry was serving a subscription (a resource watcher or an open `subscriptions/listen` stream), and the oldest went anyway                                                                                                                                                                                                                                                                              |
| `idle`                | `--pool-idle-timeout` reclaimed an entry nobody had used                                                                                                                                                                                                                                                                                                                                                                             |
| `stale_credential`    | The credential had not been checked against GitLab inside the one-hour age ceiling, so the entry is rebuilt rather than trusted                                                                                                                                                                                                                                                                                                      |
| `rejected_credential` | GitLab refused the credential on a call: a `401` naming the token, or a `401` the credential probe then confirmed, never a permission refusal. A GraphQL `401` to a token carrying neither `api` nor `read_api` names the token too ([Refused calls](/gitlab-mcp-server/operations/http-server/#refused-calls))                                                                                                                      |
| `invalid_credential`  | Periodic revalidation found GitLab refusing the credential                                                                                                                                                                                                                                                                                                                                                                           |
| `below_minimum`       | GitLab said of a credential the pool already serves that it is genuine and carries neither `read_api` nor `api`, the admission minimum: a confirmation or a revalidation got `403 insufficient_scope`, or the token's own description, asked again because its kind was unknown when the entry was built, named only scopes below it ([Credential verification](/gitlab-mcp-server/operations/http-server/#credential-verification)) |
| `rebuild`             | The configuration shape's catalog registration failed, taking its entries with it                                                                                                                                                                                                                                                                                                                                                    |

`size_pressure_busy` is the one to alert on. Every eviction ends the
subscriptions of the credential it removes, but this is the only one that takes
a subscriber's entry for want of room, its credential still good, and it means
the pool held nothing quiet to take: see [the lever](/gitlab-mcp-server/operations/http-server/#the-lever-and-what-it-costs)
for the value of `--max-http-clients` that puts it out of reach. It has a
matching `WARN` line carrying `in_use=true` and the `max_size` to raise:

```text
server pool: evicted an entry that was serving a subscription
```

Entries dropped at shutdown are deliberately uncounted: nothing observes a
metric after the process ends.

One attribute the convention asks for is missing, and it cannot be supplied:
`jsonrpc.request.id`. The Go SDK gives a receiving middleware no access to the
JSON-RPC id of the message it is handling, so there is nothing to record. It is
[registered upstream](https://github.com/jmrplens/gitlab-mcp-server/blob/main/docs/development/upstream-bugs.md#a-receiving-middleware-cannot-read-the-json-rpc-request-id).

Seconds, not milliseconds. The convention fixes that, and it is the opposite of
the `duration` field in this server's log records.

Two of those dimensions carry a name the caller chose, `gen_ai.tool.name` and
`gen_ai.prompt.name`. On a metric they are bounded: a call that named something
this server does not have is recorded as `_OTHER` rather than under the name it
sent, so the number of stored time series follows what is registered rather than
what a client types. The span keeps the name verbatim, which is where you look
when a client reports that its calls are failing.

A refusal is not a malfunction, which is why it has an attribute of its own:
`error.type` cannot tell a call this server declined from one that broke. The
call arrived well formed and this server chose not to run it:

| `gitlab_mcp.refusal_reason` | Why                                           |
| --------------------------- | --------------------------------------------- |
| `safe_mode`                 | safe mode answered a write with a preview     |
| `needs_confirmation`        | a destructive action was not confirmed        |
| `invalid_params`            | the parameters do not fit the action          |
| `unknown_action`            | no action by that name exists on this surface |
| `rate_limited`              | the deployment's own limit rejected the call  |
| `fine_grained`              | a fine-grained token cannot run that action   |

Those six are the whole set, which is what makes the attribute affordable as a
metric dimension as well as a span attribute: a deployment refusing every third
call looks exactly like a healthy one on a duration histogram alone.

Some of them carry `error.type` as well, and that is not a contradiction. A
refusal the caller can fix is answered with an error result, so the model is
told plainly that its call failed; safe mode answers with a preview instead,
which is a successful result and sets no `error.type`. Group by the refusal
reason rather than by `error.type` when you want the declined calls.

`rate_limited` is the one worth alerting on, because it is the only refusal that
is not the caller's doing. Its log line is throttled to one every ten seconds,
so a client in a retry loop cannot flood the terminal; the metric counts them
all.

### Logs

The third signal is this server's own structured records: the same lines it
writes to stderr, exported from `INFO` upward. `GITLAB_MCP_LOG_LEVEL` still governs the
terminal; the export floor is separate, so running at `debug` does not send a
record per GitLab round trip to your collector on top of the span that already
describes it.

Every record written while serving a request carries the trace and span id of
that request, so a backend can jump from a slow span straight to the lines
written inside it. Startup, shutdown and background records carry none, because
there is no span to belong to.

The identity policy governs these records as well, and the two legs differ on
purpose. Your terminal keeps `user`, `user_id` and `instance` whatever the
policy says: you are reading your own server's output, and a setting about what
leaves the process has no business editing that. The exported copy carries what
the policy allows and under the same names the spans use, `user.*` and
`gitlab_mcp.instance`, so one query joins them.

That last paragraph was untrue until recently, and a live deployment is what
showed it: running on `pseudonymous`, which names nobody, its spans carried a
digest and its logs carried the username in the clear. The policy had been
applied where it was written and never to the log bridge.

By default the digest is keyed with a secret generated at startup and written
nowhere, so it identifies a caller within one process and nowhere else. A
deployment running several replicas gives the same person a different digest on
each, at the same time, and a restart renumbers everybody. For a single
instance that is usually what you want: nothing to store, nothing to leak.

Two settings change it, and which one you reach for follows from how you run
the server.

| Setting                                  | What it does                                                                                                                   |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `GITLAB_MCP_TELEMETRY_IDENTITY_KEY`      | a secret every replica derives its keys from, so one caller carries one digest across the whole deployment and across restarts |
| `GITLAB_MCP_TELEMETRY_IDENTITY_ROTATION` | how long a generated key lives, such as `24h`; empty keeps it for the life of the process                                      |

Set the key when you run more than one replica, or when a count of distinct
users has to survive a deploy. Rotation then does not apply: a key you supplied
is yours to rotate, on your schedule, and this server says so at startup rather
than rotating it underneath you.

Set the rotation interval when you run one instance and want the pseudonym to
stop correlating after a while. It is off by default because replicas start at
different moments, so they would rotate out of phase and a distinct-user count
would churn without anybody asking for it. An interval that is not a duration,
such as `24` with no unit, or one that is negative or longer than 30 days
refuses the start while telemetry is on and no key is set; beside a key it is
ignored, whatever it says.

Nothing prescribes either answer. The OpenTelemetry registry defines `user.hash`
as a value "to correlate information for a user in anonymized form" and says
nothing about how long it should hold, and neither the specification nor ENISA
offers guidance on the lifetime of a pseudonymisation secret. What the field
shows is two coherent designs, and Matomo ships both at once: an
installation-wide salt that never rotates where a pseudonym must persist, and a
seed discarded every day where it must not.

### What setting the key means

Say it plainly, because it is a real change in what the export is. A stable
pseudonym is what the EDPB calls a person pseudonym, which "requires long-term
storage of the pseudonymisation secrets" and whose "risk of unauthorised
attribution is comparatively high". Under GDPR Article 4(5) that key is the
"additional information" that allows attribution, so it has to be kept
separately from the data it protects.

Concretely: GitLab user ids are small integers, so anyone holding both the key
and an export recovers the mapping by enumeration, in about two minutes on one
core. The key must not live where the telemetry lands. An environment variable
is where this server reads it, with the caveat every environment secret carries:
it is visible to anything that can read the process environment.

The key is expanded with HKDF-SHA256 into two independent keys, one for callers
and one for resource URIs, so the value you supply is never used as a key
itself and a digest of a user cannot be compared against a digest of a resource.

Under `GODEBUG=fips140=only`, HKDF takes no key shorter than 112 bits, so a key
of fewer than 14 bytes cannot be used: the server starts, logs why and records
nothing about callers, as it does whenever it cannot derive its
pseudonymisation keys. 3.1.0 stopped the process with a panic on the same key.

### What is never recorded

Not by default and not by any setting, because there is no setting:

- **Tool arguments and results.** The conventions define `Opt-In` attributes for
  both; this server declines them, because they carry project paths, issue
  bodies and search queries.
- **Resource contents.** The URI that named the resource follows the identity
  policy: a keyed per-process digest by default, and the URI itself only under
  `full`, which already exports the caller's real name.
- **Your GitLab token**, or any header a client sent.
- **GitLab response bodies and error messages.** A failure records a
  classification such as `-32603`, never the text, which can name private paths.
- **Full URLs of GitLab calls.** The child span records the method, the host,
  the status and, where the server's table holds it, the route template, which
  names the endpoint with placeholders where the URL would carry project paths,
  identifiers and query values. The parent span already names the action.
- **`credential_hash`**, the handle an HTTP client's credential is logged by: a
  keyed digest of it, under a key drawn when the process starts and never
  written anywhere, so it carries none of the token's characters. It keeps
  being written to stderr, where it is what an operator correlates a refusal
  by on their own terminal, and it is stripped from the exported copy of every
  log record at any depth: it authenticates nothing and correlates everything
  one caller does, which is not a distinction a telemetry backend can make for
  you.
- **The `Host` header of a request the host guard refused.** It stays on
  stderr, where it is what you read to find out which host a misconfigured
  proxy is forwarding, and it is stripped from the exported copy the same way:
  on a published endpoint the value is whatever a caller chose to send. It
  reached collectors in 3.0.0, unnoticed because the test that says it cannot
  was winning its race against the log batch, and is stripped from 3.1.0 on.

An end-to-end test drives real traffic carrying a distinctive project path, a
search query and a token, then searches every exported payload for all three;
another sends a spoofed `Host`, a spoofed `X-Forwarded-For` and a probe path
and does the same.

## Recording who made a call

Off by default, in three steps:

```bash
--telemetry-identity none          # the default: nothing about the caller
--telemetry-identity pseudonymous  # a per-process digest: correlatable, not readable
--telemetry-identity full          # user.id, user.name and gitlab_mcp.instance
```

or `GITLAB_MCP_TELEMETRY_IDENTITY`.

A value the server does not recognise refuses the start, on either
transport, whenever telemetry is on, with an `ERROR` naming the flag or the
variable that held it. Starting anyway is what it used to do: the server ran
and recorded nothing about callers, and the only sign of why was in `ERROR`
lines of its logs, easy to miss behind a dashboard that simply stayed empty.
With telemetry off, or vetoed by `OTEL_SDK_DISABLED`, nothing is exported
under the setting and nothing is refused.

The policy governs one more thing than its name suggests: **which resource a
request named**. A resource URI here embeds project and group ids, so it says
what a caller is working on, which is the same class of disclosure as saying who
they are. Under `none` and `pseudonymous` a span carries
`gitlab_mcp.resource.ref`, a keyed per-process digest that correlates reads and
polls of one resource without naming it. Under `full` it carries
`mcp.resource.uri`, the convention's own attribute, with the URI in it.

One flag rather than two, because a deployment that recorded project paths while
claiming to record nobody would be the predictable result of letting the two
settings drift apart.

**`none`** is the default because whether to record a person's identity is your
decision about your own users, and a default that decides for you is wrong
whichever way it points. The conventions agree: these attributes are `Opt-In`,
whose rule is "Instrumentations SHOULD populate the attribute if and only if the
user configures the instrumentation to do so".

**`pseudonymous`** emits `user.hash`, an HMAC-SHA256 digest. By default its key
comes from 32 random bytes generated at startup and never written anywhere; with
`GITLAB_MCP_TELEMETRY_IDENTITY_KEY` set it is derived from that key instead
([Logs](#logs) has both settings). It gives a shared endpoint the
one thing it genuinely needs, telling one caller's traffic from another's, so a
burst can be attributed and a session followed, without naming anybody.

The digest is taken over the GitLab instance and the user id together, because
a user id names one person only within one instance: on a deployment that
publishes two instances, user 7 of each carries a digest of their own. Releases
before 3.5.0 took it over the user id alone, so the same person carries a
different digest after the upgrade, once.

<Aside type="note" title="Two properties of the digest">
By default it is **stable within a process and different after a restart**,
deliberately: a digest stable across processes would let anyone holding two
deployments' exports link the same person across both. Setting
`GITLAB_MCP_TELEMETRY_IDENTITY_KEY` makes it stable across processes and
restarts, which is that setting's purpose (read
[what setting the key means](#what-setting-the-key-means) first); a rotation
interval changes it within a process each time the generated key is replaced.

Pseudonymous is not anonymous. Somebody who can correlate a known person's
activity with a digest can link the two. That is inherent to the technique, not
to this implementation.
</Aside>

**`full`** emits `user.id` and `user.name`, and `gitlab_mcp.instance`, the
GitLab instance the call was answered by, which tells user 7 of one published
instance from user 7 of another. What an organization auditing its own users
wants, and what it is entitled to: those are its people and its collector.

None of these ever reach a **metric**, under any policy. A span carrying a user
id costs one span; a metric dimension carrying one is a time series per person,
growing without bound with the number of people using the deployment.

A request an HTTP server could not attribute to any credential is rare, a POST
whose client went away or a credential the pool dropped while serving it. A
`tools/list` or a `subscriptions/listen` of that kind is refused before
telemetry sees it and leaves no span; a tool call, a resource read or a prompt
is refused by its handler, inside its span.

## Turning it off

```bash
--telemetry=false      # do not turn it on; this is the default
OTEL_SDK_DISABLED=true # veto it from the environment, whatever the flag says
```

`OTEL_SDK_DISABLED` is the specification's own kill switch, and this server
honors it where nothing beneath it does: the string appears in no OpenTelemetry
Go module. It is a **veto** rather than a switch, because its specified default
means "enabled" while telemetry here is off until asked for. Setting it to
`true` forces no-op providers even when `--telemetry` was passed, which is what
lets you disable telemetry across a fleet without editing every unit file.

Its boolean grammar is the specification's and is stricter than Go's: only the
case-insensitive string `true` disables. `1`, `t` and `yes` do not, and an empty
value counts as unset.

## Seeing whether it is on

The enumerating server card reports it, at the `.well-known` path. The SEP-2127 card at `/server-card` states identity and connection details only, and carries no capability blocks.

```bash
curl -s http://localhost:8080/.well-known/mcp/server-card.json | jq .telemetry
```

```json
{
  "enabled": true,
  "signals": ["traces", "metrics", "logs"],
  "protocol": "http/protobuf",
  "conventions": "OpenTelemetry, following the MCP semantic convention",
  "recorded": "the method called, the tool and catalog action, the outcome and the duration",
  "not_recorded": "tool arguments, tool results, resource contents, queries, tokens, and GitLab response bodies"
}
```

The block is absent when telemetry is off, rather than present and saying
`false`: you should not have to parse a negation to learn that nothing is being
recorded. The collector address is deliberately **not** published there, because
it names your infrastructure and the card is served to anyone who asks.

## When it goes wrong

Telemetry failures never affect a request. A collector that is down, refusing
connections or rejecting your credential produces log lines on stderr and
changes nothing else: the same status, the same body, the same latency. The
specification leaves this choice open ("The API or SDK MAY fail fast … but MUST
NOT cause the application to fail later at runtime"), and the choice here is
that a server which can talk to GitLab keeps doing so when it cannot talk to a
collector.

```bash
GITLAB_MCP_LOG_LEVEL=debug gitlab-mcp-server --telemetry 2>telemetry.log
```

Export failures, malformed header pairs, unparseable durations and protocol
warnings all arrive there as structured records.

<Aside type="danger" title="On stdio, never use a console exporter">
`OTEL_LOGS_EXPORTER=console` and the stdout exporters write to **stdout**, which
on the stdio transport carries JSON-RPC and nothing else. One stray line ends
the session. This server ships no console exporter for that reason, and an
end-to-end test asserts stdout stays pure JSON-RPC while every export is
failing.
</Aside>
