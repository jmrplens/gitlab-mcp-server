A project's pipelines: list them, read one or the latest, run one, wait for one to finish, retry, cancel and delete one, update its metadata, and read its variables and its JUnit test report or summary. Deleting a pipeline removes its jobs with it.

Pipeline schedules (with their variables, running one now and taking one over), pipeline trigger tokens (and running a pipeline with one), and resource groups, the locks that keep jobs from running at once, are actions of this group too.

## Sample questions

- "Show the pipelines of project 42"
- "What is the status of the latest pipeline on main?"
- "Retry the failed pipeline"
- "Which tests failed in pipeline 1234?"

## How to call it

- **Dynamic**, the default surface: call `gitlab_execute_action` with `action` set to the action's ID, such as `pipeline.cancel`, and its parameters in `params`. `gitlab_find_action` finds an ID from a description of the task.
- **Meta** (`GITLAB_MCP_TOOL_SURFACE=meta`): call `gitlab_pipeline` with `action` set to the action's name, such as `cancel`, and its parameters in `params`.
- **Individual** (`GITLAB_MCP_TOOL_SURFACE=individual`): call the action's own tool, such as `gitlab_pipeline_cancel`, with its parameters as the arguments.

## Availability

Every tier serves the whole group, on self-managed instances and on GitLab.com alike.

Read-only actions: 15 of 33, the ones a deployment in read-only mode keeps. A token with `read_api` and not `api` is served 16 of the 33.
