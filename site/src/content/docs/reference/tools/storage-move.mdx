An administrator moves repositories between Gitaly storage shards with storage moves. For each of projects, groups and snippets these actions list every move, list the moves of one, read a move, schedule one, and schedule moves for every repository on a shard. Group moves are served from Premium.

## Sample questions

- "List the project storage moves in progress"
- "Move project 42 to the storage2 shard"
- "What is the state of group storage move 7?"

## How to call it

- **Dynamic**, the default surface: call `gitlab_execute_action` with `action` set to the action's ID, such as `storage_move.get_group`, and its parameters in `params`. `gitlab_find_action` finds an ID from a description of the task.
- **Meta** (`GITLAB_MCP_TOOL_SURFACE=meta`): call `gitlab_storage_move` with `action` set to the action's name, such as `get_group`, and its parameters in `params`.
- **Individual** (`GITLAB_MCP_TOOL_SURFACE=individual`): call the action's own tool, such as `gitlab_get_group_storage_move`, with its parameters as the arguments.

## Availability

How many of these actions an instance serves at each tier, out of a total of 18:

- **Free**: 12
- **Premium**: 18
- **Ultimate**: 18

Listed only for a token that carries `admin_mode`: the server removes the group from every surface for a token whose scopes it knows and that lacks it.

Read-only actions: 12 of 18, the ones a deployment in read-only mode keeps. A token with `read_api` and not `api` is served 12 of the 18.
