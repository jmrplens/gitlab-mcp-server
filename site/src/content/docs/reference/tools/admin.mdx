Instance-level administration of a GitLab instance: application settings and appearance, the license, broadcast messages, instance feature flags, system hooks, Sidekiq metrics, plan limits, usage data and Service Ping, database migration marks, OAuth applications, application statistics and metadata, custom attributes, and topics. Imports live here too: bulk imports between GitLab instances, and imports from GitHub, Bitbucket Cloud, Bitbucket Server and GitHub gists.

A few project-level features are also actions of this group: CI/CD secure files, error tracking settings and client keys, alert metric images, Terraform states, cluster agents and their tokens, and purging a group's dependency proxy cache. Most actions need an administrator, and GitLab refuses anyone else with its own error.

## Sample questions

- "Show the instance's application settings"
- "List the active broadcast messages"
- "Which Sidekiq queues are backing up?"
- "Import the GitHub repository acme/api into group platform"

## How to call it

- **Dynamic**, the default surface: call `gitlab_execute_action` with `action` set to the action's ID, such as `admin.alert_metric_image_delete`, and its parameters in `params`. `gitlab_find_action` finds an ID from a description of the task.
- **Meta** (`GITLAB_MCP_TOOL_SURFACE=meta`): call `gitlab_admin` with `action` set to the action's name, such as `alert_metric_image_delete`, and its parameters in `params`.
- **Individual** (`GITLAB_MCP_TOOL_SURFACE=individual`): call the action's own tool, such as `gitlab_delete_alert_metric_image`, with its parameters as the arguments.

## Availability

Every tier serves the whole group, on self-managed instances and on GitLab.com alike.

Listed only for a token that carries `admin_mode`: the server removes the group from every surface for a token whose scopes it knows and that lacks it.

Read-only actions: 41 of 92, the ones a deployment in read-only mode keeps.
