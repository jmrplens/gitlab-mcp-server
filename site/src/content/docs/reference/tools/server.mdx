Two read-only actions about this server rather than about GitLab's data. `server.status` reports whether the server reaches GitLab, the GitLab version and edition, and the user the token belongs to, and is the first thing to call when another action is refused with 401 or 403. `server.health_check` probes the connection to GitLab, and is served on the dynamic and meta surfaces only.

## Sample questions

- "Is the GitLab connection working?"
- "Which GitLab version is the server talking to?"
- "Which user does this token belong to?"

## How to call it

- **Dynamic**, the default surface: call `gitlab_execute_action` with `action` set to the action's ID, such as `server.status`, and its parameters in `params`. `gitlab_find_action` finds an ID from a description of the task.
- **Meta** (`GITLAB_MCP_TOOL_SURFACE=meta`): call `gitlab_server` with `action` set to the action's name, such as `status`, and its parameters in `params`.
- **Individual** (`GITLAB_MCP_TOOL_SURFACE=individual`): call the action's own tool, such as `gitlab_server_status`, with its parameters as the arguments.

## Availability

Every tier serves the whole group, on self-managed instances and on GitLab.com alike.

Read-only actions: 2 of 2, the ones a deployment in read-only mode keeps.

### `server.status`

> Check MCP server connectivity, GitLab reachability, and authenticated identity details.
