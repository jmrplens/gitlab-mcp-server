Everything done to a project: create (for the user or for someone else), read, list, update, fork, star, archive, transfer, delete and restore it, with its forks, starrers, users, groups, languages, statistics and storage; its members and its sharing with groups; webhooks; labels, milestones, boards and badges; push mirrors; Pages and its custom domains; integrations, including group integrations and the group Datadog integration; Markdown uploads and its avatar; export and import; housekeeping; and its service accounts with their personal access tokens.

From Premium the project also carries approval rules and approval settings, push rules, pull mirroring, target branch rules and the dependency firewall's package evaluation; from Ultimate, its security settings. Repository content, branches, issues and merge requests have pages of their own.

`project.transfer` needs the Owner role on the project and permission to create projects in the target namespace. Since GitLab 19.4 GitLab applies a transfer in the background (GitLab 18.11 to 19.3 do so when the `groups_and_projects_async_transfer` feature flag is enabled): it answers with the project where it still is, and a worker moves it and checks there that the name and path are free in the target namespace. The action reads the project back every 2 seconds for up to 45 seconds. GitLab reports a failed move only as a pending to-do item of action `transfer_failed` for the user who asked for it, which the action turns into an error; a move that has neither landed nor failed by then is answered with `transfer_queued` set. Read the project back later with `project.get`, look for that item with `user.todo_list`, and do not send the transfer again, since GitLab runs a second transfer as well while the first is queued.

`project.dependency_firewall_evaluate` is an experiment GitLab 19.4 introduced behind the `dependency_firewall_phase1` feature flag, which is disabled by default, and while it is off every project on the instance answers 404; the action answers that 404 by naming the flag first. With the flag on, GitLab evaluates a package only for a project the Dependency Firewall is turned on for, and answers 422 (`dependency_firewall_not_enforced`) for any other: on a self-managed instance an administrator turns it on under Admin > Settings > Security and compliance > Dependency firewall, which no API sets, and on GitLab.com an Owner turns it on in the top-level group's security settings. Until a verdict arrives, treat the package as not evaluated rather than as allowed.

## How to call it

- **Dynamic**, the default surface: call `gitlab_execute_action` with `action` set to the action's ID, such as `project.approval_config_change`, and its parameters in `params`. `gitlab_find_action` finds an ID from a description of the task.
- **Meta** (`GITLAB_MCP_TOOL_SURFACE=meta`): call `gitlab_project` with `action` set to the action's name, such as `approval_config_change`, and its parameters in `params`.
- **Individual** (`GITLAB_MCP_TOOL_SURFACE=individual`): call the action's own tool, such as `gitlab_project_approval_config_change`, with its parameters as the arguments.

### `project.approval_config_change`

> Change a project's approval configuration. Returns: the updated approval settings. See also: [`project.approval_config_get`](#projectapproval_config_get), [`project.approval_rule_create`](#projectapproval_rule_create).

- **Meta-tool**: `gitlab_project`, action `approval_config_change`
- **Individual tool**: `gitlab_project_approval_config_change`
- **Tier**: Premium
- **Behavior**: writes, idempotent

| Parameter                                        | Type             | Mandatory | Description                                                                                      |
| ------------------------------------------------ | ---------------- | --------- | ------------------------------------------------------------------------------------------------ |
| `project_id`                                     | `string/integer` | yes       | Project ID or URL-encoded path                                                                   |
| `approvals_before_merge`                         | `integer`        | no        | Number of approvals required before merge                                                        |
| `disable_overriding_approvers_per_merge_request` | `boolean`        | no        | Prevent overriding approvers per MR                                                              |
| `merge_requests_author_approval`                 | `boolean`        | no        | Allow MR author to approve their own MR                                                          |
| `merge_requests_disable_committers_approval`     | `boolean`        | no        | Prevent MR committers from approving                                                             |
| `require_password_to_approve`                    | `boolean`        | no        | Require the approver's password to approve (deprecated: use require_reauthentication_to_approve) |
| `require_reauthentication_to_approve`            | `boolean`        | no        | Require reauthentication to approve                                                              |
| `reset_approvals_on_push`                        | `boolean`        | no        | Reset approvals when new commits are pushed                                                      |
| `selective_code_owner_removals`                  | `boolean`        | no        | Only remove code owner approvals when relevant files change                                      |
