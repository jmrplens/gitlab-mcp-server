What a fine-grained personal access token needs for each action this server offers, as GitLab 19.4.1 declares it. The requests come from the handlers ([`docs/development/action-requests.json`](https://github.com/jmrplens/gitlab-mcp-server/blob/main/docs/development/action-requests.json)) and the permissions from the authorization GitLab records for each route, GraphQL type and mutation ([`docs/development/gitlab-api-live.json`](https://github.com/jmrplens/gitlab-mcp-server/blob/main/docs/development/gitlab-api-live.json)). Permissions are named in GitLab's own words, as its token creation page shows them, with the boundary each is held at: a token whose grant covers every permission of one line, at one of the boundaries named, can run the action. Where an action has several lines, any one of them is enough, since the action sends a different request depending on its input. Where one of those requests is one no fine-grained token passes, the entry says so after what the others need: the action runs, except with an input that makes it send that request.

An action GitLab declares nothing for cannot be run with a fine-grained token at this release, whatever the grant says: the reason is in the second column, and a classic personal access token is the way out. **Served empty** names a part of the answer GitLab leaves out for a fine-grained token while the rest is served: always, or unless the grant also holds what follows it. Each part is written as the GraphQL selection that reaches it from the field the action asks for.

This table judges fine-grained tokens alone. The scope a classic personal access token or an OAuth token needs for each action, `read_api` or `api`, is printed on the action's entry in the [tool reference](/gitlab-mcp-server/reference/tools/), beside its tier and the line this table holds for it. The fine-grained requirement is also served for each action in the `fine_grained` block of its `gitlab://tools/{id}` detail. [Fine-grained tokens](/gitlab-mcp-server/operations/fine-grained-tokens/) covers creating a token, what the server needs from it at startup, and how a refusal reads.
